# 🛠️ Development

Install the package in editable mode:

```sh
$ git clone git@github.com:datamodel-code-generator/datamodel-code-generator.git
$ pip install -e datamodel-code-generator
```

# 🤝 Contribute

We are waiting for your contributions to `datamodel-code-generator`.

Before you open an issue or a pull request, read the
[contribution policy](https://github.com/datamodel-code-generator/datamodel-code-generator/blob/main/.github/CONTRIBUTING.md):
problems from real use are welcome, AI tools are welcome, every pull request links an issue, and planned work stays
with the maintainers.

## 📝 How to contribute

```bash
## 1. Clone your fork repository
$ git clone git@github.com:<your username>/datamodel-code-generator.git
$ cd datamodel-code-generator

## 2. Install [uv](https://docs.astral.sh/uv/getting-started/installation/)
$ curl -LsSf https://astral.sh/uv/install.sh | sh

## 3. Install tox with uv
$ uv tool install --python-preference only-managed --python 3.13 tox --with tox-uv

## 4. Create developer environment
$ tox run -e dev

.tox/dev is a Python environment you can use for development purposes

## 5. Install pre-commit hooks
$ uv tool install prek
$ prek install

## 6. Create new branch and rewrite code.
$ git checkout -b new-branch

## 7. Run unittest under Python 3.13 (you should pass all test and coverage should be 100%)
$ tox run -e 3.13

## 8. Format and lint code (will print errors that cannot be automatically fixed)
$ tox run -e fix

## 9. Check generated docs, diagrams, and playground assets are up to date
$ tox run -e docs-check-all -- --check

## 10. Commit and Push...
```

## 🧪 E2E test assertions

E2E tests that validate generated output must use the shared assertion helpers
instead of direct `assert` statements. The helpers compare complete generated
files, generated modules, warnings, errors, and HTTP request behavior with
consistent diffs and update hints.

Use helpers such as `run_main_and_assert`, `run_main_url_and_assert`,
`create_assert_file_content`, `assert_output`, `assert_directory_content`,
`assert_generated_modules_output`, `assert_generated_file_matches_output`,
`assert_httpx_get_kwargs`, and `assert_warnings_contain` where they fit. Prefer
full expected-file or inline snapshot comparisons for generated output over
substring checks.

Tests do not need to name expected files. Write the test with the helpers (input
and arguments only), run `pytest '<test>'`, and commit every file it writes:
`tests/data/expected/**` and the `.refs` files, which can include those of other
modules that share output with it; `git add -A tests` stages them all and the
run lists them. To accept changed
output, run `pytest '<test>' --inline-snapshot=fix`. Never edit `.refs` or
expected files by hand; every failure prints the exact command that fixes it.
Review the resulting `git diff` before committing.

Each test module has a `.refs` file next to it that records, per test, which
stored expected output it compares. pytest writes it, starting with a
`# Generated by pytest. Do not edit by hand` header that local runs restore and
CI requires. Plain local runs create
missing expected output (the `[tool.inline-snapshot]` default flags in
`pyproject.toml`); `pytest -n` runs only rewrite `.refs` files into the form
pytest writes (sorted, with the header), and CI runs never write. Tests with the same
output share one stored file. When a fix changes the output of only some of the
tests that share a file, those tests get their own file and the others keep
theirs, so a partial run never changes what other tests compare against; the
report prints the command that updates the others too. When a CI lane produces
different output than your environment, its failure ends with a
`python scripts/fix_expected.py --apply '...'` command (or use
`--from-ci <run id>`) that writes that lane's output as an override for that
environment only, so other environments keep the stored file and no other
interpreter or formatter is needed locally. When lanes that would get
different overrides send the same output for one stored file (lanes that share
one override, such as one Python on two platforms, count once), the change is
common to them and belongs in the stored file itself: the command then writes
nothing for that file and prints how to go on, either regenerating it locally,
rerunning with `--as-base`, or rerunning with `--per-environment` (one override
per lane). `--as-base` writes that output as the stored file and drops the
overrides equal to what their lanes then compare. Every environment without an
override of its own then compares that output: yours, and the lanes that sent
no payload because they passed or did not run. Run the tests here, and check
those lanes with a dispatch run of the Test workflow on your branch
(`gh workflow run test.yaml --ref <branch>`), which also runs the lanes pull
requests skip.
`python scripts/fix_expected.py --where '<test>'` shows where a test's expected
output is stored.

Direct `assert` statements are blocked in guarded test modules by
`tests/test_assert_helper_usage.py`. New test files are guarded by default; add
legacy or unit-focused files to
`assert_helper_direct_assert_exempt_files` in `pyproject.toml` only when they
are intentionally outside the generated-output helper policy. Use
`@pytest.mark.allow_direct_assert` for narrow in-file exceptions that cannot
reasonably be expressed with the shared helpers, such as external-request mock
checks or intermediate-state checks.

## 🎯 Client and server target tests

Tests for the generated client and server (FastAPI) packages live in `tests/api_generation/`. The client runtime
scenarios, one module per behavior such as `client_retry_calls.py`, live in `tests/api_generation/scenarios/`, and
`test_client_runtime.py` drives them. The shared harness, fixture servers, and generation helpers live in
`tests/api_generation/support/`. The other `test_*.py` modules (client generation, CLI, typing, and the FastAPI
tests) keep their own cases and use `support/` for setup. Both directories are linted and covered like other tests,
except for the modules still listed in `[tool.coverage] run.omit` in `pyproject.toml`; issue
[#4572](https://github.com/koxudaxi/datamodel-code-generator/issues/4572) tracks removing those entries.

Tests go through the public `generate()` function or the `datamodel-codegen` CLI only. Do not assert on
internal objects, and use mocks only for abnormal paths (injected faults, marked with
`@pytest.mark.abnormal_path`) and external services.

A generated client copies the codec module of its own model backend only. The dataclass and TypedDict modules,
`_runtime/model_codecs/stdlib_dataclasses.py` and `stdlib_typeddicts.py`, are derived from `stdlib.py.jinja2` beside
them: edit that source and run `python scripts/build_stdlib_codecs.py`. Its `--check` option, which
`tests/model_codecs/test_wire_values.py` runs, fails when a module differs from what the source derives.

Expected output lives under `tests/data/expected/main/generation_platform/`:

- `client/packages/<case>/<backend>/` and `fastapi/packages/<case>/<backend>/` hold generated packages, including
  server `README.md` files where the case selects one.
- `client/bindings/<case>/<backend>/<variant>/client/_generated/model_bindings.py` pins the model bindings each
  case generates.
- `client/capabilities/*.txt` and the other `*.txt` reports list copied runtime modules by name. Line counts appear
  only in `minimal`. Each capability report also lists the modules the package imports from outside the standard
  library: those of the printed dependencies, then the others, which only those dependencies' own requirements may
  provide.
- `client/typing/dependencies/*.txt` hold the checkers' findings for a package of each backend where only its
  printed dependencies are installed.
- Reports hold listings, diagnostics, and outcomes. Generated source is pinned as files at its generated path, not
  embedded in a report.

Compare output with the helpers described under "E2E test assertions":
`assert_output` for reports, `assert_generated_modules_output` for `generate(output=None)` modules,
`assert_exact_directory_content` for trees written to disk, and `run_main_and_assert` for CLI runs. Regenerate
expected files by running the module with `--inline-snapshot=fix` (without `-n`). Under `pytest-xdist`, expected files
are neither created nor fixed, but comparisons still run.

`tests/test_assert_helper_usage.py` guards these directories against direct asserts, unit-style checks, and
private imports. Its exceptions are listed in `tests/assert_helper_allowlists.py`. Those lists only shrink: remove
an entry when you fix its violation, and do not add new ones.

## CI certificate stores

Keep the lockfile's certifi and uv versions, the pinned Windows uv, the composite action's pip, and the PyPI publishing
action updated together when their bundled CAs change. Docker builds update the OS CA package in the shared base stage
and use fresh build layers when publishing.

Node used by Wrangler and the release analysis action is selected separately from the GitHub runner's Node executable
that runs JavaScript actions. `actions/setup-node` updates the former only. Hosted runner updates and third-party
action containers must also include the CA fixes; self-hosted runners need their own updates. The release analysis
action additionally installs Bun and a native CLI, with independent trust stores. As of 2026-10-21, the eMudhra fix for
Bun is [merged but awaiting a release](https://github.com/oven-sh/bun/pull/46159). A Node upgrade does not fix those
embedded stores. Consult the [incident's runtime update list](https://emudhra.we-have-a-problem.com/) before updating
their pins or treating the entire CI environment as remediated.

## Documentation formatting

Ruff formats Python code blocks in Markdown, including hand-written explanations.
Documentation builders surround fixture-backed examples and generated output with
`<!-- fmt: off -->` and `<!-- fmt: on -->` so the displayed code keeps the exact
quote style and layout produced by the documented command. Keep these markers in
the builders rather than editing generated Markdown directly.

After changing documentation, regenerate the affected pages, run
`python scripts/build_migration_docs.py` (`docs/llms.txt` lists the upgrade guide's
pages) and then `python scripts/build_llms_txt.py`, which updates the committed
`docs/llms.txt` (`docs/llms-full.txt` is built when the site is deployed and is not
committed). Run `tox run -e fix` and
`tox run -e docs-check-all -- --check` to verify formatting and generated content
agree.

## Release notes

Release notes should describe changes that affect users: features, fixes,
generated output, performance, compatibility, installation requirements, and
the official GitHub Action or Playground.

Use the `skip-changelog` PR label for changes that only maintain tests, CI,
release automation, generated documentation, or development tooling. The
release workflow adds it automatically when every changed file is a known
maintenance file, including CHANGELOG updates and release benchmark data.
Other changes need a maintainer's judgment before applying the label.

Check the complete diff before excluding dependency updates, refactors, or
documentation changes. They can affect users through `action.yml`, packaged
CLI prompt data, Playground assets, or generated code. A PR that mixes
maintenance with user-facing changes should stay in the release notes.

The label only filters GitHub's generated change list. Breaking-change
analysis still runs independently, and the full comparison link remains
available. Excluded PRs receive no release notification unless they are
referenced elsewhere in the release body.

## Upgrade guide entries

The [upgrade guide](migration/index.md) and the release notes' Breaking Changes are built from one list of
changes, one TOML entry per change a user meets when upgrading. A pull request that makes such a change adds its
entry as `docs/data/migration/unreleased/<id>.toml`; the release moves it into
`docs/data/migration/changes/<version>.toml`.

Write an entry for every behaviour change of the default output and every removal (an option, an option value, a
template, a public name), and also for runtime floors, Python API behaviour, custom template content, inputs that are
now refused and changes of experimental features that shipped in a release. A change of the generated text only, whose
models behave the same, gets an entry with `action = "none"`, so users who compare generated code see it coming. A crash
fix gets a `crash-fix` entry with `action = "none"`. Deprecations, removals the deprecation registry schedules,
experimental features and new dated presets get their entries from their registries; write nothing for them, or an entry
with the same id (`deprecation:<id>`, `removal:<id>`, `experimental:<id>`, `preset:<date>`) to add a better title or a
`supersedes`.

```toml
[[change]]
id = "specialized-enum-default"
category = "decided-change"
decision = ["#2500"]
kind = "default-output"
action = "keep"
title = "String and integer enums become `StrEnum` / `IntEnum`"
summary = "Enums of strings or integers subclass `StrEnum` or `IntEnum` instead of `Enum`."
affects = { input_file_types = ["openapi", "jsonschema"] }
before = "class Status(Enum):"
after = "class Status(StrEnum):"
keep = { flags = ["--no-use-specialized-enum"] }
refs = ["#2512"]
source = "release-note"
```

- `category` (every unreleased entry): why the stored output changed, which decides what the entry holds
  (`scripts/_change_records.py`, `RULES`). `new-surface` (output only an option, option value, dated preset or public
  name the latest release lacks reaches; `surface` names them), `experimental` (a released experimental feature;
  `affects.experimental` names it, and `decision` the owner's decision unless it is the generated clients or servers),
  `crash-fix` (generation, import or decoding failed before, or for an added stored output the previous package fails to
  generate it or writes a unit `scripts/_behaviour_classify.py` calls unusable; `action = "none"`), `output-text` (the
  modules' syntax trees are equal apart from docstrings, comments and the order of imports, or their signatures are
  equal and no changed node is in a function body, a decorator or a configuration key the signature does not list),
  `default-fix` (only invalid input changes outcome) and `decided-change` (any other behaviour change of the default or
  a released option's output, with a `keep` table), both with the owner's `decision`, `notice` (warnings and error
  messages), `api` (a public CLI or Python API change; `decision` unless the deprecation registry schedules it), and
  `docs-text`, `internal` and `harness` (listing text, traces of internals, a changed test, input or repository script
  whose package output is the same), which have no guide entry and hold only `title`, `summary` and `refs`. An entry
  with `extends = "<id>"` adds more stored outputs to an unreleased record and holds nothing else. Entries of released
  changes may lack a category. An entry that only adds text to a derived entry (below) has none.
- `kind`: `default-output`, `output-text` (the text changes, the models behave the same), `removal`, `cli`,
  `python-api`, `template`, `runtime`, `warning`, `error`, `experimental` or `preset`.
- `action`: `required` (users must change something; give `migrate`), `keep` (the output changes and `keep.flags`
  restore it, or `keep.note` says how outside the command line), `review` (the output changes and nothing restores
  it; `keep.note` may name the nearest tool), `warn` (a new warning) or `none`. A `warn` entry is listed under "New
  warnings" in the guide and "New Warnings" in the release notes; only the `deprecation:<id>` entries are listed as
  deprecations with their planned removal.
- `affects` narrows who meets the change: `output_model_types`, `input_file_types`, `options` (only users who pass
  them; their keep flags are listed apart), `python_api`, `templates` and `experimental` (feature ids).
- `supersedes` drops older entries from the path of a user who meets both; `reverts` drops a change and the entry
  that undoes it.
- `keep.flags` must be options of the current release: the build parses them and writes their `pyproject.toml` form.

`complete_from` in `docs/data/migration/releases.toml` names the oldest release whose users meet every change in the
steps. The hub, the range pages, the per-release Markdown and the JSON mark the steps from an older release as
incomplete and point to the changelog; move it back once the entries of the releases before it are written.

Two rules are checked. An accepted default-output change in `scripts/behaviour_diff_allowlist.toml` names its entry
in `migration`, and that entry must be unreleased. `docs/data/migration/surface.json` holds the options, option values,
public names, `GenerateConfig` fields and builtin templates of the latest release; one that your change removes must
be named in the `affects` of an unreleased entry (an option or value as `--name` or `--name value`, a field as
`GenerateConfig.<field>`, a template by its path under the template directory), unless the deprecation registry
schedules its removal. New options and option values get their entries from the same comparison.

An entry with `source = "run"` carries a minimal fixture, `[change.verify]` with a `schema` and the `args` of every
run, and is proven by runs. `python scripts/build_migration_docs.py --record <id>` generates the fixture with the
release before the entry's and with the entry's release (or this checkout for an unreleased entry), each installed
into the cache of `scripts/compare_release.py` unless `--release-python VERSION=PYTHON` names an interpreter that has
it. It checks that their models behave differently, that `before` and `after` are in their outputs and that
`keep.flags` give this checkout the previous release's behaviour, and keeps the previous release's output in
`docs/data/migration/recorded.json`; never edit that file by hand. `--verify` checks the keep claims of every such
entry against this checkout and the recorded outputs, also with all keep flags of the steps from that release
together, and `--verify --text` also checks the `before` and `after` lines. `--check` fails while an entry's fixture
has no recorded output.

Run `python scripts/build_migration_docs.py` to rebuild the committed hub `docs/migration/index.md` and, locally, the
files the docs deploy builds and the repository does not commit (`docs/migration/changes.md`,
`docs/data/migration.json`), so a change fragment conflicts with no other; `--check` fails on a stale hub and on invalid
entries. `--release-notes unreleased` prints the release-note sections of the next release, and
`--range-pages docs/migration` writes the page of each range of releases locally, as the docs deploy does.

## Declared changes

Every change of stored expected output has a change record: an entry of the upgrade guide (above), or a record of a
category without a guide entry, in `docs/data/migration/unreleased/<id>.toml`. Its `covers` lists the labels of the
stored outputs it moves; `python scripts/declared_changes.py declare` writes them from the diff against the merge
base with `origin/main`, never write them by hand.

```bash
python scripts/declared_changes.py status
python scripts/declared_changes.py declare my-change --category output-text --title "..." --refs "#123" --rest
python scripts/declared_changes.py prune
python scripts/declared_changes.py check --base origin/main --report-only
```

The unit is a reference, one line of a `.refs` file: a change of its stored content, its environment predicate or its
`?` flag needs a record, so does a removed reference, and so does an added reference when `src/` or `uv.lock`
changes. Only a change that touches neither has moves: a renamed test or file whose references keep their content
needs no record. Coverage is per label, so a label covers every test item that compares it. `declare` selects all of
them (`--rest`), those whose label matches (`--labels GLOB`) or those of matching test items (`--tests NODEID-GLOB`),
and adds them to the record, creating it from `--category`, `--title`, `--summary`, `--refs`, `--decision`,
`--surface` or `--extends` when it is new. A stack layer passes `--base <layer below>` to every command. A change
covers only the labels it adds to `covers`, and each must move in it or be a gap of its base (a record that only
backfills an older change); `prune` drops the others and those that no longer differ from the latest tag. A label a
change brings back to the latest tag needs no record, and a record that still covers it is stale. A failing check
prints one `declare` command per kind of stored output (model output, notices, listings, internals), with `--base`
when the base is not the merge base with `origin/main`, `--extends` for an output a lower layer's record covers, and
the id of the record the change adds when it has one. `new-surface` covers model output only where the latest release
has none, and a `harness` record of a change that touches `src/` is listed as needing the replay. The check also lists
the outputs that moved since the latest tag with no unreleased record, judged by the same rule for each change since
the tag as main takes them (an output a test-only change added needs none later either; one it renamed keeps the need
of the output it renamed, and `declare` takes its new label), and a tag that `releases.toml` does not list yet. A stack
layer's base counts as one change from its merge base with `origin/main`; the check needs the history since the tag
and stops on a shallow clone. It reports only, for now; `--report-only` keeps its exit status 0 once it fails CI.

## Review checklist

`python scripts/review_checklist.py --base origin/main` prints the review items your diff triggers, at most ten: the
rules of `AGENTS.md` and these pages that no check enforces, each with the lines that triggered it, the question a
reviewer asks and the pull requests where the rule was broken. The items are the rows of
`scripts/review_checklist.toml`; a row states its rule in words its file holds and names two pull requests, and it
leaves the table once a check enforces its rule. `--head <revision>` reviews a commit instead of the working tree, and
`--table <file>` tries a new row on past diffs before it enters.

## Architecture boundaries

Before adding a dependency between layers, check `docs/architecture.md` and run:

```bash
python scripts/check_architecture_boundaries.py
```

The guard rejects concrete output-backend imports and backend-name inspection in
parsers, concrete backend imports or `sys.modules` lookups from shared model
modules, private `parser._*` imports from shared code, parser/backend dependencies
from configuration, and local output-family mappings in `input_model.py`. Move
output behavior to a neutral capability on `DataModel` or `DataModelFieldBase`,
keep backend lifecycle and cache management with its backend or the model
composition root, and move reusable helpers to a neutral package module. Do not
add an allowlist entry for new code. Existing entries document compatibility debt,
have bounded occurrence counts, and fail when stale.

The guard reads names through `scripts/_source_model.py`, which does not say which
binding of a name a read reaches, so a name holds every binding of its scope and the
guard fails closed: a name bound both to a concrete backend (a module string,
`importlib`, `sys.modules`) and to something else is read as the backend wherever it
is read, and a name bound under `TYPE_CHECKING` and again at run time (an import and
a fallback `Any`) has no single type, so a `*Host` annotation that uses it reaches
no members. Rename the variable, or import the name once. A name another module of
the package re-exports (`DataModelType`, `import_module`) is read as what that module
imports.

In the parser concern modules (every module below a `parser/_*` module or
package, and `model/_field_imports.py`: the files where the `pyproject.toml`
per-file ignores turn off ruff's `SLF001`) the guard owns private access: a
private member is reached only through a method's receiver or a parameter typed
as a `*Host` Protocol (or `type[...]` of one) that declares it, which ty checks
against the parser passed in. A method's receiver is the first parameter, `self`
or `cls`, of a function defined directly in a class body that is not a
`staticmethod`, also inside the closures and lambdas nested in it; elsewhere
`self` and `cls` are ordinary parameters. Names follow Python's binding rules: a
nested function, lambda, class body or comprehension that binds the parameter's
name (by any binding form: assignment, `for`, `with`, `except`, `import`, `def`,
`class`, a `match` capture, a walrus target, a type parameter or `global`) hides
the parameter. Declare the member on the Host the function takes instead of
adding a `noqa` comment. The other private access there is counted in
`scripts/host_private_access_baseline.toml`, which only shrinks: route a new
access through a Host instead of regenerating the file. The private names the
Host Protocols declare are counted as `host-friend-names` by
`scripts/check_ratchets.py`. Runtime modules (`_runtime/`), which generated
packages copy, import only the standard library, the third-party packages
generated code depends on, and each other relatively.

The guard also rejects an import cycle of the package whose imports all run
when their modules are imported: at module or class level and outside
`if TYPE_CHECKING:`, under a version, platform or `ImportError` guard too.
`scripts/check_ratchets.py` counts the modules on the import cycles of the
package (`src`) and of `scripts/` as `import-cycle:<measure>@<area>` keys
(`scripts/_import_cycles.py`): `module-level` for those cycles, `lazy` for the
cycles of every import, function-local and `TYPE_CHECKING` ones included, and
`largest-lazy` for the largest of them. Instead of importing back, inside a
function or not, move what the modules share into a module that imports none
of them.

A key of `scripts/check_ratchets.py` rises only with an owner decision, through
an `[[approved]]` entry of `scripts/ratchet_approvals.toml`: the key, the count
it may reach (`head`), the pull request it is for (`pr`), the public references
of the decision (`decision = ["#1234"]`) and a reason. The checker reads the
table from the base revision, so the entry lands in its own pull request first,
and the approved pull request then needs a base that holds it (rebase it onto
`main`; a re-run alone keeps its old base). Only the CI runs of that pull
request, and the push of its squash commit to `main`, accept the rise; a local
run does not. An entry that its tree already reaches is stale and fails, so the
approved pull request removes its own entry.

The same script counts the sites of the source rules in
`scripts/check_source_rules.py`, the code shapes that reviews keep finding, as
`source-rule:<rule>` keys: a change may keep or lower a count, and an absolute
rule fails on any site and cannot be approved. The rules marked
`absolute=True` in `RULES` of that script are absolute (today `doc-citations`,
`unused-private-global`, `flaky-test-workarounds`, `dead-capability` and
`never-run`), and the summary of
`python scripts/check_source_rules.py` names the kind of each rule.
`python scripts/check_source_rules.py --rule <rule>` prints each site and how to
fix it. `lost-last-caller` compares the tree with the base and needs coverage
data to decide, so the ratchet prints its candidates without failing on them.
A test that needs something of its environment names a capability of
`tests/capabilities.py` (`@needs("symlinks")`) instead of writing a `skipif`:
the table states each capability as clauses over the environment facts of
`tests/units.py`, with its reason. `raw-skip` counts every other skip,
`dead-capability` fails on a capability that no lane of
`.github/workflows/test.yaml` has (`scripts/_ci_lanes.py` reads the facts of
each lane from the matrix, `tox.ini`, `pyproject.toml` and `uv.lock`), and
`never-run` fails on a test whose capabilities together exclude every lane.
`tests/test_checks_are_run.py` names every `scripts/check_*.py` and every source
rule that nothing runs on the repository tree: a workflow `run:` step or a hook
`entry` that executes it, a `commands` line of a tox environment a workflow
runs, a ratchet key, or a test that asserts the exit status of its `main` on
the tree, each with arguments that run it on the tree (read with the check's own
parser). A mention, such as a `paths:` filter or a hook `files:` pattern, is no
run, and neither is a lookup such as `check_ratchets.py --ruff-pin`.

Tests for the checker use source fixtures and expected reports under
`tests/data/architecture_boundaries/` and
`tests/data/expected/architecture_boundaries/`. Keep diagnostics specific enough
that a contributor or coding agent can identify the owning layer and the expected
remediation without reading the checker implementation.

## Decision homes

A decision that several parser passes or output models need has one home in
`docs/architecture.md` ("One home per decision"): a pure core and its adapters.
Build the facts in an adapter and call the core; for a decision without a home,
add the home in the same change instead of writing a second copy. A new `legacy-*`
row needs a row of the "Legacy rows" table in `docs/architecture.md` with what
deletes it (`fix`); `tests/test_legacy_rows.py` fails for a row on one side only.

## Parser generation state

Parser code must keep generated output, naming order, parse order, and
canonical model selection compatible with existing releases. `ModelResolver`
remains the only authority for names. Do not move name generation or parser
dispatch into the generation index.

Use the store's `GraphBuilder` (`generation_store.builder()`, `self._graph_builder` in
parser code) for parser-side mutations that affect generation facts; the same
methods on `GenerationStore` are deprecated:

- Register parsed models with `builder.register_model(model)`.
- Replace references with `builder.replace_data_type_ref(...)` or
  `builder.detach_data_type_ref(...)`.
- Replace field or nested data types with `replace_field_type(...)`,
  `replace_nested_data_type(...)`, or `set_nested_data_types(...)`.
- Replace fields or base classes with `set_fields(...)`,
  `append_field(...)`, `insert_field(...)`, or `set_base_classes(...)`.
- Rename generated models with `rename_model(...)`; move them with
  `update_model_reference(...)`.
- Report models whose fields, base classes, or data types changed without the
  store, for example through a model method, with `note_changed_models(...)`.
  A refresh records again only the field types and base lists the store knows
  have changed.

Parser code should not directly assign `data_type.reference`, `model.fields`,
`model.base_classes`, `model.reference.name`, or call reference child mutation
helpers. Read dependency information through `GenerationIndex` queries instead
of using `Reference.children` as a reverse index.

The local pre-commit hook `generation-store-usage` runs
`scripts/check_generation_store_usage.py`, which checks `parser/`, the
parser-facing hooks in `model/` and `types.py`, and caches kept in the
`__dict__` of data types, fields and models, against the attribute-to-fact
table in `scripts/fact_tables.py`. The hook runs when a
parser file changes; after editing `model/`, `types.py` or the table, run the
script yourself (the test suite runs it too).

Writes that bypassed the store when the checker learned them are listed in
`scripts/generation_store_allowlist.toml`, by path, function and target with a
count. The list only shrinks:

- A new write outside a store operation fails. Route it through a store
  operation instead of adding an entry.
- When you route a write, the entry no longer matches and the check fails
  until you remove it or lower its count. `python
  scripts/check_generation_store_usage.py --write-allowlist` does that for you;
  it refuses to add entries or raise counts.
- A refactor that moves a write to another function renames its entry by
  hand (path, function or target) without raising the total count.
- A new attribute on `DataType`, a field or a model needs a row in
  `ATTRIBUTE_FACTS`; a model method that parser code calls and that reaches a
  fact write needs an entry in `PARSER_HOOK_METHODS` of the checker, or in
  `CONSTRUCTION_METHODS` or `RENDER_ENTRY_POINTS` with a reason.

The runtime write guard (the `STORE_WRITES` debug check below) sees the same
writes while the generator runs, also where the scan cannot follow them. Every
test runs it, and a test fails when its generations write outside a store
operation at a place the allowlist does not list. A write that only the guard
sees is listed with a witness instead of a count: `target = "arguments"`, the
`datamodel-codegen` arguments of one run that makes the write.
`python scripts/check_generation_store_usage.py --witnesses` runs every witness
and reports the entries whose witness no longer makes their write; remove those.
Witness entries are never added for new writes either. When the scan learns to
find a write that a witness covers, `--write-allowlist` turns the witness into a
count entry; that move is the only one that may raise the counted total.

If a new mutation helper is needed, add the method to `SITE_EFFECTS` or
`NO_SITE_EFFECT` (which make up `GENERATION_STORE_MUTATION_METHODS`), name it in
the `store_ops` of the rows it writes, and update the checker tests so
contributors get an actionable message.

## Debug checks

Some internal invariants are checked only when a debug flag turns the check on, so that production runs do not pay
for them. Each area of checks has one environment variable, `DATAMODEL_CODE_GENERATOR_CHECK_<AREA>`:

| Value | Effect |
| --- | --- |
| unset, empty or `0` | off, as in production |
| `1` | raise at the first violation, with a message that starts with the variable |
| `report:<path>` | append every violation to `<path>` as one JSON line (`area`, `message` and the area's details) and go on |

Any other value fails the run. A parse reads every variable once, at its start, and its code reports a violation
through the mode of the area.

The areas (`Area` in `tests/checks/areas.py`) are checks of the test suite and ship nothing in the package: they wrap the internals that `tests/checks/seams.py` lists, read the variables when the pipeline of a parse
starts and do nothing outside a parse. `tests/checks/plugin.py` installs them in the test process and, through the
`sitecustomize` of `tests/checks/child` that it puts on the `PYTHONPATH`, in every Python a test starts that imports the
same package. `python -m tests.checks <datamodel-codegen args>` runs the command line with them outside pytest.

`tests/conftest.py` sets every area to `1` for the test suite with `os.environ.setdefault`, so a value you set first
wins: `0` runs the tests without that area and `report:<path>` collects the violations of a whole run. Under
`--codspeed` (the CodSpeed workflow and `tox -e perf`) it sets nothing, so benchmarks measure what production runs;
measure performance outside pytest with the variables unset as well.

`FACT_FINALITY` raises only for violations that `KNOWN_WRITES` in `tests/checks/finality.py` does not list; the listed ones are today's, each with the roadmap item that removes it and a witness, the
`datamodel-codegen` arguments of one run that makes it. `python scripts/check_fact_finality.py --witnesses` (and the
test suite) run the witnesses and fail for an entry whose witness no longer makes its violation: remove the entry. The
list only shrinks. A new pass is declared in `scripts/pass_decls.py` and gets an entry, by name, in the pipeline
tables of `Parser`; the check runs it inside the scope of that declaration (`tests/checks/parse.py:run_pass`), the same
script checks the declarations, `scripts/check_pass_pipeline.py` checks the tables and their order, and a test that fails with "... undeclared: ..."
made a write its pass does not declare.

`STORE_WRITES` is the exception: today's code still writes outside store operations at the places
`scripts/generation_store_allowlist.toml` lists, so `1` would stop every generation. Unless you set the variable,
`tests/conftest.py` (`StoreWritesCheck`) sets it to `report:<file>` during each test, with one file per test process,
and fails the test for a write of the package that the allowlist does not list.

| Area | Checks |
| --- | --- |
| `SCHEMA_LOCATIONS` | every model parsed from a JSON document has a schema location at the end of L1 (`tests/checks/schema_locations.py`, [Metadata Output](architecture.md#metadata-output)) |
| `MODULE_IMPORTS` | the imports of every module, and those all modules share, equal the replay of their import ledger when the module's import text is written, and each module writes the model names and binds the imports of its import plan (`tests/checks/module_imports.py`, [Model Processing Passes](architecture.md#model-processing-passes)) |
| `MODEL_GRAPH` | collapsing root models stops before an inlining that would make a data type contain itself, the generation store never meets two Reference objects that share a model key, a copy and its original, every model parsed from a JSON document has an owner or is a root at the end of L1, and the models the output writes are the store's emitted models (`tests/checks/model_graph.py`, [Model Processing Passes](architecture.md#model-processing-passes), L5 `collapse_root_models`; [Generation Store](architecture.md#generation-store)) |
| `SCHEMA_GRAPH` | no reader writes a schema object the schema graph validated once and shares (`tests/checks/schema_graph.py`, [Layers](architecture.md#layers), L0) |
| `TEMPLATE_ASSIGNMENTS` | every class-scope field line that a model's built-in template renders after B2, annotated or assigned, binds the field's name (`= value`) exactly where the model's row of `classify_assignment` decides that the class body binds the field, as the compiled renderer or Jinja writes it; not checked: renders before B2, models under a custom root template, models whose class brings its own assignment hooks (rule `hook`), fields the text writes no line for, and text the running Python cannot parse; the shapes of `LEGACY_ROWS` (`legacy-annotated-factory-binds`, `legacy-typed-dict-binds`, `legacy-enum-member-unbound`) differ today and are only recorded with a report file (`tests/checks/template_assignments.py`, [Model Processing Passes](architecture.md#model-processing-passes)) |
| `STORE_WRITES` | after L1, data types, fields and models change their facts only inside store operations ([Generation Store](architecture.md#generation-store)) |
| `RENDER_MEMOS` | every value a per-parse memo returns equals the value computed anew where it is read (`tests/checks/memos.py`, [Generation Store](architecture.md#generation-store)) |
| `FACT_FINALITY` | each pass changes only the facts its declaration in `scripts/pass_decls.py` lists, on the models its scope allows, before they are final ([Fact Finality](architecture.md#fact-finality)) |
| `FACT_FINALITY_SWEEP` | with `FACT_FINALITY` on, a global pass that transforms or repairs compares every model, not only those it touched; it reports nothing itself, so `1` and `report:<path>` both turn it on |
| `PASS_TRIGGERS` | a pass whose trigger is false, which its `PassSpec` skips, runs anyway and changes no fact, memo revision, import, parser attribute, run-state field and warns nothing (`tests/checks/finality.py:ParseChecks.idle_pass`, [Pass Declarations](architecture.md#pass-declarations)) |

A new area adds a member to `Area` in `tests/checks/areas.py` and its seams to `tests/checks/seams.py`, its variable
to `CHECK_AREA_ENVS` in `tests/conftest.py` and a row to this table, and keeps tests that run it on and off.
`test_check_seams` fails when a seam is not wrapped or a module of the package holds a wrapped function the table does
not list. That every `ConfigDict` key the generator can write has a row in `_requirements.py` depends only on the
installed Pydantic, so it is a test (`tests/main/test_pydantic_floor.py`), not an area. `FACT_FINALITY_SWEEP` and `PASS_TRIGGERS` are the exceptions: `tests/conftest.py`
sets them to `1` only on `SWEEP_PYTHON` (the newest Python of CI), so one lane runs the slower full comparison and the
passes whose trigger is false, while the others skip those passes as users do.

`DATAMODEL_CODE_GENERATOR_CHECK_BUILTIN_FORMATTER_PARITY=1` shares the prefix but is not an area: the test helpers in
`tests/main/_builtin_parity.py` read it on every call and then generate each output of the default formatters a
second time with the built-in formatter. The CI black-latest lane sets it; the test suite does not.

## Comparing output with a release

Before sending a change to parsing, naming or rendering, compare the output of your checkout with the latest
release over the test inputs and the option sets your change touches:

```bash
.venv/bin/python scripts/compare_release.py --base 0.85.0 \
  --types pydantic_v2.BaseModel,msgspec.Struct \
  --options 'default;--collapse-root-models --reuse-model' \
  --extra '--input-file-type openapi' --import-check --show-diff 30 \
  tests/data/openapi/*.yaml
```

The script installs the release once into a cached virtual environment with `uv`, next to the same versions of every
other package in your environment, and caches the release's outputs, so later runs only generate your side. A cached
output is reused while the input's directory, the local files it references through `$ref`, the files named by arguments
and the arguments stay the same; pass `--no-cache` to regenerate it. Old environments and outputs are not removed;
delete the cache directory (`~/.cache/datamodel-code-generator/compare-release` by default) to reclaim space. Every run
goes through warm worker processes that import the generator once and generate in a temporary working directory, so give
files in `--options` and `--extra` as absolute paths.

The script prints one line for each run that differs, fails on either side, or imports on one side only,
then a summary. It exits with 1 when any run differs, fails only on your side or imports only on the release
side, or when every run fails on both sides. Use `--base-python` to compare with another interpreter, such as a build of another branch, and
`--no-cache` when that build changes without a version change. The script needs a POSIX system.

`--base` also takes a git revision of this repository (`main`, `HEAD~1`, a commit): its `src/` is extracted once with
`git archive` and runs with your interpreter, so only what your commits changed shows up. Your side is this checkout's
`src/`. Both sides run in an environment built from scratch (your `PYTHONPATH` and `PYTHONWARNINGS` reach neither),
and a side whose package is imported from outside its tree or environment stops the run. To check that a refactoring
changes nothing at all, run `scripts/behaviour_diff.py gate <revision> --identity`: it compares each run's output,
warnings (category, message and the module warning filters match, not the line that raised them; deprecations
included), the exception classes the CLI module handled, messages (errors by class and message, without traceback
frames), exit status, the refusal of a single output file before a modular run, and the options and their values on
each side, and fails on any difference. A cell that fails alike on both sides is not compared where the timeout or
the memory cap stopped both or where every cell of its input fails on both sides; the run prints how many.

## Calibrating the option recommender

`scripts/recommender_calibrate.py` checks the option recommender's rules against the public schemas listed in
`scripts/recommender_corpus.toml`. Each entry pins a spec to a commit and a sha256, names its license and the schema
style it stands for, and is either a calibration or a holdout schema. Specs are downloaded into a cache at run time,
used only when the digest matches, and never committed.

```bash
.venv/bin/python scripts/recommender_calibrate.py --check-manifest
.venv/bin/python scripts/recommender_calibrate.py --out calibration-run --import-check --jobs 4
```

For each schema, a run asks the recommender for its recommendation and scores every configuration of the manifest's
decision grid. It writes `report.md` (regret against the best grid configuration, rules whose decision disagrees with
the grid, threshold and preset proposals, changes since `scripts/recommender_calibration.json`), `scores.json`, a
proposed `calibration.json` and, when a threshold change would agree better with the grid, `rules.diff`. The script
never edits the rules, the calibration file or the manifest: proposals go through a normal pull request. A spec whose
`$ref` leaves the document is rejected unless its entry sets `stub_external_refs`, so generation never reads other
files or the network. Generated code runs only with `--import-check`, in a temporary directory through an isolated
interpreter.

Runs use only the refs pinned in the manifest and never ask the network whether they are current. Add the opt-in
`--check-upstream` to an `--out` run to also ask each schema's source repository for its `HEAD` with `git ls-remote`
(this uses the network, but downloads no spec). `report.md` then gets a "Proposed rotation" section that lists the
schemas whose upstream head differs from the newest pinned ref. Rotating an entry pins that head, with its date and
sha256, as the newest version, and the version pinned before becomes the baseline. Like every proposal, a rotation
is made by hand in a pull request.

The grid scores only the decisions it lists (`[grid]` in the manifest, keyed by rule `decision`), and a rule is judged
by its own `when`: the order of rules within a decision is not modelled.

## Writing a recommender rule

Rules are data in `src/datamodel_code_generator/resources/recommender_rules.json`. The schema is measured in
`src/datamodel_code_generator/_recommend/_signals.py`, rules are loaded, validated and evaluated in `_rules.py`, and
the report is written by `_report.py`. This rule from the file (evidence shortened) turns inline enums into
`Literal` types:

```json
{
  "id": "enums.inline-value-sets-as-literal",
  "decision": "enum-shape",
  "when": {
    "all": [
      {"signal": "inline_enums", "op": ">=", "value": 5},
      {"ratio": ["inline_enums", "all_enums"], "op": ">=", "value": 0.5}
    ]
  },
  "set": {"enum_field_as_literal": "all"},
  "reason": "Most enums are inline value sets of one property (inline enums: {inline_enums} of {all_enums}). As Enum classes they add one class name each, the longest and most numbered names; Literal types keep the values without a class.",
  "evidence": ["GitHub REST API description: 1872 -> 1538 types, names over 40 characters 370 -> 227"]
}
```

### Rule fields

| Field | Required | Meaning |
|-------|----------|---------|
| `id` | Yes | `<group>.<name>` in lowercase letters, digits and hyphens. The report prints it after each option. |
| `decision` | Yes | The question the rule answers, such as `title-source`. Lowercase letters, digits and hyphens. |
| `applies_to` | No | Limits the rule to `input_file_types` and `output_model_types`; empty or missing means all. |
| `when` | Yes | The condition that fires the rule (see below). |
| `set` | No | Config fields (snake_case) and their values, spelled as in `pyproject.toml`. |
| `value_from` | No | A field computed by `pascal_case_input_stem`: a class name made from the input file name. |
| `reason` | Yes | Why the option helps this schema. `{name}` placeholders are filled from the schema's signals. |
| `caveats` | No | Texts printed as `caveat:` after the reason, with placeholders filled. |
| `evidence` | Yes | Measurements printed as `measured:`, as written (no placeholders). |
| `optional` | No | `validation` or `policy`: the rule's values are only listed in that section of the report. |

How rules are decided:

- Rules are evaluated in file order. Within one `decision`, the first rule that applies to the input and output
  model type, whose `when` matches, and that has its values wins; later rules of that decision are skipped. A
  `value_from` rule has no value when the input has no file name or a named schema already has that class name, so
  the next rule of its decision can fire. Put the specific rule of a decision before the general one.
- A field belongs to one decision. When candidates are compared, the trial generates the recommendation without
  each decision (candidate `recommended - <decision>`), so the options a decision sets are kept or left out together.
- A fired rule's values join the command when they differ from what the starting preset gives and the user did
  not set the field. Values the preset already gives are listed under "Start from"; a rule that only sets fields to
  `false` and that the preset already follows is listed under "Not recommended". When the user set a field to
  another value, the user's value is kept and the difference is listed under "Your configuration".
- An `optional` rule is listed under "Optional (validation; not in the command)" or "Optional (policy; not in the
  command)". Its values never join the command, the configuration, or the compared candidates.
- A value no CLI option can express (`false` for a field without a `--no-` option) makes the recommender start from
  the next family in `families` and add a note that says which value.

### Conditions

A condition is one of these objects, nested freely:

- `{"signal": "<name>", "op": "<op>", "value": <number>}` compares one signal with a number.
- `{"ratio": ["<numerator>", "<denominator>"], "op": "<op>", "value": <number>}` compares the ratio of two signals
  with a number. A zero denominator never matches.
- `{"all": [<condition>, ...]}`, `{"any": [<condition>, ...]}` and `{"not": <condition>}`.

`op` is one of `>=`, `>`, `<=`, `<`, `==` and `!=`. Signals are integer counts; a yes/no signal such as
`root_is_object` is `0` or `1`. The signal names are the `SignalName` literal in `_signals.py`, counted by
`measure_signals()`. To see a schema's signals, run:

```bash
datamodel-codegen --input schema.yaml --recommend-options quick --output-format json
```

The payload's `signals` are the counts conditions read; `signals` and `facts` (example texts such as
`inline_title_examples`, or `none` when empty) are the placeholders `reason` and `caveats` may use. Write a literal
brace as `{{` or `}}`. A new signal goes into `SignalName` and is counted in `measure_signals()`; it then appears in
every JSON report, so record the changed expected reports.

### Validation

- Unknown keys, an unknown signal name, a bad `id` or `decision`, or an unknown `op` fail when the rules load, so
  every recommender run and test fails.
- `set` values are validated through the same model as preset values, so a rule cannot name a field that does not
  exist or give it an invalid value. An `optional` rule's values are validated as generation options instead, so any
  generation option may be one.
- `test_recommender_rules_match_the_option_registry` in `tests/main/test_main_recommend_options.py` fails when a
  field a rule sets has no registry entry listing the rule or has no CLI option, when a field is decided by more than
  one decision, when a text uses a placeholder that is neither a signal nor a fact, when a rule text cites an issue or
  pull request number, or when no stored report names a rule (it has no fixture).

### What a new rule needs

1. Measured evidence on public schemas. Run [the calibration](#calibrating-the-option-recommender) (add the
   decision's values to `[grid]` in `scripts/recommender_corpus.toml` to score it), or compare the trial of
   `--recommend-options full` with and without the rule's options on the corpus schemas. Write each measurement in
   `evidence`: the schema, what changed, and the numbers. Users read every rule text in the report, so never cite
   issue or pull request numbers or list known bugs in it.
2. A test fixture: a small schema under `tests/data/recommend_options/` that fires the rule, added as a
   `pytest.param` to `test_recommend_options_for_schemas`. Run the test to record its expected report under
   `tests/data/expected/main/main_recommend_options/`, accept the changed reports of other fixtures with
   `--inline-snapshot=fix`, and check that each change is one the rule should make.
3. A registry entry: list the rule id in `options.<field>.rules` for every field it sets (see
   [Step 4](#step-4-register-the-option-in-the-recommender-required)).
4. A new `rules_revision`: the date of the change.

## ➕ Adding a New CLI Option

When adding a new CLI option to `datamodel-code-generator`, follow these steps:

### Step 1: Implement the option (Required)

Add a row for the option to `OPTIONS` in `src/datamodel_code_generator/_option_table.py`, in the help section it
belongs to; `arguments.py` adds every row to the argument parser:

```python
OPTIONS: Final[tuple[Option, ...]] = (
    # existing rows
    toggle(Section.MODEL, "--my-new-option", help="Description of what this option does"),
)
```

The constructor of a row is its form: `toggle` (a flag with a `--no-` form), `flag` (off unless given), `deprecated`
(a flag whose help is its message in the deprecation registry), `clear` (the `--no-` form of a list option) or `value`
(an option that takes a value, with the arguments `argparse` takes, such as `choices=_values(MyEnum)` or `type=int`).

The value of a row reaches the run through the config field its dest names (`my_new_option`): add the field to the
config models. A row marked `config=False` is the option of a command that no config carries, such as `--help`.
`test_option_table_matches_the_config_models` (`tests/cli_doc/test_cli_options_sync.py`) fails for a row without its
field and for a config field without a row; a field that no option sets is listed in `CONFIG_ONLY_FIELDS` there, with
the reason.

### Step 2: Add a test with documentation marker (Required)

Create a test that demonstrates the option and add the `@pytest.mark.cli_doc()` marker:

```python
@pytest.mark.cli_doc(
    options=["--my-new-option"],
    input_schema="jsonschema/example.json",  # Path relative to tests/data/
    cli_args=["--my-new-option"],
    golden_output="jsonschema/example_with_my_option.py",  # Expected output
)
def test_my_new_option(output_file: Path) -> None:
    """Short description of what the option does.

    This docstring becomes the documentation for the option.
    Explain when and why users would use this option.
    """
    run_main_and_assert(
        input_path=JSON_SCHEMA_DATA_PATH / "example.json",
        output_path=output_file,
        extra_args=["--my-new-option"],
        ...
    )
```

### Step 3: Categorize the option (Optional)

The CLI reference documents a new option in the category of its help section (`Section.MODEL` gives "Model
Customization"). `src/datamodel_code_generator/cli_options.py` derives the documentation rows (`CLI_OPTION_META`) from
the cells of the option's row in `_option_table.py`: a category, group or topic written after the section in the
place argument puts it in another category or in a focused documentation page (a topic only where it is not that of
the category), and the cells `implies`, `requires` and `conflicts` document its relations to other options:

```python
OPTIONS: Final[tuple[Option, ...]] = (
    # existing rows
    toggle((Section.MODEL, _C.TEMPLATE, _G.GENERATED_OUTPUT), "--my-new-option", help="..."),
    value(Section.MODEL, "--my-other-option", help="...", requires=_relations("--other-option", message="...")),
)
```

### Step 4: Register the option in the recommender (Required)

Every option needs a decision in the [option recommender](recommend-options.md). Add an entry for the config field
(the snake_case name, such as `my_new_option` for `--my-new-option`) to the `options` table of
`src/datamodel_code_generator/resources/recommender_rules.json`, in alphabetical order.

An option that a dated standard preset sets for every input, output model type and Python target needs no entry: the
recommendation starts from a preset, so the preset decides it. Add an entry only when a rule decides it or its reason
says more, such as the outputs the option applies to.

If a recommender rule decides the option, list the rule ids. Each rule must supply the field through `set` or
`value_from` (see [Writing a recommender rule](#writing-a-recommender-rule)):

```json
"my_new_option": {"rules": ["naming.my-rule"]}
```

Otherwise, record why the recommender leaves the option to the user, with one of the categories `io`, `target`,
`preset`, `style`, `runtime-behaviour`, `formatting`, `compat`, `debug`, `platform`, `command`, or `pending`:

```json
"my_new_option": {"not_recommended": "style", "reason": "A naming convention only the project can choose."}
```

Use `pending` only while a rule for the option is being measured: give the follow-up id in `follow_up` and the
release it must be decided by in `release`, such as `"release": "0.86.0"`. Once `CHANGELOG.md` lists that release,
the registry test fails until the entry gets a rule or a category.

`test_every_option_is_registered_with_the_recommender` in `tests/main/test_main_recommend_options.py` fails when a
config field or CLI option has neither an entry nor a dated preset that sets it (`Options missing from the recommender
registry: ...`) or an entry has no option. `test_recommender_rules_match_the_option_registry` fails when an entry names
a rule that does not set that field, when a rule sets a field whose entry does not list it or that has no CLI option, or
when a `pending` entry lacks `follow_up` and `release` or outlives its release (`Rule data problems: ...`). Both
failures show the entry format above.

### Step 5: Generate and verify documentation

```bash
# Regenerate CLI docs
$ pytest --collect-cli-docs -p no:xdist -q
$ python scripts/build_cli_docs.py

# Verify generated docs are correct
$ tox run -e docs-check-all -- --check

# If you modified config.py, regenerate config TypedDicts
$ tox run -e config-types
```

### 🔧 Troubleshooting

If the `tox run -e docs-check-all -- --check` CLI docs step fails:

- **"No test found documenting option --xxx"**: Add `@pytest.mark.cli_doc(options=["--xxx"], ...)` to a test
- **"File not found: ..."**: Check that `input_schema` and `golden_output` paths are correct
- **"CLI docs are OUT OF DATE"**: Run `python scripts/build_cli_docs.py` to regenerate

| `input_schema` | Yes | Input schema path (relative to `tests/data/`) |
| `cli_args` | Yes | CLI arguments used in the test |
| `golden_output` | Yes* | Expected output file path |
| `model_outputs` | No | Dict of model type → output file (for multi-model tabs) |
| `version_outputs` | No | Dict of Python version → output file |
| `comparison_output` | No | Baseline output without option (for before/after) |
| `primary` | No | Set `True` if this is the main example for the option |

*Either `golden_output` or `model_outputs` is required.

See existing tests in `tests/main/` for examples.
