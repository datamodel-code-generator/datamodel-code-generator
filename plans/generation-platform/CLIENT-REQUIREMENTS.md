# Production requirements for Python API clients

2026-09-19. These are **design and acceptance requirements** for dcg's new client, not a list of implemented features. They define supported workflows, wire semantics, ownership, and failures. The detailed contracts own concrete defaults and APIs; acceptance uses independent protocol and runtime expectations.

“Common requirement” means a requirement for offering a normal HTTP client for production use. “API-conditional” means a capability required by the applicable API, not something excluded from consideration. “External operations” means providing the information and interfaces required in generated output without making dcg operate the hosted service itself. An unsupported diagnostic alone does not count as implementing a required capability.

[CLIENT](DECISIONS-CLIENT.md), [RUNTIME](DECISIONS-RUNTIME.md), [PROTOCOLS](DECISIONS-PROTOCOLS.md), and [MODEL-CODECS](DECISIONS-MODEL-CODECS.md) are authoritative for concrete APIs and settings; [ENTRY](DECISIONS-ENTRY.md) owns generation. This table maps requirements to verification. It is not a menu from which to select these already agreed contracts later.

## 2. Retry as the state machine of one logical request

The following defaults are dcg design decisions. RFC 9110 conditions automatic replay of non-idempotent requests. Retry-After is a number of seconds or an HTTP date; waiting time and method safety are distinct information. [RFC 9110 §9.2.2/§10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html) (checked 2026-09-17).

1. Resolve the operation and effective request settings once. Own the logical request ID, optional idempotency key, overall deadline, and body-replay policy separately from each attempt's temporary request object.
2. Allow retry only when **repeating the operation is safe** and **the same body can be recreated**. Even a safe HTTP method cannot retry an unreplayable body. POST/PATCH requires an explicit API idempotency contract or reliable transport information proving the request was not applied. Creating a key header alone does not satisfy the latter condition.
3. Streams/files declare whether they are nonreplayable, seekable to their initial offset, or recreatable through a caller factory. Do not automatically buffer the entire body or spool implicitly to disk. The factory owns the identical-payload guarantee, and each attempt has explicit close ownership.
4. Retry candidates are classifiable transient transport failures and 408/429/500/502/503/504. Exact exception/cause/delivery classification is fixed in RUNTIME §5. API configuration may change candidates, but must not automatically add 409 or every 5xx response. Always apply the safety conditions above as well as the HTTP-status test. Do not retry caller ValueError, validation, decoding, cancellation, or authentication-configuration failures as transport errors.
5. max_retries defaults to 2, allowing at most 3 resource attempts including the initial attempt; 0 disables retries. It is configurable at both client and request level. Backoff/jitter/Retry-After/deadline/stream defaults, merging, and limits are fixed in RUNTIME §2/4/5 and are not independently redefined here. Tests control random/clock/sleeper. These values are unrelated to performance tolerances for existing D behavior.
6. When accepting a positive Retry-After, do not clamp it down to the backoff cap and resend early. If the wait exceeds the remaining deadline or explicit maximum wait, end the call and return the reason. Derive HTTP-date delays from the wall clock at receipt; waiting itself uses monotonic time. Define invalid-value, past-date, and custom retry-after-ms handling explicitly. Do not infer vendor-header semantics without configuration.
7. Close the preceding response before retrying. Do not require fully reading its error body; bound diagnostic retention. Apply deadline/cancellation to sleep as well.
8. Credential refresh must not create another unbounded resend loop. Record refresh counts, retry attempts, and overall deadline in one execution state. Do not silently replay a nonreplayable body after 401.
9. Separate retries before the first HTTP response from resumption after stream events have reached the caller. The latter requires an explicit resumption protocol. By default, return the midstream exception without hiding duplicate events or repeated execution.
10. Normally disable internal retries in HTTP transports the SDK creates, making SDK policy the sole retry owner. If an injected transport retries internally, declare its capabilities and ownership and provide a configuration that avoids stacking SDK retries on top. Do not guarantee “at most three” without knowing actual network send counts.

HTTPX2 transport-level retries cover connection errors/timeouts, not general HTTP-status retry behavior. [HTTPX2 transports](https://pydantic.dev/docs/httpx2/advanced/transports/) (checked 2026-09-17). This is not a reason to divide retry ownership across two layers.

## 3. Serialization and validation while preserving existing models

Do not embed SDK-specific base classes, Parsable, additional fields, NOT_GIVEN types, credentials, or caches into dcg models. Preserve existing model configuration, custom serializers, aliases, and field order. Client method omissions use a client-owned sentinel to distinguish unpassed arguments from explicit null. Typed models use their backend's supported presence/serialization APIs. Do not infer unavailable presence information from value equality alone.

Request/response use context and readOnly/writeOnly are needed in both type binding and wire codecs. When using request/response variants normally generated by D, bind to their actual symbols. Do not guess by appending Request/Response to type names or silently enable D's variant-generation settings for the client.

Tolerance of unknown enums/additional fields is bounded by existing model settings. Preserving a strict model can make a new enum value a validation error. Do not hide this limitation and claim every SDK is forward-compatible. The typed route returns a clear decode error; callers can access status/headers/body through an **explicitly selected raw route**. Even when callers want a type tolerant of unknown enums, the new client must not change model settings on its own.

A model_dump call alone cannot handle every parameter and body representation for date/Decimal/bytes, custom types, union branches, roots, containers, and primitives. Separate OpenAPI wire codecs from model validation/serialization. Maintain presence and any required envelopes outside models for all five backends. MODEL-CODECS fixes static native/envelope selection and failure rules. [OAS 3.1.1 serialization rules](https://spec.openapis.org/oas/v3.1.1.html) (checked 2026-09-17).

## 4. Runtime, configuration, and additional metadata

The initial implementation combines HTTPX2 native sync/async with all five dcg model backends: Pydantic v2 BaseModel/dataclass, standard dataclass, TypedDict, and msgspec.Struct. All are supported from the first client release, with codecs owned outside models. Treat HTTPX and HTTPX2 types separately even where their API surfaces look similar. [HTTPX2 migration](https://pydantic.dev/docs/httpx2/get-started/migration/) (checked 2026-09-17). The four I/O timeout categories do not by themselves implement an SDK-call overall deadline. [Timeouts](https://pydantic.dev/docs/httpx2/advanced/timeouts/) (checked the same day).

Generated output bundles its required private runtime. D owns the runtime source and tests once, with shared sync/asyncio policy. Generated SDKs do not depend on the dcg generator package at runtime. Record runtime/generator versions and dependency ranges in generated metadata, and account for regeneration and SDK-release costs when fixes are needed. Do not initially publish a separate runtime package or maintain two distribution modes in parallel.

Resolve the dependency closure of runtime fragments at generation time. Do not import unused WebSocket/OAuth/Webhook helpers and dependencies into every SDK. Do not add client-runtime dependencies to model-only D installation or generation. Provide explicit contracts specific to the new client for injected transports/loggers/credential providers; do not build a generic public plugin registry initially.

Information absent from OAS for pagination, polling, idempotency, signatures, stream resumption, and similar capabilities belongs in versioned configuration specific to the new target. Reference operation/source locations and validate types, field/header existence, and conflicts at generation time. Explicitly map supported external extensions; do not assume unknown `x-*` entries have matching semantics. Do not change existing D configuration/preset/metadata formats or use automatic overlays to change D models.

The existence of newer versions such as OAS 3.2.1 is distinct from full support in the fixed D baseline. [OAS versions](https://spec.openapis.org/oas/) (checked 2026-09-17). Maintain a version/feature support table for new targets. New-target constraints must not make existing entry points reject input previously accepted by D.

## 5. Verifying completeness of the plan

For each capability, record where information originates, which layer owns it, when state/resources are created and released, expected wire behavior/exceptions, and the independent fixtures used to test it. Verify retry/auth/pagination/streaming combinations as well as isolated behavior. [ACCEPTANCE.md](ACCEPTANCE.md)

This ledger and the agreed contracts prevent omissions in known production capabilities; they do not declare implicit support for every API. Initial capabilities, applicability, diagnostics, and oracles are already selected. Separate passing implementation evidence is required. If binding to an existing model fails, do not bypass it with guessed type names, graph repair, or automatic configuration changes.
