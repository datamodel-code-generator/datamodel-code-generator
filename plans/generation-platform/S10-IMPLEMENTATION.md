## Deviations from the plan

- Background renewal (S10-4, user decision after review of #4236). The plan has the call that reaches a token's renewal point wait for the renewal. A token is now renewed a tenth of its lifetime, at most 30 s, before it expires (`refresh_margin`), and past that point an unforced caller is served the unexpired cached token without waiting while the renewal runs in the background. The renewal starts only when it can be admitted at once and the call can pay for it, and it is charged to that call; otherwise the caller is served and a later call renews. Forced refreshes, expired caches, and tokens without an expiry still wait. It applies to the client credentials and refresh token families (#4236, #4239), and an unexpired token keeps serving when its renewal fails or, for a rotated family, sends nothing.
- `retry_store(*, expected_revision=...)` (S10-4, user decision in #4243). The plan fixes `retry_store() -> TokenSet`, which stores the pending token set again with the same expected revision and says not to guess a new one. Since a conflict repeats until the expected revision changes, the keyword lets the application retry expecting another revision once it has checked what is stored, such as the conflict's `observed_revision`; omitted, the pending slot's revision is used as planned. A revision that is not an integer or None, or is negative, raises `AuthConfigurationError`, as does one at or above the pending token set's, which storing would roll back (`stale_revision`); a newer stored token set is adopted with `replace_token_set(..., persist=False)` instead. Concurrent retries share one store only when they expect the same revision.
- `invalid_client` on a refresh is `EXCHANGE_REJECTED` with `OAuthExchangeError` and spends the sent refresh token, as the plan's mapping says; a review question on it was answered without a change. A 401 counts as a rejection only for `invalid_client`.
- `replace_token_set(..., persist=False)` is refused with `AuthStateConflictError` while a store runs, including a store whose session ended before its callback returned (#4243), but allowed while a refresh whose session ended is still stuck in its token request, since it is the way out of the `UNCERTAIN` state that refresh left.
- Closing and deadlines of the providers (S10-4). The synchronous `request_close()` releases an idle provider on its worker, or on a daemon `oauth-release` thread when it never started one, so a closing client does not release on its own thread unless no thread can start (#4238); a busy provider releases on its own `oauth-release` thread once its running acquisition returns or its session ends. `exchange_needed` expires an overdue job before judging whether 401 recovery needs an acquisition (#4237). Async token responses check the session deadline at each chunk as the synchronous flow does, and the receipt time of a token response is taken before the response is closed (#4231).
- Open specification questions left for the plan owner: a refresh or a replacement can store a revision below the stored one a load or store confirmed, so revisions are not strictly monotonic against the store; and a synchronous `TokenStore.store` return value is not checked, so a synchronous wrapper around an async function would silently not store. The latter is not fixed because strict mypy refuses using the return value of a `-> None` Protocol method.
- `docs/python-client.md` states that Basic charset overrides, resource audience metadata, and generated OAuth provider factories are not available yet, so applications construct providers explicitly and `CredentialContext.audience` is `None` for generated calls, as the 2026-09-28 decisions defer them to S14-1 generation integration.

S10 resolves these S09 deferrals:

- `AttemptIOContext` carries the call's `deadline` and `cancel_token`, and `TimeoutOptions` replaces the fixed 5/30/30/5-second phase timeouts (S10-1).
- The native adapter declares `delivery_evidence=True` and reports trace evidence, and HTTPX2's `RemoteProtocolError` is classified by its provenance and the observed headers instead of phase `unknown` (S10-2).
- Hooks see `limiter_wait` and `limiter_acquired` (S10-1), `retry_scheduled`, `redirect`, and `retry_reason` (S10-2), and `auth_start`, `auth_end`, `auth_wait`, and the `auth_invalid_token` retry reason (S10-3, S10-4).
- A call makes several attempts: `BodyAttemptContext` carries real `attempt_index`, `hop_index`, and `remaining_timeout`, a call binds and encodes its body once, a field body included, and replays it from a `BodySource`, and a factory's `fingerprint` is checked (S10-2).
- Transport failures are `PhaseTimeoutError` or `DeadlineExceededError` where a limit fired (S10-1), `retry_stop_reason` is set when a retry is refused (S10-2), and security requirements are compiled, selected, and applied to headers, query, and cookies, which header and query patches can no longer override or remove (S10-3).

These remain: `parent_session_id` stays None and `call_start` has no origin until operation sessions arrive with the protocol helpers (S11), where the later events of a call carry its origin; `ProtocolDataError` has no `location` (S11), while #4223 added `OperationRef` and `ProtocolError`'s `helper_id` and `operation`; `AsyncRawResponse.stream_to` still writes with blocking calls on the event loop; and the CLI flags and generated SDK documents belong to S14.

## S10-1: deadlines, cancellation, and concurrency limits (#4224)

Runtime: `timing.py` defines `Deadline` (`after`, the monotonic `at`, `remaining()`) and the thread-safe, idempotent `CancelToken`; `logical.py` holds one call's identity, send admission counters, time limits, and the release of its asynchronous work. `ClientOptions`/`RequestOptions` gain `timeout` (`TimeoutOptions` merged per phase), `total_timeout` (60 s), `deadline`, `cancel_token`, `max_network_sends`, `stream_idle_timeout` (60 s), `stream_total_timeout`, and `limiter`; the earlier of the relative and absolute deadlines applies, a phase is clamped to the remaining budget, and a cap the deadline supplied raises `DeadlineExceededError` rather than `PhaseTimeoutError`, ties favoring the deadline. Sync deadlines are cooperative checks around callbacks, encoding, decoding, and each send and chunk boundary; async calls stop in the caller's task under the `asyncio.timeout`-style guard, and native cancellation always propagates unchanged, ahead of a token, client closing, the deadline, and the result. Streams switch to the idle and stream-total limits at handoff. `Limiter`/`AsyncLimiter` with `Permit`/`AsyncPermit` and `LimiterContext` are exported from `pkg.hooks`; a permit is held until the response is released and always released on failure, with `LimiterExecutionError` for acquire and release failures. The logical call fills the counter snapshots that `ResponseInfo`, terminal events, and every `SDKError` carry, even without a response. Work an interrupted async file body left settles on a retained task that the call and a later `aclose` wait for within `cleanup_timeout`.

Tests: the `deadline-options`, `deadline-cleanup`, `deadline-files`, `deadline-races`, `deadline-streams`, `limiters`, and `limiter-faults` scenarios, with an HTTP/2 fixture (`fixture_http2.py`).

## S10-2: retries and redirects (#4225)

Runtime: `retry.py` decides eligibility, server timing (`Retry-After` seconds or HTTP-date, a declared milliseconds header, a declared should-retry header), and saturated backoff with full jitter; `RetryOptions` defaults to 2 retries, 0.5–8 s, statuses 408/429/500/502/503/504, `max_retry_after` 60 s, and no pool-timeout retries. Retries need a candidate failure or status, operation safety (GET/HEAD/OPTIONS/PUT/DELETE, or `retry_safety="idempotent"`, or a valid idempotency contract; `never` forbids all), a replayable body, and time and send slots; a proven unsent native connection failure permits unsafe methods. `evidence.py` walks exception cause graphs within 16 levels and 64 nodes for the transient errno rule, and the native adapter records resource-header starts through the `trace` extension. `body_sources.py` binds a call's body once and opens an attempt per hop. `redirects.py` and `urls.py` implement `RedirectOptions` (disabled by default, five hops, same origin unless allowed, no HTTPS downgrade, 301/302/303/307/308 rules) with `RedirectPolicyError`, and `TransportOptions` configures the owned HTTPX2 client with `retry_owner`. The generator takes `RuntimeOperationMetadata.retry_safety`, `idempotency` (`IdempotencyMetadata`), `retry_after_ms_header`, and `should_retry_header`, from Python and TOML, and the runtime supplies `IdempotencyKey`. Raw requests and redirect origins parse an absolute URL once, about 17 µs less per raw call. The client e2e jobs run from Python 3.11.

Tests: the `retries` case and the `retry-errors`, `retry-calls`, `retry-boundaries`, `retry-ownership`, `retry-options`, `retry-policy`, `redirects`, `redirect-head`, `native-wire`, `native-faults`, `body-replay`, `body-replay-faults`, and `multipart-replay` scenarios.

## S10-3: client authentication (#4230)

Generator: `_client/security.py` compiles effective security from the observed document, root requirements and operation overrides, into the generated `SecurityBinding` records; `RuntimeOperationMetadata.auth_challenge_less_401` declares an API's challenge-free 401 and permits token-expired recovery under the retry policy. Runtime: `auth.py` exports `AuthConfig` (credentials, `selection`, `allowed_origins`, anonymous opt-in, signers, `max_token_exchanges`), `ApiKeyCredential`, `BasicCredential`, `BearerCredential` with `AccessToken` and `TokenVersion`, static and environment providers in both modes, the provider and signer Protocols, and `OwnedCredentialProvider`; `auth_policy.py` selects the first available alternative, validates callback results, and owns the managed header, query, and cookie fields of each hop; `auth_challenges.py` parses Bearer challenges; `scopes.py` canonicalizes requested scopes and token grant metadata. The resource server authorizes scopes; a 403 never expands scopes or triggers refresh. Credentials are sent only to allowed origins and rebuilt for each hop, one 401 recovery invalidates the exact used version under the retry gates, signers run in order over the finalized request with an optional SHA-256 body digest (`BodyFactory(..., sha256=...)`), and auth errors after a send carry the call's delivery state.

Tests: the `auth` cases and the `auth-errors`, `auth-values`, `auth-challenges`, `auth-flows`, `auth-options`, `body-digest`, and `native-signing` scenarios.

## S10-4: OAuth grants and concurrent refresh (#4231–#4243)

- #4231: `oauth.py` sends one token request through a provider-owned transport that verifies TLS and never redirects or retries, and classifies the answer; `grants.py` adds `TokenSet`, `OAuthProviderOptions` (30 s `refresh_timeout`, 5/15/15/5 s phases), and `AuthorizationCodeFlow`/`AsyncAuthorizationCodeFlow` with PKCE S256, single-use requests, and `AuthStateUncertainError` when issued tokens may not have arrived intact.
- #4232: `DeviceAuthorizationFlow`/`AsyncDeviceAuthorizationFlow`, one transaction per flow, bounded by the response's `expires_in` and a `SessionOptions` whose `max_network_sends` defaults to 128.
- #4236: `refresh.py`'s shared acquisition, one job per family on the provider's worker or task under its own deadline, bounded by `max_concurrent_refreshes`, `max_pending_refreshes`, and `max_waiters`; `ClientCredentialsProvider`/`AsyncClientCredentialsProvider`, `refresh_snapshot` and `RefreshInfo`, and background renewal.
- #4237: `admission.py` charges an acquisition to the call that starts it, or to the oldest waiting call when a queued one starts, against `max_token_exchanges` and `max_network_sends`, with `auth_wait`, `AuthBudgetExceededError`, and `auth_exchange_budget_exhausted`.
- #4238: a client that owns a provider releases it within its `cleanup_timeout`, through the synchronous `request_close()` Future or the async `aclose`, and otherwise raises `CleanupError` with `pending_providers`.
- #4239: `rotation.py`'s `RefreshTokenProvider`/`AsyncRefreshTokenProvider`: revisions, rotation, spent refresh tokens, stopped states, and `replace_token_set`.
- #4240: the `TokenLoad`, `TokenStore`, and async Protocols, `TokenPersistenceContext` with its `cache_key`, and `AuthTokenLoadError`, `AuthTokenStoreError`, and `AuthTokenStoreConflictError`.
- #4241: the first call loads once in a provider-owned session, `LOAD_FAILED`, and `reload_token_set`.
- #4242: each refresh reads the persisted token set before its request, and reads again after `invalid_grant`.
- #4243: a refreshed or replaced token set is stored before it becomes current, `PERSIST_PENDING`, and `retry_store`.

Tests: the `oauth-code`, `oauth-device`, `oauth-client-credentials`, `oauth-shared`, `oauth-accounting`, `oauth-closing`, `oauth-refresh`, `oauth-refresh-load`, and `oauth-refresh-store` scenarios over the local HTTPS server, synchronously and with asyncio.
