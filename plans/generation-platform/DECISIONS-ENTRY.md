# Final contract for generation entry points, configuration, distribution, and publication

2026-09-18. These are design decisions for implementation, not a report of published APIs or completed implementation. Internal restructuring and optional new APIs/options must preserve existing behavior and compatibility. The new FastAPI generator supports two backends from its first release: Pydantic v2 BaseModel and Pydantic v2 dataclass. The new client supports all five dcg model backends from its first release. Existing D model-only generation continues to support all five backends unchanged.

## 1. Ownership and placement

The new generators belong to the same repository, `datamodel-code-generator` distribution, version, and release as D. The old F repository/package/CLI remains independent; its docs/help identify it as deprecated and guide migration to the new D. Do not create a launcher for F, a D-to-F dependency, discovery of another environment, or a separate runtime distribution.

|Location|Owns|
|---|---|
|Existing `datamodel_code_generator.__main__` / `arguments`|Mutually exclusive server/client selection added to the existing CLI, and invocation of the CLI adapter only when selected|
|`datamodel_code_generator.fastapi`|New public Python server entry points, FastAPIConfig, server generation, templates/contexts/hooks|
|`datamodel_code_generator.client`|New public Python client entry points, ClientGenerationConfig, resource/method/SDK package generation|
|`datamodel_code_generator.api_types`|Shared records/errors/selection for the new entry points. Does not expose the generator's internal parser graph|
|`datamodel_code_generator._api_generation`|Execution management for one target, shared diagnostics, artifacts/ownership manifests, and publication. Does not contain parser-private graph operations|
|Explicit connection points inside the parser/store|Accepted attempts, operation facts, and final type mapping, as specified by BINDING|
|D-owned runtime sources/templates and tests|Codecs outside models, client policies/protocols, and server integration. Emit only the required dependency closure into the selected package's private runtime|

One execution generates either a server or a client. Do not introduce a CLI dedicated to simultaneous generation, independent new server/client CLIs, a main for each new module, public `.api` generate_api/render_api entry points, a targets array, or a retire API/CLI. Retain publication transactions spanning multiple models/files, because generating even one target requires them.

Preserve the existing top-level `__all__`, `generate()`, console name `datamodel-codegen`, meanings/defaults of existing options, and preset/metadata formats. The new explicit model scope value `api` is a specialized model-generation setting defined by BINDING; it does not select server/client generation. The generation selectors in §3 must not add or change scopes. Do not remove old members/options; record new options/help output as additive differences against a separate baseline. Add dependency rules for the new layers to the architecture checker, without adding exceptions for parser-private imports or external graph mutation. Reverse dependencies from D core/model/parser to FastAPI/client/HTTP runtimes are prohibited.

## 2. Public entry points and return values

Only the following new Python APIs are specified. `input_` accepts a file Path, schema text as str, an HTTP(S) URL as `urllib.parse.ParseResult`, or a Mapping, without modifying the input object. Do not infer a filename or URL from str. The new target entry points accept single-root OpenAPI; directories/lists produce E_INPUT_ROOT in the order defined in §2.1. Do not limit the number of externally referenced documents; distinguish them from root-operation identity. Do not restrict ordinary D directory/multiple-file/other-schema support. These target-entry restrictions also do not apply to model-only generation with an explicit api scope.

```python
# datamodel_code_generator.fastapi
generate_fastapi(input_, *, model_config: GenerateConfig,
                config: FastAPIConfig) -> GenerationReport
render_fastapi(input_, *, model_config: GenerateConfig,
              config: FastAPIConfig) -> GeneratedProject

# datamodel_code_generator.client
generate_client(input_, *, model_config: GenerateConfig,
                config: ClientGenerationConfig) -> GenerationReport
render_client(input_, *, model_config: GenerateConfig,
              config: ClientGenerationConfig) -> GeneratedProject
```

The common fields of the new configs require `output: Path` (the target's logical output root), `package: str` (the target's Python import prefix), and `model_package: str` (the D models' import prefix), with `model_mode: Literal['generate','verify']='generate'`. The new target entry points also require `model_config.output: Path`. Do not infer model locations/import prefixes, or change existing D entry points/return values for `output=None`, stdout, or dynamic models.

[MODEL-CODECS §12](DECISIONS-MODEL-CODECS.md) is authoritative for the additional settings on both targets: `builtin_codec_compatibility: tuple[BuiltinCodecCompatibility,...]=()` and `export_bindings: tuple[ModelExportBinding,...]=()`. Do not add fields to the existing GenerateConfig. In flat CLI target TOML, use `[[builtin_codec_compatibility]]` / `[[export_bindings]]`. The generator computes artifact digests and final module/field identities from accepted artifacts. Conflicting declarations fail before publication; registration order must not give the first declaration precedence. These registrations, including custom templates/bases/codecs/parameter adapters, must not expand the set of permitted server backends.

Standalone generate/render calls use the same single-target coordinator. Generate models once with the shared model_config, and render the selected target from the same accepted attempt and completed artifacts. Do not create separate server/client parse/retry drivers, automatically convert to another configuration, or generate models twice. Public report.target is fastapi or client; there is no third generation target named api.

Put shared public records/errors/selection in `datamodel_code_generator.api_types`; `.fastapi` / `.client` re-export the same objects. This covers GenerationReport, GeneratedProject, GeneratedArtifact, ArtifactRecord, Diagnostic, APIGenerationError, PublicationRollbackError, OperationRef, OperationSelection, and the MODEL-CODECS generator registration records/SchemaRef/SchemaDirectionalUse/capability values/BuiltinCodecCompatibility/ModelExportBinding. Emit generated-runtime views/Protocols into the generated package.model_codecs with the same schema version; they must not import the generator package at runtime. Do not re-export them from the existing top-level module.

OperationRef is keyword-only: `OperationRef(pointer: str, document: str | None = None)`. A plain RFC6901 pointer is equivalent shorthand. An omitted/None document denotes the root input use site: `urn:dcg:root` for Mapping/raw text, the canonical file URI for Path, and the existing loader's canonical root URL for URL. Do not mix an input digest into OperationId. A root-operation selector identifies the root path/method use site, not the declaration URI of an external PathItem. Keep the declaration address separately in the binding. An explicit document that does not match the root identity produces E_OPERATION_REF.

Keep the target's Python package root separate from the models' output/package root; reject overlapping owned paths and parent/child containment. The layout in §6 permits disjoint target-package and model locations within a standalone distribution root. The whole distribution root does not grant the target recursive deletion authority. Do not discover, import, or update another server/client. Share generator-side sources/tests and type/semantic contracts, while emitting the generated runtime into the selected target's private package.

`generate_*` publishes only after staging and all validation succeed. `render_*` returns all artifact bytes after the same staging/formatter/binding validation. Render does not write models, targets, lockfiles, or metadata to publication destinations. Input/reference reads, explicit caches, private temporary directories, and formatter costs may still occur. Return remote-lock updates as unpublished artifacts as well, leaving the existing lockfile unchanged.

GenerationReport is frozen and has `target, schema_version=1, written_files, unchanged_files, deleted_files, diagnostics, generator_version, runtime_revision`. File records contain logical Path/kind/sha256/size/target_id, without content/live parsers/staging paths/credentials. GeneratedProject has the same provenance and `artifacts: tuple[GeneratedArtifact,...]`; each artifact contains logical Path/kind/write-delete-unchanged/bytes (None for delete)/sha256/target_id. target_id is str or None: None for models/metadata/remote locks and shared diagnostics, and the §4.1 id for target-specific files/manifests/inventories. Artifacts are in publication order; diagnostics are ordered by phase → shared/target → operation → field. Do not duplicate all bytes into a generate report.

Configuration/binding/target contract violations retain ordered diagnostics in APIGenerationError. Re-raise existing D input/parse/formatter exceptions with their types and causes preserved, adding the stage to the new entry point's diagnostic record. Cleanup must not replace the original exception. Resource-release failures become suppressed issues where reporting is possible; inability to roll back uses the dedicated exception in §5.

|---|---|---|---|
|`PydanticV2BaseModel` / `pydantic_v2.BaseModel`|Supported|Supported|Unchanged|
|`PydanticV2Dataclass` / `pydantic_v2.dataclass`|Supported|Supported|Unchanged|

Validation order is: call-signature/constructor or CLI syntax errors; existing model-configuration validation; basic selected-target configuration validation; shared facade preparation in §5.2 (warning → preset → missing sentinel → metadata Path validation); backend validation against the table above; and single-root input-shape validation. Existing model-configuration failures preserve the original type/cause and E_MODEL_CONFIG; do not rewrap them as backend or E_INPUT_ROOT failures. Do not bypass normal validation of unknown DataModelType values. Original GenerateConfig validation in Python and existing argparse choices/Config handling in the CLI run first.

A server selecting a valid but unsupported enum retains exactly one shared diagnostic in APIGenerationError: `code='E_FASTAPI_BACKEND_UNSUPPORTED', severity='error', stage='config', option_path='model_config.output_model_type', target_id=None`. source_uri/source_pointer/operation/artifact_path are None; message identifies the actual enum value and both permitted values. The CLI uses the same code and existing Exit.ERROR=2. Do not remove the three valid values from argparse choices and turn them into usage errors. Subsequent root validation returns one E_INPUT_ROOT in APIGenerationError for a directory/list. If both conditions hold, return only the backend diagnostic without adding a later root error. A client or permitted server proceeds to E_INPUT_ROOT validation. A directory Path in the CLI is also a semantic error and retains its code.

Complete both validations before acquiring the remote lock, staging, core preparation/parsing, reading the OpenAPI/reference bodies to generate from, or resolving target hook/adapter modules. This does not claim zero configuration-file/existing-config-associated JSON reads or zero facade metadata Path checks. Also defer reading the CLI stdin body until after these checks; do not read ahead and then re-enter another public generation entry point.

Use the same validation for generate/render, model_mode='generate'/'verify', and --check. Never omit it for primitive/container/root/alias-only schemas, zero model classes, empty artifacts under an explicit api scope, or zero selected operations. Verify does not import an existing package to infer its backend; after validating the specified config, it performs one candidate generation and compares actual model bytes. Do not convert an unsupported server to Pydantic or bypass validation with adapter/template/export registrations. Native/codec-adapter selection within the two permitted backends is a separate decision in [FASTAPI](DECISIONS-FASTAPI.md). Retain codec/binding/field facts for all five client backends.

Ordinary D CLI/Python generate calls with no generation selector must not gain these target checks, target imports/objects, target-configuration validation, or additional walks. Do not impose server restrictions on the existing model-only api scope either. The argparse Actions and selection dispatch added to the CLI are subject to §3 and existing performance gates; do not claim completely zero cold-path cost without measurement.

## 3. CLI and configuration formats

Add mutually exclusive `--generate-server fastapi` / `--generate-client httpx` to the existing `datamodel-codegen` and `python -m datamodel_code_generator`. The former has only the fastapi choice and the latter only httpx; without either, retain ordinary model-only generation. httpx is the public family name for client generation; its actual runtime is fixed to HTTPX2 in §6. Do not fall back to HTTPX or automatically convert to another transport. Existing `--http-backend` controls input/reference retrieval and is independent of generated-client selection.

Selection requires `--target-config PATH`; do not automatically discover or read a default file. `--target-output PATH` explicitly overrides output in the target config. `--diagnostics-json PATH` (`-` means stdout) is an additional option for new-target diagnostics only. Any of these three without a generation selector is usage error/2, never silently ignored. Both selectors, unknown choices, and a missing target-config are also usage error/2. Preserve existing early help/version exit without loading target config/runtime.

Existing `--output` remains the model output. Input, url, model backend/scope, Python version, model formatter/header, and similar settings remain owned exclusively by the existing CLI and `[tool.datamodel-codegen]`/profiles. Do not put models/options/input or an independent model-output in the target file. Explicitly select generation on the CLI; unselected target settings in an existing pyproject must not initiate generation.

The example generates one server with the existing model settings. If the schema/model settings lack a required type binding, diagnose the use and required explicit model settings; the generation selector must not automatically add a scope.

```sh
datamodel-codegen --input openapi.yaml --output src/example/models.py \
  --generate-server fastapi --target-config fastapi.toml \
  --target-output src/example/server
```

```toml
# fastapi.toml
schema_version = 1
package = "example.server"
model_package = "example.models"
```

Generate a client in a separate execution with `--generate-client httpx --target-config client.toml`, explicitly specifying package/output and other fields in client.toml. Flat TOML contains schema_version=1 and only fields of the selected config, such as output/package/model_package/model_mode. Multiple target sections, a targets array, and independent model settings produce E_CONFIG_UNKNOWN. The file's schema_version must be the integer 1, excluding bool; a missing/unknown version or type violation produces E_CONFIG_VALUE. The loader uses it to identify the file format and does not pass it to model settings. Preserve ClientGenerationConfig's existing public field schema_version: Literal[1]=1, which remains 1 after file validation. Do not add a same-named field to the server config; pass only the fields each constructor defines. Require output in either the file or --target-output, and package/model_package in the file; missing values produce E_CONFIG_VALUE. model_mode defaults to generate; explicitly select verify for shared models. Put formatters/hooks and similar settings in the same flat config, allowing arrays of tables such as `[[builtin_codec_compatibility]]`.

Target precedence is explicit --target-output > file value > documented default. CLI Paths are relative to the invocation CWD, Paths in a file to that file's parent, and relative Python API Paths to the invocation CWD. Do not conflate None with omission, invent null-substitute strings, or infer module/distribution names. The target loader explicitly diagnoses unknown fields/versions/types/combinations. Check diagnostic-output paths for collisions with input/config/model/target/metadata/lock paths as well, preventing diagnostic files from overwriting them.

## 4. Model generation/reuse and artifact ownership

Every model-module file referenced by a binding must match. If the selected target has an existing inventory, compare it including removed/added models. Do not convert valid candidate differences in generate mode into this error; --check treats them as difference=1 under §4.2.

When the explicitly selected new `api` scope contains only operations without bodies/schemas and the parser result itself is empty, this is a valid empty model-artifact sequence. Both ordinary D generation with the new scope and target generation handle this result under the same conditions. Do not create model-code files or empty packages/placeholders, or arbitrarily delete old model files. Even with zero model symbols, if a Result containing constants actually exists because of an explicit setting such as `openapi_include_info_version=True`, emit that Result in normal order. Preserve the `Models not found` exception, ordering, and output state for existing scopes. Do not normalize timestamps, headers, or newlines to declare a match. Verify mode compares against models generated the same way; for other conditions, users align input names, settings, and dependencies. Otherwise, return the actual diff.

The model-generation side owns models/model metadata/remote locks; the target owns routes/clients/private runtimes and similar files; users own their own modules, such as service implementations and custom code, outside target-owned paths. Targets have no create-only files: every planned path is target-owned, and the publisher never adopts an existing unmanaged path.

The model fingerprint is the SHA256 of canonical JSON containing `schema_version=1`, model_package, and the ordered sequence of relative artifact paths/kinds/byte hashes generated by ordinary D. ## 5. Staging and publication contract

Pinned D already has staging that preserves logical output, batch publication of models/metadata/remote locks, and backup/rollback: [generation transaction](https://github.com/datamodel-code-generator/datamodel-code-generator/blob/3452dfbb428c4384f40cb16faf61aadfda58a3a8/src/datamodel_code_generator/__init__.py#L1735), [publication journal](https://github.com/datamodel-code-generator/datamodel-code-generator/blob/3452dfbb428c4384f40cb16faf61aadfda58a3a8/src/datamodel_code_generator/_publication.py#L631). New targets share these ownership principles and low-level checked filesystem operations; do not create a separate unsafe writer for each target.

The new `TargetPublicationBatch` is an internal journal accepting WRITE / DELETE for multiple artifacts, including models, for one selected target. It does not represent a public targets array. Fix commit order to: (1) model code in ordinary emit order, (2) selected-target files in plan order, (3) explicit model metadata, (4) remote-lock artifact, (5) selected-target model inventory, and (6) target manifest last. In verify mode, do not plan model-code/metadata WRITEs. DELETE applies only to files that target previously owned and whose hashes are unchanged. Model-file deletion belongs to the model-side plan; a new target must not arbitrarily delete files that ordinary D would not delete. Rollback follows the exact reverse order of successful journal entries. Never make the manifest point to new state before generated files do.

Fix processing order as follows.

1. Finalize existing model settings, selected-target settings, and shared facade preparation in §2.1 order, then pass backend validation and E_INPUT_ROOT single-root validation. Afterwards, check path collisions among input/config/template/model/target/metadata/lock/manifest/diagnostic files. Also reject symlink/parent-directory replacement, distinct Paths to the same entity, and output collisions under case normalization. In standalone mode, use individual owned paths from §2/6; do not treat the distribution root containing a model as a collision merely because of containment. Do not move the existing facade-owned metadata-destination validation into this later phase.
2. Allocate private staging on the same filesystem as each destination; perform ordinary model emit while preserving existing logical output/CWD/formatter context. Even when model and target roots/filesystems differ, keep every individual rename within one filesystem.
3. After the same model core completes ordinary staged emit, only the new composition uses `ModelGenerationProduct` and `GeneratedTypeContractBatch`, constructed from the accepted batch/source lease/completed artifacts, to run `validate_artifact_bindings(product, staged_artifacts)` once against artifacts after existing final rendering/formatting. Do not verify through an additional model render/type_hint evaluation.
4. Complete all selected-target rendering, compile/configuration validation, ownership differences, and verify-mode byte comparison. Public outputs/lockfiles remain unchanged up to this point. Release the model graph/source lease after all required freezing is complete.
5. Immediately before publication, recheck ownership hashes/file identities/anchors and acquire shared resource locks for model output, the selected target root, and any remote lockfile being updated. Separate target generations use the same lock for shared models/remote locks. Acquire deduplicated locks in canonical-path order to prevent mutual waiting. Failure to acquire produces E_OUTPUT_BUSY; do not guess a waiting time and proceed. Inside the locks, recheck the starting snapshot, model/selected-target ownership hashes, and management-file same-identity preconditions. Do not check another target's manifest. Render/check does not acquire write locks; if snapshots differ between the start and end of reading, abort comparison with E_STATE_CHANGED.
6. WRITE secures a backup of an existing file before replacing it; DELETE first moves the file to backup. Journal each success. The new batch rolls back in reverse order for every failure, including Exception and interrupt/cancellation, not only OSError. Do not change failure semantics of the existing standalone D writer.
7. After all commits, mark the remote lock committed and release backups/staging/descriptors/locks. On failure, preserve the original exception; if rollback is impossible, return PublicationRollbackError with its cause, paths that could not be restored, and backup paths, leaving recoverable backups in place. Do not claim successful restoration.

### 5.1 Shared-lock implementation

Use standard-library nonblocking OS advisory locks only for new publication. On POSIX, use `fcntl.flock(fd, LOCK_EX | LOCK_NB)`; on Windows, lock the first byte with `msvcrt.locking(fd, LK_NBLCK, 1)`. For each canonical resource (model output, selected-target root, remote lockfile being updated), put a one-byte lockfile under the resolved resource's parent at `.dcg-api-state/locks/<SHA256 of the UTF-8 NFC-normalized and casefolded basename>.lock`. Do not acquire duplicate keys for the same resource. Do not place these files in the model-artifact tree; create them only under parents that pass symlink/identity checks. Also exclude same-resource concurrency within one process using a nonblocking thread lock for the same key. Acquire all keys in canonical-path order; on failure, release acquired locks in reverse order and return E_OUTPUT_BUSY. Do not wait/retry or infer stale PIDs.

Lockfiles are persistent coordination artifacts excluded from VCS; their existence is not a busy signal. This is not a PID-file liveness scheme. After the OS releases locks on process exit/SIGKILL, reuse the remaining file unchanged. Do not replace the lock inode through rename/unlink. Generated docs explain how to exclude the locks directory from VCS, without automatically editing an existing user .gitignore. Render/check does not create lockfiles. Explicitly document that the first generate lock acquisition may leave directories/files as coordination side effects, distinct from the guarantee that pre-publication failure leaves published models/targets/remote locks and similar artifacts unchanged.

The initial shared-exclusion guarantee applies only to participating new generators on a local filesystem on the same host. It does not guarantee distributed exclusion against writers on other hosts over NFS/SMB, cloud sync, or other tools ignoring locks. An unavailable OS lock API produces E_OUTPUT_LOCK_UNSUPPORTED with zero publication; do not fall back to unlocked operation. Independent-process oracles cover acquisition contention on Windows/local filesystems, reacquisition after process exit, two threads in one process, shared-model contention between two processes generating different targets separately, and reverse resource-request order. Do not replace old D PROCESS_STATE_LOCK or its existing writer with these new locks.

Do not promise that multi-file/multi-filesystem updates form an atomic snapshot that switches instantaneously for readers in other processes. Guarantees are no publication changes on pre-publication failure, rollback for detectable intermediate failures, and explicit reporting of rollback failure. Automatic recovery after power loss/SIGKILL/disk corruption is not guaranteed. Coordination with other tools concurrently modifying generated destinations is limited to precondition checks and the explicit lock scope. These are fixed guarantee boundaries, not undecided items.

Existing D calls retain their existing writer, return values, and exception semantics. Even when reorganizing shared filesystem helpers, preserve old-call ordering/modes/exception conditions. Do not add new-batch locks/journaling/ownership checks to model-only paths.
