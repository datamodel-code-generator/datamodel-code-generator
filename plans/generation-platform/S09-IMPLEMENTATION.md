## Scope and split

Generated calls have to run to be tested end to end, so S09-1 carries the HTTPX2 core they need: sync and asyncio clients over a borrowed or owned HTTPX2 client, `close`, `aclose` and context managers, `with_response`, the success body cap and the bounded error prefix.

PR-STACKS plans a second PR for HTTPX2 sync and asyncio, injection, ownership and close, and raw, file and multipart bodies. It is split so each part stays reviewable: S09-2 decodes response content codings in the SDK, which raw responses need; then come transport adapters and the client lifecycle (`ClientClosedError`, `with_options` views), raw and streaming responses, and file, stream and multipart bodies with wildcard request media and `RequestCodecs.part`. The third planned PR, the full option set, the remaining typed exceptions, hooks and `api-diff.json`, comes last.

## Deviations from the plan

- Until file and multipart bodies land, multipart request or response media, wildcard request media, and form encodings the URL-encoded writer does not read fail generation with the temporary `E_CLIENT_UNSUPPORTED`, so no operation is generated without a capability it needs. That PR removes the code.
- A media type name that is not a media type, such as `json`, fails with `E_METADATA_REQUIRED` instead of raising `ValueError`. The FastAPI planner still raises; that is left to a separate fix.
- A base URL carries no query, besides the userinfo and fragment the plan excludes: the operation path and query are appended to it, so a query would end up inside the path. One predicate, `options.is_base_url` in the runtime, decides for `ClientOptions`/`RequestOptions`, `default_base_url`, `server_base_url` and resolved servers, so generation and the runtime never disagree.
- A response whose body HTTPX2 already read, such as a `MockTransport` response built from content, arrives decoded: HTTPX2 removed its coding while reading it, so the SDK takes the decoded bytes instead of decoding twice. Every streamed response is decoded by the SDK (S09-2).
- `ProtocolError` has no `helper_id` or `operation`, and `ProtocolDataError` no `location`, until the protocol helpers define `OperationRef`, `Selector` and `RequestTarget` (S11).
- `ResponseInfo.elapsed` is measured when the response headers arrive, so streaming handles can carry it (S09-2).
- Embedded packages send no `User-Agent`, since they have no distribution; standalone distributions send `<distribution>/<version>`.
- Response headers without a schema have no decoder, so `decode_<method>_header` leaves them out.
- Until S10, every transport failure is a `TransportError` with its phase and delivery state, `retry_stop_reason` is always `None`, and security requirements are recorded in the contract digests but not applied.
- A `default` response contributes to the success union, since it may carry a 2xx status, as well as to the error payload.
- Unknown keys in nested TOML tables, such as a `resource_names` entry or an operation's `runtime`, are `E_CONFIG_VALUE` from the shared loader; unknown top-level keys are `E_CONFIG_UNKNOWN`.

## S09-1: resources, methods, and URL, parameter, request and response generation

Generator (`_client`):

- `config.py`: `ClientGenerationConfig` with `schema_version`, `transport` (`"httpx2"`), `resource_names` (`ResourceName` tag to dotted namespace), `operations` (`ClientOperationConfig`: `ref`, `resource`, `name`, `parameter_names`, `request_media_type`, `response_media_type`, `runtime` with `request_id_header` and `success_statuses`, `description`), `default_base_url`, `server_base_url` and `codec_adapters`, each checked as §§1 and 7.1 require, and the TOML converters of the shared loader.
- `naming.py`: the §3 rule. Text is NFKC-normalized and split at ASCII case boundaries; other code points become `u<hex>` tokens, a leading digit takes `n_`, and a keyword takes a trailing `_`. A method without `operationId` is its HTTP method, then the path's literal parts and `by_<parameter>` parts, or `root`. Reserved members, reserved arguments and Windows device names need explicit names.
- `plan.py`: resources from the first tag or the configured namespace (untagged operations share `default`), parent namespaces, method and argument names with every collision reported (`E_NAME_COLLISION`, `E_RESERVED_NAME`), parameters in §4 order, request media with the default media, responses classified as success or error with their media and headers, effective servers resolved to absolute templates against `server_base_url` or the source URI (`E_BASE_URL`), and operation references of the settings (`E_OPERATION_REF`, `E_CONFIG_CONFLICT`). All problems of a target are reported together.
- `render.py` and `templates/{client,resource,types}.jinja2`, compiled like the model and FastAPI templates: `__init__.py` with lazy `Client` and `AsyncClient`, `_client.py`, `_async_client.py`, the public `options`, `errors`, `responses`, `bodies` and `model_codecs` modules, `resources/<namespace>/{__init__,_sync,_async}.py` with cached child resources and `with_response` views, `types/<namespace>/{__init__,_operations}.py` with `<Pascal>Response`, `<Pascal>ErrorData`, `<Pascal>HTTPError`, `<Pascal>RequestCodecs` and `decode_<method>_header`, `_generated/model_bindings.py`, and `_operations.py` with one `OPERATION_<index>: Final[OperationPlan[<Pascal>Response, <Pascal>ErrorData]]` per operation. Signatures are keyword-only; optional arguments default to `UNSET`; outbound types are `T | ModelValue[T]` (native) or `T | DecodedValue[T]` (envelope). `Literal` overloads narrow the body by `media_type` and the result by `response_media_type`. Model types are imported under private `_dcg_type_<index>` aliases, only where a module spells them.
- `target.py`: `ClientTarget` for all five backends. It plans the wire and the codecs with `surface="client"`, renders the package, and records `ClientManifestData` v1: the namespace, and for each public operation its reference, resource, method, parameters, exports, and SHA-256 digests of its signature, request, response and security contracts. Dependencies are `httpx2>=2.13.0` and `typing-extensions>=4.16`, the codec validators when bindings exist, the backend's library, RE2 for patterns, and the libraries the models import.

Shared changes: `plan_wire` plans the fields of form bodies (`WirePlan.forms`) and owns `operation_uses`; `TypeSource` takes a leaf callback, so the manifest spells types by import location; `_target_render.py` holds what both targets render (runtime copies, `FieldPlan`/`ParameterPlan` literals, pattern and model dependencies), which the FastAPI target now uses too. Its runtime copy caches each module's relative imports and reads only the modules a package imports: the move first dropped the FastAPI renderer's cached graph and scanned the whole runtime, client runtime included, on every render.

Runtime (`_runtime/client`, copied into each package):

- `options.py`: `ServerSelection`, `ClientOptions` and `RequestOptions` with `server`, `base_url`, `max_response_bytes` and `max_error_body_bytes`, layered as RUNTIME §2 describes; `UNSET` inherits, and `server` and `base_url` in one layer conflict.
- `operations.py`: `OperationPlan`, parameter specs, request bodies of JSON, text, form and binary media, and `ResponseDecoder`: status by exact code, then range, then `default`; only 2xx (and configured `success_statuses`) succeed; `HEAD`, 204, 205 and 304 have no body; media by exact type, then without parameters, then `type/*`, then `*/*`.
- `client.py`: `ClientCore` and `AsyncClientCore` build one `httpx2.Request` per call (path, query, header and cookie parameters through the codecs, `Accept` from the success media, fixed timeouts), send it with redirects and HTTPX2 auth off, stream the body up to 16 MiB for a success and a 64 KiB prefix for an error, and decode it. The client's settings, its fixed headers and each server list's resolved URL are computed once per client.
- `errors.py`: `SDKError` with `reason_code`, `ConfigurationError`, `RequestEncodingError`, `TransportError`, `HTTPStatusError[E]`, `UnexpectedStatusError`, and the `ResponseDecodeError` family (`UnexpectedMediaTypeError`, `BodyProtocolError`, `DecodeError`, `ResponseValidationError`, `ResponseHeaderDecodeError`, `ResponseTooLargeError`), with `DeliveryState`, `IOPhase` and representations that name no header or body values.
- `responses.py` (`HeadersView`, `ResponseInfo`, `Response[T]`) and `codecs.py` (`RequestCodecs` and the response header decoders).

Tests:

- `test_client_generation.py` renders sixteen fixtures (pets, media, servers, default and implicit servers, names, querystring, empty selection, and every error family) and ten configurations, and compares each report and every generated module of each backend with the expected files.
- `test_client_runtime.py` generates the pets, media, querystring, servers and default-server packages for every backend and calls them through HTTPX2 mock transports, synchronously and with asyncio: every request line, header and body, each success, error payload, header decode, media mismatch, bodyless and oversized response, transport failure in each phase, option and server selection, and ownership. It runs in the new `client-e2e` environment (dependency group `client`), which collects coverage; the runtime reaches 100% there.
- `test_client_typing.py` checks the pets package of every backend and a positive sample clean under strict mypy 2.3.1, strict Pyright 1.1.414 and ty 0.0.84, and a negative sample with seven marked lines: mypy and ty report one error on each, and Pyright one on four and two (an argument and the failed overload) on the other three; the expected files list every diagnostic. It runs in `typing-nocov-e2e`, now "FastAPI server, client, and model codec typing e2e".

Benchmarks (macOS on arm64, Python 3.13, medians or best of repeated runs):

- Generation with the builtin formatter, 10/50/200 operations: models only 5.3/19.8/73.5 ms; FastAPI 46.3–47.9/182.0–186.8/730–739 ms before and 47.2–47.7/184.5–187.3/736–743 ms after the shared rendering, within noise once the runtime copy caches again (it cost 3 ms per render without); client 60–63/244–250/978–990 ms. For 200 operations the client writes 3.9 MiB (FastAPI 3.2 MiB), with a traced peak of 95 MiB against 63 MiB and a maximum RSS of 306 MiB against 229 MiB; formatting and compiling the larger sync, async and `with_response` modules is most of the difference.
- Calls through an HTTPX2 mock transport, best of 7 × 3000, µs: a GET with a path and a query parameter decoding one model takes 99–100 with Pydantic BaseModel (104.6 before caching the settings, server URL and response groups), 95.7–96.4 with dataclasses and 96.1–96.7 with msgspec; a POST with a JSON body 115.6–116.5; a bodyless DELETE 36.0–36.4; asyncio adds about 3. The handwritten HTTPX2 call with `model_validate_json` takes 34.4–35.2 (GET), 24.8–25.0 (POST) and 16.7–16.8 (DELETE). Under the profiler a GET spends about 45% in the model codecs (wire validation, freezing and projection), 35% in HTTPX2 and 13% in the client runtime.
- Imports: `import <package>` takes 1.9 ms and loads no HTTP runtime; `Client` 35 ms (HTTPX2 26.5 ms); the first resource 63–84 ms with its models. The first call takes about 400 ms, 345 ms of it importing jsonschema: `jsonschema[format-nongpl]` installs `rfc3987-syntax` for the `iri` formats, and it builds a Lark grammar at import (320 ms). FastAPI packages pay the same on their first request; the shared codec runtime is the place to address it.

## S09-2: response content codings

- `coding.py` reads the codings of every `Content-Encoding` header, comma lists and case-insensitive, drops `identity` and treats `x-gzip` as gzip. They are checked at the first body chunk, so a response without a body never fails on them: more than two layers are a `ProtocolSizeError(kind='content_layers')` and an unknown coding an `UnsupportedContentCodingError`. Each layer is removed incrementally with zlib, gzip with every member and deflate with zlib framing, at most 64 KiB per step, and its decoded bytes may not pass max(1 MiB, 100 × its encoded bytes), or `DecompressionLimitError` stops the read. Corrupt data, data after a deflate stream or garbage after a gzip member, and a coding without its end are `ProtocolDataError(condition='malformed')`.
- The client core reads `iter_raw` and `aiter_raw` and removes each coding exactly once; both body caps count decoded bytes. A coding failure on a success raises that error. On an error status the operation's `HTTPStatusError` keeps the prefix decoded so far with `truncated=True` and the failure as `error_decode_error`; on an undeclared status `UnexpectedStatusError` keeps it as its cause.
- `errors.py` gains `ProtocolError`, `ProtocolDataError`, `ProtocolSizeError`, `UnsupportedContentCodingError` and `DecompressionLimitError`. Their messages name only SDK-defined values; the coding a server sent stays in the `coding` field.

Tests: the `codings` runtime scenario decodes gzip, `X-Gzip`, deflate, a stacked `gzip, deflate` body, identity, a two-member gzip body and a 112 KiB list whose gzip body streams in 100-byte chunks; refuses three layers, `br`, a truncated and a corrupt gzip body, data after deflate and garbage after gzip, and a bomb of 2 MiB of zeros; keeps a gzip error payload, a truncated one as the decode error, a coded 302 as `UnexpectedStatusError`'s cause, and a bodyless 204 with an unknown coding; and repeats stacked, identity and truncated bodies with asyncio. The runtime stays at 100% coverage.

Benchmarks (best of 5 × 2000 calls, µs): a GET streaming one small item takes 88.7–92.0 before and 89.1–92.1 after as identity, 92.2–95.6 and 94.1–97.9 gzip-coded; a 30 KiB item takes about 5900 either way, all of it in the model codec.
