## Scope and split

Generated calls have to run to be tested end to end, so S09-1 carries the HTTPX2 core they need: sync and asyncio clients over a borrowed or owned HTTPX2 client, `close`, `aclose` and context managers, `with_response`, the success body cap and the bounded error prefix.

PR-STACKS plans a second PR for HTTPX2 sync and asyncio, injection, ownership and close, and raw, file and multipart bodies. It is split so each part stays reviewable: S09-2 decodes response content codings in the SDK, which raw responses need; S09-3 adds transport adapters, the client lifecycle and `with_options` views; then come raw and streaming responses, and file, stream and multipart bodies with wildcard request media and `RequestCodecs.part`. The third planned PR, the full option set, the remaining typed exceptions, hooks and `api-diff.json`, comes last.

## Deviations from the plan

- Until the rest of the media land, generation fails with the temporary `E_CLIENT_UNSUPPORTED` for multipart request media other than form-data, multipart responses with a schema other than form-data, a form-data schema that is no object, a style given to a form-data member holding files, a form-data object sent whole whose encoding requires a header, and a JSON or text media type no builtin writes, so no operation is generated without a capability it needs. The last of those PRs removes the code.
- A media type name that is not a media type, such as `json`, fails with `E_METADATA_REQUIRED` instead of raising `ValueError`. The FastAPI planner still raises; that is left to a separate fix.
- A base URL carries no query, besides the userinfo and fragment the plan excludes: the operation path and query are appended to it, so a query would end up inside the path. One predicate, `options.is_base_url` in the runtime, decides for `ClientOptions`/`RequestOptions`, `default_base_url`, `server_base_url` and resolved servers, so generation and the runtime never disagree.
- `ProtocolError` has no `helper_id` or `operation`, and `ProtocolDataError` no `location`, until the protocol helpers define `OperationRef`, `Selector` and `RequestTarget` (S11).
- `ResponseInfo.elapsed` is measured when the response headers arrive, so streaming handles can carry it (S09-2).
- `AttemptIOContext` has no `deadline` or `cancel_token` until S10 defines `Deadline` and `CancelToken`, and every attempt sees the fixed 5/30/30/5-second phase timeouts until `TimeoutOptions` exists. The native adapter reports no trace evidence and declares none (`delivery_evidence=False`); its failures carry the delivery state their HTTPX2 class implies (S09-3).
- A form-data file part is sent as `application/octet-stream` unless its FilePart or its encoding names a media type, even when its schema has a `contentMediaType`, and a read-only member keeps its part codec, which refuses any value in a request (S09-8).
- A media selector belongs to the request codecs instance that made it, which stands for the operation, its media plan, and its generation: a reloaded or regenerated package makes new instances, so its older selectors are refused as the plan's stale fingerprints are (S09-10).
- Header and query patches do not yet reserve the headers, query, and cookies that security schemes manage, since those are applied from S10 on (S09-17, S09-18).
- The client choices of CLIENT §9.3 are target-file and Python settings only: their `--client-*` options, among them `--client-request-validation` and `--client-response-validation`, help, and CLI reference come with `--generate-client` (S14-3), since S09 enables no public entry point. `docs/python-client.md` documents them from tested fixtures and stays out of the navigation until then. The template context views that expose them (`signature_style`, `ClientSignatureView.kind` and `unpack_type`) and the generated SDK documents that describe the selected profile come with templates and generated documents (S14-1) (S09-19).
- A server that closes a connection before a body ends raises HTTPX2's `RemoteProtocolError`, which the native adapter classifies with phase `unknown` until the retry classification of S10 assigns it (S09-23).
- Selecting Pydantic argument validation, as `arguments` or among `argument_overrides`, fails generation with the temporary `E_CLIENT_UNSUPPORTED` until the next PR implements it; `ValidationOptions.arguments` accepts only `none` meanwhile, as no package allows another mode (S09-25).
- Hooks see the events of one attempt until S10 adds authentication, limiters, retries, and redirects: `auth_*`, `limiter_*`, `retry_scheduled`, and `redirect` are named but never emitted, `retry_reason` and `parent_session_id` stay None, and `call_start` has no origin, which the first attempt gives (S09-20).
- Every call makes one attempt until retries and redirects arrive (S10), so a body input builds exactly one attempt per call: `BodyAttemptContext` has `attempt_index` and `hop_index` 0 and `remaining_timeout` None, an owned file closes when that attempt closes, and a factory's `fingerprint` is kept but not checked until signing and idempotency use it (S09-5).
- The body inputs build their attempts through `__call__(context)`, the shape of `BodyAttemptFactory`, so the client runtime reaches none of their private state; a factory's attempt is refused as `same_attempt` when it is the one that factory returned last (S09-5).
- `AsyncRawResponse.stream_to` writes its file with blocking calls on the event loop, one chunk of at most 64 KiB at a time (S09-4).
- Embedded packages send no `User-Agent`, since they have no distribution; standalone distributions send `<distribution>/<version>`.
- Response headers without a schema have no decoder, so `decode_<method>_header` leaves them out.
- Until S10, every transport failure is a `TransportError` with its phase and delivery state, `retry_stop_reason` is always `None`, and security requirements are recorded in the contract digests but not applied.
- A `default` response contributes to the success union, since it may carry a 2xx status, as well as to the error payload.
- Unknown keys in nested TOML tables, such as a `resource_names` entry or an operation's `runtime`, are `E_CONFIG_VALUE` from the shared loader; unknown top-level keys are `E_CONFIG_UNKNOWN`.

## S09-1: resources, methods, and URL, parameter, request and response generation

Generator (`_client`):

- `config.py`: `ClientGenerationConfig` with `schema_version`, `transport` (`"httpx2"`), `resource_names` (`ResourceName` tag to dotted namespace), `operations` (`ClientOperationConfig`: `ref`, `resource`, `name`, `parameter_names`, `request_media_type`, `response_media_type`, `runtime` with `request_id_header` and `success_statuses`, `description`), `default_base_url`, `server_base_url` and `codec_adapters`, each checked as §§1 and 7.1 require, and the TOML converters of the shared loader.

## S09-2: response content codings

- `coding.py` reads the codings of every `Content-Encoding` header, comma lists and case-insensitive, drops `identity` and treats `x-gzip` as gzip. They are checked at the first body chunk, so a response without a body never fails on them: more than two layers are a `ProtocolSizeError(kind='content_layers')` and an unknown coding an `UnsupportedContentCodingError`. Each layer is removed incrementally with zlib, gzip with every member and deflate with zlib framing, at most 64 KiB per step, and its decoded bytes may not pass max(1 MiB, 100 × its encoded bytes), or `DecompressionLimitError` stops the read. Corrupt data, data after a deflate stream or garbage after a gzip member, and a coding without its end are `ProtocolDataError(condition='malformed')`.
- The client core reads `iter_raw` and `aiter_raw` and removes each coding exactly once; both body caps count decoded bytes. A response whose body something already read, an HTTPX2 event hook or a mock built from `content=` or `json=`, is refused with `AdapterContractError(delivery_state=RESPONSE_STARTED)` as RUNTIME §4 requires, so the test responders stream their bodies as a server does. A coding failure on a success raises that error. On an error status the operation's `HTTPStatusError` keeps the prefix decoded so far with `truncated=True` and the failure as `error_decode_error`; on an undeclared status `UnexpectedStatusError` keeps it as its cause.
- `errors.py` gains `ProtocolError`, `ProtocolDataError`, `ProtocolSizeError`, `UnsupportedContentCodingError`, `DecompressionLimitError` and `AdapterContractError`, which the generated `errors` module exports. Their messages name only SDK-defined values; the coding a server sent stays in the `coding` field.

Tests: the `codings` runtime scenario decodes gzip, `X-Gzip`, deflate, a stacked `gzip, deflate` body, identity, a two-member gzip body and a 112 KiB list whose gzip body streams in 100-byte chunks; refuses three layers, `br`, a truncated and a corrupt gzip body, data after deflate and garbage after gzip, and a bomb of 2 MiB of zeros; keeps a gzip error payload, a truncated one as the decode error, a coded 302 as `UnexpectedStatusError`'s cause, and a bodyless 204 with an unknown coding; refuses a pre-read mock response; and repeats stacked, identity and truncated bodies with asyncio. The runtime stays at 100% coverage.

Benchmarks (best of 5 × 2000 calls, µs): a GET streaming one small item takes 88.7–92.0 before and 89.1–92.1 after as identity, 92.2–95.6 and 94.1–97.9 gzip-coded; a 30 KiB item takes about 5900 either way, all of it in the model codec.

## S09-3: transport adapters, the client lifecycle, and views

Runtime:

- `transports.py`, exported as `pkg.transports`: `PreparedRequest[AttemptT_co]`, `TransportAdapter` and `AsyncTransportAdapter`, `TransportResponse` and `AsyncTransportResponse`, `TransportCapabilities`, `ResolvedTimeoutOptions`, `TransportTraceSink`, `AttemptIOContext`, `OwnedTransportAdapter[AdapterT_co]` and `IOPhase`, as RUNTIME §1 lists them. `bodies.py` adds the `BodyAttempt` and `AsyncBodyAttempt` protocols a prepared request carries; an encoded body is one `EncodedAttempt` that every attempt reads again.
- `native.py`: HTTPX2 clients behind the same adapter interface. They send with redirects and HTTPX2 authentication off, pass header values as UTF-8 bytes as the parameter codecs encode them (a non-ASCII value failed while S09-3 decoded them as ASCII; CodeRabbit on #4196), stream the body with its `Content-Length`, return `iter_raw` and `aiter_raw` untouched for the SDK to decode, classify HTTPX2 failures by phase and delivery state, and refuse a response whose body something already read (`AdapterContractError`), as S09-2 did.
- `client.py`: every call builds one `PreparedRequest` and sends it through the adapter. `Client`/`AsyncClient` take `transport_adapter`, borrowed unless wrapped in `OwnedTransportAdapter`; giving it with `http_client` or with `http_client_ownership="owned"`, an object without the protocol's methods or of the other mode, and capabilities that are not `TransportCapabilities` are refused at construction. At the adapter boundary a classified `TransportError` or `AdapterContractError` an adapter raises gets the call's identifiers; any other exception becomes `AdapterExecutionError` whose delivery state comes from the trace evidence (`RESPONSE_STARTED` after reported headers, `NOT_SENT` when an adapter with evidence reported no send); a status outside 200–599, headers that are not a `HeadersView`, a phase outside `IOPhase`, or a chunk that is not bytes is an `AdapterContractError`. Empty chunks are skipped. A close failure after a successful read is an `AdapterExecutionError`; after a failure it joins the error's `secondary_errors`, and a `BaseException` such as `KeyboardInterrupt` propagates as it is after the response is closed. The native adapter is trusted, so its responses skip these checks.
- `lifecycle.py`: a client and each of its views are OPEN, then CLOSING, then CLOSED. A call is admitted only while both are open, and an admitted call stops with `ClientClosedError` at its next step (after the headers, between chunks) once either starts closing; a transport failure while closing becomes that error's cause. `close`/`aclose` wait up to `cleanup_timeout` (5 s, a new `ClientOptions`/`RequestOptions` field, positive and finite; a sync close waits in slices of at most `threading.TIMEOUT_MAX`, CodeRabbit on #4196) for the active calls, close an owned transport exactly once, and raise `CleanupError(pending_calls=…)` when calls are left or the transport fails to close; closing again waits again. Admission and release take one lock; only a closing scope is notified.
- `with_options(options)` returns a view of the same class sharing the transport and fixed headers: its calls layer the options on the client's, count in the owner too, and closing it stops only its own calls. Closing the owner stops the calls of every view.
- An `AsyncClient` belongs to the event loop it was created in, or else to the loop of its first call; a call outside asyncio or on another loop raises `UnsupportedAsyncBackendError` before anything is sent.
- `errors.py` gains `AdapterExecutionError`, `ClientClosedError`, `CleanupError` and `UnsupportedAsyncBackendError`, all exported from `pkg.errors`.

Generator: `_client.py`/`_async_client.py` take `transport_adapter`, build their core with `ClientCore.create`, and gain `with_options`; the new `transports.py` public module follows `model_codecs.py`, and `bodies.py` exports the attempt protocols.

Tests: the `transports` scenario sends through queued sync and async adapters: requests with their headers, body, length, media, phase and timeouts; trace evidence; an adapter `TransportError`; adapter bugs before and after reported headers; every contract violation; read and close failures and both together; a `BaseException` while sending and while reading, the latter over a close failure; owned and borrowed adapters, an owned adapter whose close fails, and every construction error; and a pre-read HTTPX2 async response. The `lifecycle` scenario runs views with other options, a closed view beside an open one, a closed owner stopping its views, `cleanup_timeout` validation, and with threads and with asyncio a close that stops an active call, one that outlasts the cleanup time and closes again, and a read that fails while closing; then a call without an event loop, on a second loop, and a client created inside a loop. Both run in `client-e2e`; the runtime stays at 100% coverage. The typing samples add a structural sync and async adapter, owned and borrowed, and `with_options`, clean on all three checkers; the negative sample gains an owned async adapter for `Client`, a sync adapter for `AsyncClient` and `with_options(None)`, one error each on each checker.

Benchmarks (best of 7 × 3000 calls through HTTPX2's mock transport with streamed bodies, µs): GET 99.3–100.0 before and 102.3–104.1 after, POST 115.6–117.5 and 118.4–122.6, DELETE 35.2–36.5 and 39.6–40.7; passing the headers as bytes, which spares HTTPX2 their normalization, brings them back to 100.4, 116.3 and 38.8. The added 3 µs are the adapter layer and its response wrapper, the frozen `PreparedRequest` (0.27), admission and release (0.22), and the attempt context (0.11). The first profile showed the `Condition` lock and a notification on every release; admission now takes the plain lock and only a closing scope is notified.

## S09-4: raw and streaming responses

Runtime:

- `raw.py`, exported as `pkg.responses.RawResponse` and `AsyncRawResponse` (RUNTIME §10): a raw call's response becomes a handle over the native response. `with_raw_response` reads the body into memory and releases the response before returning, keeping `body_bytes` (content codings removed once) and `raw_body_bytes` (as received; an identity body is one shared `bytes`), each within `max_response_bytes`; `read`, `text`, `json`, `iter_bytes` and `iter_raw_bytes` may repeat, the iterators in pieces of at most 64 KiB, and the value stays readable after its client closes. `with_streaming_response` returns a context manager that sends on entry and closes the handle on exit. Its body is read once: `read`, `text` or `json` first buffer it under the same limits and then repeat; one `iter_bytes`, `iter_raw_bytes` or `stream_to` streams it without keeping it, and any other read then raises `ResponseConsumedError(state, action)`, as does reading after `close`, a failure, or the end. `text` decodes with the Content-Type charset or UTF-8 and `json` parses JSON syntax only; their failures are `DecodeError`.
- `max_stream_bytes`, a new `ClientOptions`/`RequestOptions` field defaulting to `None`, caps a streamed body: decoded bytes for `iter_bytes` and `stream_to`, content-coded bytes for `iter_raw_bytes`. The chunk that would pass it is never handed out: the handle closes and `ResponseTooLargeError` names the representation. A buffered body counts its coded bytes against `max_response_bytes` before decoding them.
- `raise_for_status()` returns for a success without reading. ## S09-20: hooks and call events

RUNTIME §11's hooks observe each call through `CallEvent`s. `pkg.hooks` exports `Hook`, `AsyncHook`, `CallEvent`, `CallOutcome`, `EventName`, and `RetryReason`, and `ClientOptions` and `RequestOptions` take `hooks`, which an explicit tuple replaces, and `context`, a secret-free map of JSON scalars whose names a layer replaces, refused over 8 KiB of JSON. A call without hooks builds no event. Events carry the operation's path template, the origin, the attempt index, whether the resource request reached its transport, the status, durations, counters, a request ID the operation declares, and the context, never a query, header, or body.

Each event reaches every hook in order. The first failure raises `HookExecutionError` with the event's name, whether the call sent, and its delivery state, the others joining its secondary errors, and stops the call's further network actions; the attempt and the call still end, and a failure beside an error the call already raised joins that error's secondary errors. Tests: the `hooks` scenario reports every event of a success with a client and a call context and a declared request ID, an HTTP error, a refused encoding, a refused connection, and an interrupted call; hooks failing at the start, before sending, and on headers and every end, with their secondary errors; successes whose call end or every end fails, whose result `require_result` returns, and a failure before sending, whose `require_result` raises `ResultUnavailableError`; buffered and streaming raw calls, a streaming call whose hook fails, and refused raw calls; and refused hooks and contexts, a context merged over 8 KiB, and an async hook on a sync client.
