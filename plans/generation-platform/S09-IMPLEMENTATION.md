## Scope and split

Generated calls have to run to be tested end to end, so S09-1 carries the HTTPX2 core they need: sync and asyncio clients over a borrowed or owned HTTPX2 client, `close`, `aclose` and context managers, `with_response`, the success body cap and the bounded error prefix.

PR-STACKS plans a second PR for HTTPX2 sync and asyncio, injection, ownership and close, and raw, file and multipart bodies. It is split so each part stays reviewable: S09-2 decodes response content codings in the SDK, which raw responses need; S09-3 adds transport adapters, the client lifecycle and `with_options` views; then come raw and streaming responses, and file, stream and multipart bodies with wildcard request media and `RequestCodecs.part`. The third planned PR, the full option set, the remaining typed exceptions, hooks and `api-diff.json`, comes last.

## Deviations from the plan

- Until the rest of the media land, generation fails with the temporary `E_CLIENT_UNSUPPORTED` for multipart request media other than form-data, multipart responses with a schema other than form-data, wildcard request media, a form-data schema that is no object, and form or form-data encodings the writers do not read, so no operation is generated without a capability it needs. The last of those PRs removes the code.
- A media type name that is not a media type, such as `json`, fails with `E_METADATA_REQUIRED` instead of raising `ValueError`. The FastAPI planner still raises; that is left to a separate fix.
- A base URL carries no query, besides the userinfo and fragment the plan excludes: the operation path and query are appended to it, so a query would end up inside the path. One predicate, `options.is_base_url` in the runtime, decides for `ClientOptions`/`RequestOptions`, `default_base_url`, `server_base_url` and resolved servers, so generation and the runtime never disagree.
- `ProtocolError` has no `helper_id` or `operation`, and `ProtocolDataError` no `location`, until the protocol helpers define `OperationRef`, `Selector` and `RequestTarget` (S11).
- `ResponseInfo.elapsed` is measured when the response headers arrive, so streaming handles can carry it (S09-2).
- `AttemptIOContext` has no `deadline` or `cancel_token` until S10 defines `Deadline` and `CancelToken`, and every attempt sees the fixed 5/30/30/5-second phase timeouts until `TimeoutOptions` exists. The native adapter reports no trace evidence and declares none (`delivery_evidence=False`); its failures carry the delivery state their HTTPX2 class implies (S09-3).
- A form-data file part is sent as `application/octet-stream` unless its FilePart names a media type, even when its schema has a `contentMediaType`, and a read-only member keeps its part codec, which refuses any value in a request (S09-8).
- `request_raw` sends the client's fixed headers only, with a `Content-Type` only from a `BodyFactory` that declares one or a multipart body's boundary, until `RequestOptions` carries headers (S09-4, S09-5, S09-6).
- Every call makes one attempt until retries and redirects arrive (S10), so a body input builds exactly one attempt per call: `BodyAttemptContext` has `attempt_index` and `hop_index` 0 and `remaining_timeout` None, an owned file closes when that attempt closes, and a factory's `fingerprint` is kept but not checked until signing and idempotency use it (S09-5).
- The body inputs build their attempts through `__call__(context)`, the shape of `BodyAttemptFactory`, so the client runtime reaches none of their private state; a factory's attempt is refused as `same_attempt` when it is the one that factory returned last (S09-5).
- `AsyncRawResponse.stream_to` writes its file with blocking calls on the event loop, one chunk of at most 64 KiB at a time (S09-4).
- Embedded packages send no `User-Agent`, since they have no distribution; standalone distributions send `<distribution>/<version>`.
- Response headers without a schema have no decoder, so `decode_<method>_header` leaves them out.
- Until S10, every transport failure is a `TransportError` with its phase and delivery state, `retry_stop_reason` is always `None`, and security requirements are recorded in the contract digests but not applied.
- A `default` response contributes to the success union, since it may carry a 2xx status, as well as to the error payload.
- Unknown keys in nested TOML tables, such as a `resource_names` entry or an operation's `runtime`, are `E_CONFIG_VALUE` from the shared loader; unknown top-level keys are `E_CONFIG_UNKNOWN`.

## S09-1: resources, methods, and URL, parameter, request and response generation

Generator (`_client`):

- `config.py`: `ClientGenerationConfig` with `schema_version`, `transport` (`"httpx2"`), `resource_names` (`ResourceName` tag to dotted namespace), `operations` (`ClientOperationConfig`: `ref`, `resource`, `name`, `parameter_names`, `request_media_type`, `response_media_type`, `runtime` with `request_id_header` and `success_statuses`, `description`), `default_base_url`, `server_base_url` and `codec_adapters`, each checked as §§1 and 7.1 require, and the TOML converters of the shared loader.

Reserved members, reserved arguments and Windows device names need explicit names.
- `plan.py`: resources from the first tag or the configured namespace (untagged operations share `default`), parent namespaces, method and argument names with every collision reported (`E_NAME_COLLISION`, `E_RESERVED_NAME`), parameters in §4 order, request media with the default media, responses classified as success or error with their media and headers, effective servers resolved to absolute templates against `server_base_url` or the source URI (`E_BASE_URL`), and operation references of the settings (`E_OPERATION_REF`, `E_CONFIG_CONFLICT`). All problems of a target are reported together.
- `render.py` and `templates/{client,resource,types}.jinja2`, compiled like the model and FastAPI templates: `__init__.py` with lazy `Client` and `AsyncClient`, `_client.py`, `_async_client.py`, the public `options`, `errors`, `responses`, `bodies` and `model_codecs` modules, `resources/<namespace>/{__init__,_sync,_async}.py` with cached child resources and `with_response` views, `types/<namespace>/{__init__,_operations}.py` with `<Pascal>Response`, `<Pascal>ErrorData`, `<Pascal>HTTPError`, `<Pascal>RequestCodecs` and `decode_<method>_header`, `_generated/model_bindings.py`, and `_operations.py` with one `OPERATION_<index>: Final[OperationPlan[<Pascal>Response, <Pascal>ErrorData]]` per operation. ## S09-2: response content codings

- `coding.py` reads the codings of every `Content-Encoding` header, comma lists and case-insensitive, drops `identity` and treats `x-gzip` as gzip. They are checked at the first body chunk, so a response without a body never fails on them: more than two layers are a `ProtocolSizeError(kind='content_layers')` and an unknown coding an `UnsupportedContentCodingError`. Each layer is removed incrementally with zlib, gzip with every member and deflate with zlib framing, at most 64 KiB per step, and its decoded bytes may not pass max(1 MiB, 100 × its encoded bytes), or `DecompressionLimitError` stops the read. Corrupt data, data after a deflate stream or garbage after a gzip member, and a coding without its end are `ProtocolDataError(condition='malformed')`.
- The client core reads `iter_raw` and `aiter_raw` and removes each coding exactly once; both body caps count decoded bytes. A response whose body something already read, an HTTPX2 event hook or a mock built from `content=` or `json=`, is refused with `AdapterContractError(delivery_state=RESPONSE_STARTED)` as RUNTIME §4 requires, so the test responders stream their bodies as a server does. A coding failure on a success raises that error. On an error status the operation's `HTTPStatusError` keeps the prefix decoded so far with `truncated=True` and the failure as `error_decode_error`; on an undeclared status `UnexpectedStatusError` keeps it as its cause.
- `errors.py` gains `ProtocolError`, `ProtocolDataError`, `ProtocolSizeError`, `UnsupportedContentCodingError`, `DecompressionLimitError` and `AdapterContractError`, which the generated `errors` module exports. Their messages name only SDK-defined values; the coding a server sent stays in the `coding` field.

Tests: the `codings` runtime scenario decodes gzip, `X-Gzip`, deflate, a stacked `gzip, deflate` body, identity, a two-member gzip body and a 112 KiB list whose gzip body streams in 100-byte chunks; refuses three layers, `br`, a truncated and a corrupt gzip body, data after deflate and garbage after gzip, and a bomb of 2 MiB of zeros; keeps a gzip error payload, a truncated one as the decode error, a coded 302 as `UnexpectedStatusError`'s cause, and a bodyless 204 with an unknown coding; refuses a pre-read mock response; and repeats stacked, identity and truncated bodies with asyncio. The runtime stays at 100% coverage.

Benchmarks (best of 5 × 2000 calls, µs): a GET streaming one small item takes 88.7–92.0 before and 89.1–92.1 after as identity, 92.2–95.6 and 94.1–97.9 gzip-coded; a 30 KiB item takes about 5900 either way, all of it in the model codec.

## S09-3: transport adapters, the client lifecycle, and views

Runtime:

- `transports.py`, exported as `pkg.transports`: `PreparedRequest[AttemptT_co]`, `TransportAdapter` and `AsyncTransportAdapter`, `TransportResponse` and `AsyncTransportResponse`, `TransportCapabilities`, `ResolvedTimeoutOptions`, `TransportTraceSink`, `AttemptIOContext`, `OwnedTransportAdapter[AdapterT_co]` and `IOPhase`, as RUNTIME §1 lists them. `bodies.py` adds the `BodyAttempt` and `AsyncBodyAttempt` protocols a prepared request carries; an encoded body is one `EncodedAttempt` that every attempt reads again.
- `native.py`: HTTPX2 clients behind the same adapter interface. They send with redirects and HTTPX2 authentication off, pass header values as UTF-8 bytes as the parameter codecs encode them (a non-ASCII value failed while S09-3 decoded them as ASCII; CodeRabbit on #4196), stream the body with its `Content-Length`, return `iter_raw` and `aiter_raw` untouched for the SDK to decode, classify HTTPX2 failures by phase and delivery state, and refuse a response whose body something already read (`AdapterContractError`), as S09-2 did.
- `client.py`: every call builds one `PreparedRequest` and sends it through the adapter. `Client`/`AsyncClient` take `transport_adapter`, borrowed unless wrapped in `OwnedTransportAdapter`; giving it with `http_client` or with `http_client_ownership="owned"`, an object without the protocol's methods or of the other mode, and capabilities that are not `TransportCapabilities` are refused at construction. At the adapter boundary a classified `TransportError` or `AdapterContractError` an adapter raises gets the call's identifiers; any other exception becomes `AdapterExecutionError` whose delivery state comes from the trace evidence (`RESPONSE_STARTED` after reported headers, `NOT_SENT` when an adapter with evidence reported no send); a status outside 200–599, headers that are not a `HeadersView`, a phase outside `IOPhase`, or a chunk that is not bytes is an `AdapterContractError`. Empty chunks are skipped. A close failure after a successful read is an `AdapterExecutionError`; after a failure it joins the error's `secondary_errors`, and a `BaseException` such as `KeyboardInterrupt` propagates as it is after the response is closed. The native adapter is trusted, so its responses skip these checks.
- `lifecycle.py`: a client and each of its views are OPEN, then CLOSING, then CLOSED. A call is admitted only while both are open, and an admitted call stops with `ClientClosedError` at its next step (after the headers, between chunks) once either starts closing; a transport failure while closing becomes that error's cause. `close`/`aclose` wait up to `cleanup_timeout` (5 s, a new `ClientOptions`/`RequestOptions` field, positive and finite; a sync close waits in slices of at most `threading.TIMEOUT_MAX`, CodeRabbit on #4196) for the active calls, close an owned transport exactly once, and raise `CleanupError(pending_calls=…)` when calls are left or the transport fails to close; closing again waits again. Admission and release take one lock; only a closing scope is notified.
- `with_options(options)` returns a view of the same class sharing the transport and fixed headers: its calls layer the options on the client's, count in the owner too, and closing it stops only its own calls. Closing the owner stops the calls of every view.
- An `AsyncClient` belongs to the event loop it was created in, or else to the loop of its first call; a call outside asyncio or on another loop raises `UnsupportedAsyncBackendError` before anything is sent.
- `errors.py` gains `AdapterExecutionError`, `ClientClosedError`, `CleanupError` and `UnsupportedAsyncBackendError`, all exported from `pkg.errors`.

Generator: `_client.py`/`_async_client.py` take `transport_adapter`, build their core with `ClientCore.create`, and gain `with_options`; the new `transports.py` public module follows `model_codecs.py`, and `bodies.py` exports the attempt protocols.

Tests: the `transports` scenario sends through queued sync and async adapters: requests with their headers, body, length, media, phase and timeouts; trace evidence; an adapter `TransportError`; adapter bugs before and after reported headers; every contract violation; read and close failures and both together; a `BaseException` while sending and while reading, the latter over a close failure; owned and borrowed adapters, an owned adapter whose close fails, and every construction error; and a pre-read HTTPX2 async response. The `lifecycle` scenario runs views with other options, a closed view beside an open one, a closed owner stopping its views, `cleanup_timeout` validation, and with threads and with asyncio a close that stops an active call, one that outlasts the cleanup time and closes again, and a read that fails while closing; then a call without an event loop, on a second loop, and a client created inside a loop. Both run in `client-e2e`; the runtime stays at 100% coverage. The typing samples add a structural sync and async adapter, owned and borrowed, and `with_options`, clean on all three checkers; the negative sample gains an owned async adapter for `Client`, a sync adapter for `AsyncClient` and `with_options(None)`, one error each on each checker.

Benchmarks (best of 7 × 3000 calls through HTTPX2's mock transport with streamed bodies, µs): GET 99.3–100.0 before and 102.3–104.1 after, POST 115.6–117.5 and 118.4–122.6, DELETE 35.2–36.5 and 39.6–40.7; passing the headers as bytes, which spares HTTPX2 their normalization, brings them back to 100.4, 116.3 and 38.8. The added 3 µs are the adapter layer and its response wrapper, the frozen `PreparedRequest` (0.27), admission and release (0.22), and the attempt context (0.11). The first profile showed the `Condition` lock and a notification on every release; admission now takes the plain lock and only a closing scope is notified.

## S09-4: raw and streaming responses

Runtime:

- `raw.py`, exported as `pkg.responses.RawResponse` and `AsyncRawResponse` (RUNTIME §10): a raw call's response becomes a handle over the native response. `with_raw_response` reads the body into memory and releases the response before returning, keeping `body_bytes` (content codings removed once) and `raw_body_bytes` (as received; an identity body is one shared `bytes`), each within `max_response_bytes`; `read`, `text`, `json`, `iter_bytes` and `iter_raw_bytes` may repeat, the iterators in pieces of at most 64 KiB, and the value stays readable after its client closes. `with_streaming_response` returns a context manager that sends on entry and closes the handle on exit. Its body is read once: `read`, `text` or `json` first buffer it under the same limits and then repeat; one `iter_bytes`, `iter_raw_bytes` or `stream_to` streams it without keeping it, and any other read then raises `ResponseConsumedError(state, action)`, as does reading after `close`, a failure, or the end. `text` decodes with the Content-Type charset or UTF-8 and `json` parses JSON syntax only; their failures are `DecodeError`.
- `max_stream_bytes`, a new `ClientOptions`/`RequestOptions` field defaulting to `None`, caps a streamed body: decoded bytes for `iter_bytes` and `stream_to`, content-coded bytes for `iter_raw_bytes`. The chunk that would pass it is never handed out: the handle closes and `ResponseTooLargeError` names the representation. A buffered body counts its coded bytes against `max_response_bytes` before decoding them.
- `raise_for_status()` returns for a success without reading. Otherwise it classifies the status as typed calls do: a saved body gives its bounded prefix to the operation's `<Method>HTTPError`, with its error data when the whole body decodes, or to `UnexpectedStatusError` for other statuses; an unread streaming body has its prefix read up to `max_error_body_bytes`; a partly or wholly read one gives `body_bytes=b''` and `truncated=True`; and the handle is closed. `request_raw` has no operation binding and raises `HTTPStatusError` itself.
- `stream_to(path, overwrite=False)` refuses an existing file with `FileExistsError` before reading, writes a temporary file in the same directory that only its owner can read while it is written, then gives it the permissions a plain new file gets under the umask (a `mkstemp` file kept `0600`, and a file created under the umask let other users read a download in progress; CodeRabbit on #4197), and moves it into place on success, without `overwrite` through a new link, which refuses a name that exists, before the temporary name is removed, so that a file that appeared meanwhile is kept and a failed move leaves no file under the target's name (an exclusive create had left an empty one; review of #4197); on failure the temporary file is removed. `stream_to(file)` borrows the file object and never closes it.
- `client.request_raw(method, url, *, body=UNSET, options=None)` and `client.with_streaming_response.request_raw(...)` send to any absolute http or https URL with an optional query; another method than a token, URL, body or options type is a `ConfigurationError` before sending.
- A streaming handle holds its call's lease until it is closed or read to the end (RUNTIME §8), so `close` and `aclose` wait for it up to `cleanup_timeout`, then close the handles still open and raise `CleanupError(pending_leases=…)`. Once its client or view starts closing, a live handle's reads, iteration, `stream_to` and `raise_for_status` raise `ClientClosedError`, as does a stream resuming after its handle was closed that way; `close` stays allowed. A handle's close is taken once under the scope's lock, since the closer and the reader may end it together, and a buffered read that an interruption or the closing client stops before it ends the handle closes it, so its lease never waits for the cleanup time (CodeRabbit on #4197). `Settings` lives in `options.py`, so raw responses type their limits without importing the client core. Buffered raw responses and typed results survive their client.
- Decode failures of typed and raw calls, and a typed call's `ResponseTooLargeError`, now carry the call's `operation_id`, which RUNTIME §9 puts in the `HTTPStatusError` string; S09-1 left it out.

Generator: every resource gains `with_raw_response` and `with_streaming_response` views beside `with_response` (`<Resource>WithRawResponse` and `<Resource>WithStreamingResponse`, exported from the resource package). Their methods keep the body overloads but not the response media ones, since they return `RawResponse`, `AsyncRawResponse` from an `async def`, or `AbstractContextManager[RawResponse]` and `AbstractAsyncContextManager[AsyncRawResponse]` from an ordinary `def`, whatever the media. The clients gain `request_raw` and a `with_streaming_response` view holding its streaming form; `pkg.responses` exports `RawResponse` and `AsyncRawResponse`, and `pkg.errors` `ResponseConsumedError`.

Tests: the `raw` scenario runs, through HTTPX2 and through queued adapters, synchronously and with asyncio: saved responses with identity and gzip bodies, repeated reads, pieces of a 70 000-byte body, request IDs, typed, truncated and redirect statuses, undecodable text and JSON, every buffer limit, broken reads and connections, and invalid options; streaming responses read once by iteration or into memory, every refused second read, a close after a partial read, 100 MiB streamed without a cap, the stream cap on identity, decoded and coded bytes, a failure mid-stream, and a block left by an interruption; `raise_for_status` on unread, truncated, badly coded, broken and partly read error bodies; downloads to a file object and a path, an existing path, `overwrite`, a failure mid-download and a file that appears meanwhile; raw requests saved, streamed, capped and refused; and the lifecycle of handles: a view and a client closing over an open handle past their cleanup time, a stream resuming after that, a live handle while another thread or task closes, handle close failures on exit, after a read failure and after a refused read, a close whose handle fails to close, and adapter contract violations. It runs in `client-e2e`; the runtime and generator stay at 100% coverage. ## S09-5: file, stream, and factory request bodies

Runtime:

- `pkg.bodies` gains the binary inputs of RUNTIME §6: `FileBody(file, *, ownership="borrowed")` and `FileBody.from_path(path)`, `StreamBody(chunks, *, ownership="borrowed")`, and `BodyFactory(factory, *, content_length, content_type, fingerprint)`, with their asyncio counterparts `AsyncFileBody`, `AsyncStreamBody` and `AsyncBodyFactory`; the `SyncBinaryBody` and `AsyncBinaryBody` unions with bytes; and the `BodyAttemptContext` value and the `BodyAttemptFactory` and `AsyncBodyAttemptFactory` protocols. `pkg.errors` gains `BodyNotReplayableError`, `BodyChangedError` and `BodyFactoryError`.
- A binary body of a typed operation, and a `request_raw` body, may be any input of the client's mode. Bytes stay one encoded attempt, built while the request is prepared as before; any other input builds its attempt as the request is sent, and the attempt is closed once the adapter returns, its close failure kept beside a failure that is already propagating; an interruption of that close still closes the response (CodeRabbit on #4198). A body of the other mode, `None`, or anything else is a `RequestEncodingError` before anything is sent, as a `request_raw` body now is too.
- An open file is read from its position when its attempt begins, in chunks of at most 64 KiB, and sent with the `Content-Length` of what is left when it can seek, chunked when it cannot; one call reads it at a time (`BodyNotReplayableError(condition="concurrent")`), one that cannot seek is read once, a borrowed one is left open where reading stopped, and an owned one is closed after its call, so sending it again is `consumed`. A path is opened for each attempt and must still be the file whose device, inode, size and modification time `from_path` found (`BodyChangedError(check="stat")`). A file that grows or shrinks while it is read is `BodyChangedError(check="length")`, and a failure to open, position or read it is a `BodyFactoryError` with the cause.
- A stream is read once and never buffered; an owned iterator is closed after its call. A factory builds a new attempt for each call and gets the call's `BodyAttemptContext`; its attempt is sent with the length it or the factory declares, a contradiction between the two or a body of another length being `BodyChangedError`, and it is always closed. A chunk that is not bytes, and any failure of a factory, stream or attempt, is a `BodyFactoryError`; empty chunks are skipped.
- `AsyncFileBody` does its disk operations on one worker thread of its own, one chunk at a time, started by its first read; `close` and `aclose` stop it, after which the body cannot be sent, and closing a client leaves it alone. `concurrent.futures.thread` is imported only when a worker starts.

Generator: a binary request body is `SyncBinaryBody` in the synchronous resources and `AsyncBinaryBody` in the asyncio ones, imported only where a binary medium appears, and so is the `request_raw` body of each client; the new names are exported from `pkg.bodies` and `pkg.errors`.

Tests: the `bodies` scenario uploads through HTTPX2, synchronously and with asyncio: a borrowed file from its position and again from where it stopped, an owned file and its reuse, a file that cannot seek, one that cannot be read or positioned, one longer or shorter than it reports, an interrupted one, one another call is reading, a path, the same path changed, a removed path, a missing path, and a body of the other mode; borrowed and owned streams and their reuse, chunks that are not bytes, a failing stream, a stream that is not iterable, and an interrupted owned stream; factories with their context and declarations, the same attempt returned twice, a failing factory, an attempt of another length with and without a failing close, attempts longer and shorter than declared, attempts failing to close, to read and close, and to iterate; raw requests with a file and a factory's media type; and attempts built directly from a file and a factory, closed twice. The runtime and generator stay at 100% coverage. The typing samples upload every input of both modes and send raw requests with them, clean on all three checkers; the negative sample gains a body of the other mode for each client, a stream of text, an unknown ownership and a factory of the wrong shape, one error each on each checker.

Benchmarks (best of 7 × 3000 calls, µs, S09-4 then S09-5 over three alternating runs): GET 101.1–101.9 and 101.6–103.2, POST 118.0–119.4 and 117.6–119.2, DELETE 38.9–39.8 and 38.9–39.9, raw GET 53.9–54.4 and 53.2–53.9, `request_raw` 29.2–30.5 and 29.8–30.1, async GET 106.5–107.7 and 106.7–107.8 over five more. A first version that kept every request's body input in a record until sending cost about 0.5 µs a call, so bytes stay the prepared request's attempt and only other inputs are handed on. Importing `bodies.py` takes 0.27 ms instead of 0.10: its 25 classes cost 4 to 6 µs each and its four protocols 9 to 21 µs; its annotation-only aliases are declared for type checkers only.

## S09-6: multipart/form-data request bodies

Runtime:

- `multipart.py`, exported from `pkg.bodies`: the covariant value records `FieldPart[PartT_co](name, value, content_type=None, headers=())` and `FilePart[ContentT_co](name, content, filename=None, content_type=None, headers=())`, the invariant `MultipartBody[PartT](parts)` and `AsyncMultipartBody[PartT](parts)`, and the `BodyInput[PartT]` and `AsyncBodyInput[PartT]` aliases, `TypeAliasType`s with their type parameter at runtime (RUNTIME §6, TYPING §6).
- Each call draws a random boundary and names it in the request's Content-Type. A body is written part by part in order: a field's string as it is, its other scalars as JSON text, and objects and arrays as JSON with `Content-Type: application/json`; a file part with `application/octet-stream` unless it names a media type; a field whose value is UNSET is left out. Names and filenames are quoted as HTML forms quote them (`"`, CR and LF percent-encoded), and a part's own headers must be tokens on one line other than Content-Type and Content-Disposition. Each send encodes the fields and begins each file part's own attempt, so the body has a `Content-Length` when every file part knows its length and is chunked otherwise; a file part that cannot begin closes the attempts begun before it, and closing the body closes every file part's attempt, raising the first failure with the others beside it. A part that is no part, a field value outside the JSON domain, and a body or file part of the other mode are `RequestEncodingError`s at the part's name.
- A typed operation whose multipart/form-data media has no schema takes `MultipartBody[str]`, or `AsyncMultipartBody[str]` in the asyncio resources. One whose schema is an object without file parts takes the model value, as JSON does; its codec encodes and validates it, and each member becomes a part, an array one part per item (an empty array cannot be sent and is a `RequestEncodingError`). `request_raw` takes `BodyInput[WireValue]` and `AsyncBodyInput[WireValue]`.
- The encoders live in the client runtime, not in the shared `model_codecs.media`, so FastAPI packages do not carry them.

Generator: the planner accepts multipart/form-data request media without a schema or with an object schema none of whose members, `allOf` branches included, is a binary string or an array of them; binary strings are `format: binary` or a `contentMediaType` without `contentEncoding`. File parts, other schemas, other multipart media, and form-data encodings keep `E_CLIENT_UNSUPPORTED` with the reason.

Tests: the `media` case gains a form-data profile (scalars, a string array, a referenced object, a nullable member), a free-form form-data body, and parts without a schema; `media-errors` a form-data body that is a string and a file part named in its reason. The `multipart` scenario runs on both backends of the `media` case, synchronously and with asyncio: the profile with every member and with its name only, an empty array, a missing required member, a free-form object and a value that is no object; parts with fields, an UNSET field, a field with its own media type and header, bytes with a quoted filename, a file, a stream, sized parts, no parts and no body; every refused part header, media type, part and mode; a file part refused after another began, file parts failing to close, and raw requests with JSON and text fields. Boundaries are replaced by `<boundary>` in the report. The runtime and generator stay at 100% coverage. The typing samples build narrow parts into a wider multipart body and send `MultipartBody[WireValue]` and `AsyncMultipartBody[WireValue]` raw, clean on all three checkers; the negative sample gains an async file in a synchronous body, an async body for the synchronous client, a field of the wrong type, and a body of another part type, one error each on each checker.

Benchmarks (best of 7 × 3000 calls, µs, S09-5 then S09-6 over two alternating runs): GET 101.2–102.5 and 102.2–102.9, POST 117.2–119.4 and 119.0–119.8, DELETE 39.2–39.5 and 39.0–39.3, `request_raw` 29.9–30.9 and 30.0–31.2, async GET 105.9–107.1 and 106.1–106.5, within noise. ## S09-7: multipart responses

Runtime:

- `pkg.bodies` gains the covariant value records `DecodedPart[T](name, value, filename, content_type, headers)` and `MultipartData[T](parts)` (RUNTIME §9). They compare and hash field by field like the other records, and their representations name a part and its media type, or count the parts, and never show a value, filename, or header value.
- A multipart response is split by the boundary its Content-Type names, quoted or not, as RFC 2046 frames it: a delimiter starts its own line and may carry transport padding, the preamble and epilogue are skipped, a part's headers end at an empty line or at the next delimiter, are read as UTF-8, or as Latin-1 when they are not, and must be tokens with a colon. A part's name and filename come from its Content-Disposition parameters, read in order so that a quoted value cannot hide another, quoted strings unescaped, and the filename is only ever a value. A body that breaks this framing is a `BodyProtocolError(condition="invalid_framing")`, raised once the response is released, with nothing partly decoded.
- A multipart response without a schema is `MultipartData[bytes]`, whatever its multipart media. A form-data response whose object schema has no file parts decodes into the schema's type: each part goes to the member of its name, a scalar read in its lexical kind, as text in the charset its Content-Type names or UTF-8 (review of #4200), unless the part names a JSON media type, an object or array of objects parsed as JSON, repeated parts collected into an array, and other names read by the `additionalProperties` schema, as text when it allows anything, or refused when it is false. An undeclared name, a single-valued member sent twice, and a value that is not its kind or not JSON are `DecodeError`s, and the model codec validates the object, a failure being a `ResponseValidationError`. The planner derives each member's plan from the schema's members, `allOf` branches included.
- Decode failures are published by the failure itself, so `BodyProtocolError` can carry its condition.

Generator: multipart responses without a schema render `multipart_branch` and the payload type `MultipartData[bytes]`; form-data responses with an object schema render model or envelope branches with the part plans. Responses with file parts, and multipart responses with a schema other than form-data, keep `E_CLIENT_UNSUPPORTED`.

Tests: the `media` case reads a profile as form-data parts (every scalar kind, a number that may be an integer, a string array, a referenced object, and integer extras), parts of `multipart/mixed` without a schema, and an id of a form-data response that allows no extras; `media-errors` gains a `multipart/mixed` response with a schema and a form-data response with a file part. The `multipart` scenario reads the profile on both backends, synchronously and with asyncio, with a quoted boundary, a preamble, transport padding, an epilogue, and a boundary mid-line in the preamble, and refuses a missing or other boundary, a part off its line, a body ending at its boundary, an unterminated part, a header without a colon, a part without a name, a name twice, a null member twice, an extra that is no integer, broken JSON, text that is not UTF-8, and a missing required member, and reads text in Latin-1 and UTF-16 as its parts' charsets name; it reads mixed parts with headers, without them, with headers only, and empty, a quoted and an unquoted filename, a quoted filename holding `; name=`, a Latin-1 filename, and extra headers, compares and hashes two reads of them, and refuses an undeclared part where no extras are allowed. The runtime and generator stay at 100% coverage. The typing samples read every field of `DecodedPart[bytes]` and widen `MultipartData[bytes]` to `MultipartData[bytes | str]`; the negative sample narrows `MultipartData[bytes]` to `MultipartData[str]`, one error on each checker.

Benchmarks (best of 7 × 3000 calls, µs, S09-6 and S09-7 over five alternating runs): GET 101.5–103.8 and 101.8–104.0, POST 118.1–121.1 and 118.7–120.7, DELETE 38.9–40.4 and 39.2–39.8, `request_raw` 30.0–30.7 and 30.6–31.3, within noise. `multipart.py` takes 0.28 ms instead of 0.21.

## S09-8: form-data file parts

Runtime:

- `PartPlan` also plans a sent member: whether it holds files, is required, or repeats, and the encoder of its values. `MultipartSource` takes the member plans of a body whose schema has file parts, and each attempt checks the body against them: a part's name must be declared, or allowed by the schema's other properties; a file member takes FileParts and any other member FieldParts; only a file array repeats, as one FilePart for each file; and every required member needs a part. A FieldPart's value goes through its member's encoder, and each item of an array becomes its own part; UNSET leaves an optional member out and is refused for a required one. A body without a schema keeps the S09-6 rules.
- `RequestCodecs` takes the part codecs of each media type as `parts`, with no codec for a file member, and the codec of its other parts as `extras`; `_part(name, media_type)` binds a named member first, then the other parts' codec, and raises `CodecSelectionError` for a file member, a media type without the name, untyped or file extras, and a body without a default media type when the call names none. Its part type parameter defaults to `Never`, so operations without part codecs keep two.

Generator:

- A form-data body whose object schema has a file member, or file extras, is sent as parts. Each member of the body's model becomes a `PartSpec`: its plan, and, unless it holds files, a type use of its own, the body's use at the member's schema bound to the field's type. A typed `additionalProperties` schema binds its schema's own use; `true` or an absent keyword allows extras of any value, and `false` none. A read-only member is not required in a request.
- The target plans the wire again with those part uses when there are any, binds a codec for each instead of one for the body, and records the member plans and part codecs in the contract digests. The body argument is `MultipartBody[PartT]`, or `AsyncMultipartBody[PartT]`, where `PartT` unions the members' outbound types, `WireValue` for untyped extras, or `Never` when every part is a file. `<Method>RequestCodecs` gains `part(*, name, media_type=None)`: an overload for each member with a codec and a union for any name, or one method when only the extras have a codec.

Tests: the `media` case gains a body with a required title and photo, a read-only id, a counted integer, a string array, a referenced object, a file array, and integer extras; one with untyped extras beside a JSON media; one with file extras; one whose only codec is its string extras'; and one whose only part is a file. The `multipart` scenario sends them on both backends, synchronously and with asyncio, with a part codec's value, an unset optional member, files as bytes, streams, and files, and refuses a missing, unset, or repeated member, a file as a field and a field as a file, an integer that is none, an empty array, a name that is no string, a read-only value, a field where only files are extra, and a part no schema allows; it sends an extra through the extras' codec, selects part codecs, and refuses a file's, another media type's, a missing default media type's, and untyped or file extras'. `media-errors` drops the request file part. The typing samples send a pets body with file parts from narrowly typed parts and a part codec's value; the negative sample sends a field of the wrong type and a body of another part type, one error on each checker.

Benchmarks (best of 7 × 3000 calls, µs, S09-7 then S09-8 over three alternating runs): GET 101.9–102.4 and 102.6–103.8, POST 118.9–119.7 and 118.6–119.8, DELETE 39.5–40.2 and 39.4–40.2, `request_raw` 30.1–30.8 and 30.6–31.3, within noise. A form-data body without a schema, two fields and a file, takes 43.4–44.0 and 43.6–44.4 over five alternating runs; the same parts under a schema with file parts take 65.6–66.4, the codec of each field validating its value. `multipart.py`, `codecs.py` and `operations.py` import within noise of S09-7.

## S09-9: form-data responses with file parts

Runtime:

- `PartDecoder[T_co]` reads the parts of one member: `file_part(name, repeated=, required=)` keeps their bytes, and `value_part(name, kind, decode, repeated=, required=)` reads each in its member's lexical kind, or as JSON, then decodes it with the member's codec. `PartsReader[T]` reads a response part by part into `MultipartData[T]` and `parts_branch` makes its branch; the generated registry names `T`, and each decoder's value type must fit it. A part must be declared, or allowed by the other properties, only a repeated member repeats, and every required member needs a part: an undeclared or repeated part and text that is not its kind are `DecodeError`s, a value its codec refuses and a missing member `ResponseValidationError`s.
- The value decoders of headers are also those of parts, so `native_header` and `envelope_header` are renamed `native_value` and `envelope_value`.

Generator: a form-data response whose object schema has a file member, or file extras, is read as parts; others keep the S09-7 object reading. A file member's parts are bytes; any other member's part is read by the type use of its schema, or of its items' schema when the member is an array, so each part of an array holds one item. Typed extras are read the same way, untyped extras keep their bytes, and `false` allows none; a write-only member is not required. The payload is `MultipartData[PartValue]`, `PartValue` being the members' inbound types in member order and `bytes` for files and untyped extras.

Tests: the `media` case reads an upload with a required title and photo, an integer, a string array, a referenced object, an envelope, a file array, a write-only member, and integer extras; a note with file extras; a photo with untyped extras; and a photo alone.
