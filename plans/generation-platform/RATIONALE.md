# Design rationale and maintenance responsibilities

Status: planned; product implementation has not started. This document explains the dcg-owned responsibilities in [PLAN](PLAN.md). [BACKGROUND](BACKGROUND.md) records the earlier requests, and the eight detailed contracts define the implementation requirements.

## 1. Model reuse and separate generation targets

The selected order is shared generation infrastructure, FastAPI server generation, then Python OpenAPI client generation. The server supports Pydantic v2 BaseModel and Pydantic v2 dataclass; the client supports all five existing model backends. Each run selects one target and one root OpenAPI document, with normal external-reference resolution. Existing dcg directory and multiple-file model generation remains unchanged.

The new targets belong in dcg and have no dependency on fastapi-code-generator. The legacy tool retains its existing implementation and normal maintenance against current dcg APIs. Migration guidance follows an available replacement. New server output may differ from legacy output while preserving the useful workflows in [FASTAPI-REQUIREMENTS](FASTAPI-REQUIREMENTS.md).

Share operation facts, final Python type/field bindings, accepted-attempt identity, applicable codec source, and generated-file ownership. Keep FastAPI route policy and client HTTP execution policy in their respective targets. Preserve existing model bytes, APIs, behavior, dependencies, and performance under the same explicit settings. Repository placement alone does not eliminate duplicate interpretation or type repair.

Legacy fastapi-code-generator already uses dcg model generation. That model engine is an existing asset, not a new saving. The new server and client can share operation interpretation and binding rules, but legacy parsing and existing dcg scope traversals remain. The new explicit `api` scope must preserve declaration origins while maintaining alignment with existing effective-parameter and security semantics. See [the existing traversal](https://github.com/datamodel-code-generator/datamodel-code-generator/blob/4f96e22ea403a66faae96f3949d41dd61fc1186f/src/datamodel_code_generator/parser/openapi.py#L637) and [BINDING](DECISIONS-BINDING.md).

Do not first build a universal compiler, protocol runtime, or public plugin framework. Establish the boundaries used by these two targets and the G10 client consumer before server publication. The client remains part of the agreed scope: initial publication requires all five backends and C01–C33, with API-conditional features enabled only from explicit contracts.

## 2. Shared and target-specific maintenance

Measure cost by **rules changed, combinations checked for impact, and distribution units that receive fixes**, not source lines or template counts. The following allocates implementation responsibilities; it is not an unmeasured effort estimate.

| Cost category | Implementation/tests/updates owned | Counted once | Work that remains separate |
|---|---|---|---|
| Existing D | Schema/model engine, five backends, existing formatters/writers/APIs, ordinary bug/dependency maintenance | Existing assets; do not count again as new savings or client increments | Regression/performance verification that new optional integration points do not affect existing paths |
| New shared foundation | Declaration-preserving Api traversal, operation semantics, final model/field/module bindings, actual reuse/collapse/variant relationships, accepted attempts, generation configuration/diagnostics/ownership manifests/publication | One set of rules/source/tests for new server/client. One model generation per execution | Alignment between old-scope/new-Api effective traversals, updates to source type transformations, explicit custom-formatter/type adapters, and cross-target consistency tests |
| Shared wire foundation and first two backend codecs | Schema/direction/alias/omission/null/default/wire-snapshot rules; Pydantic v2 BaseModel/dataclass construction/conversion/conformance | Establish genuinely needed adapters/public factories during FastAPI work; reuse the source and verification corpus in the client. Do not apply codecs uniformly to standard FastAPI boundaries | Additional client-direction/HTTP integration tests, migration to explicit presence/factories/envelopes, and maintenance of differences between standard FastAPI profiles and strict wire rules |
| Three additional client-stage backends | Standard dataclass/TypedDict/msgspec Struct converters; presence/alias/constructor/serializer differences; generated imports/dependencies/conformance | Add converters without reimplementing the wire foundation. Shared source location does not make this increment completed server work | Client request/response and sync/async integration, backend-specific settings, typing/distribution tests. Do not expand into server projection/route tests |
| New server-specific work | Routes, service Protocols, FastAPI Request/Response, routers/tags, selective regeneration, auth integration, forms/uploads, OpenAPI documentation, hooks/templates | No shim reproducing legacy F private-parser objects or live visitors | FastAPI dependency changes, generated service contracts, documentation/HTTP consistency, consumer business-code migration |
| New client-specific work | Methods/resources, request settings, HTTPX2 sync/asyncio, body replay, retry/deadline/auth, exceptions/raw responses, pools/close, hooks | Do not duplicate HTTP execution rules per operation or backend | Sync/async lifecycle conformance, I/O failures, transport dependencies, SDK APIs, and distribution quality |
| API-conditional capabilities | Paging/polling/SSE/NDJSON/WebSocket/webhooks/cache/upload resumption/batch/queue/breaker/compression | Reuse common logical calls/sessions/codecs; one metadata contract and implementation per capability | API-specific state/signature/resumption contracts, combination tests, and selected extra dependencies. Do not charge unused capabilities to SDKs where they are disabled |
| Updating generated packages | Private runtime revisions, dependency ranges, regeneration differences, wheels/typing/snippets, consumer releases | One original generator-side fix and test suite | Bundled copies do not update automatically. Each consumer still regenerates, verifies, and releases |
| Normal legacy-F maintenance | Current D API updates, existing-implementation checks, bugs/dependencies, documentation/help, support triage | Do not allocate the same cost to the new client again | Continues while legacy F remains. Neither permanent old-D pinning nor zero maintenance cost is assumed |

To compare ongoing cost, hold existing D costs common and total **the shared foundation (including new Api traversal and old-scope alignment) + shared wire foundation/first two backend codecs + server-specific work + three additional client converters + client-specific work + enabled extra capabilities + generated-output updates + normal legacy-F maintenance**. Potential savings are duplicated operation interpretation, type-name repairs, codecs, symmetrical fixes to the same rules, and repetitive post-regeneration edits in new server/client consumers or their users. Do not count responsibilities still present in old paths as eliminated or count the same benefit as both server and client savings.

Normal typed forms/uploads use the official FastAPI Form/File/UploadFile interfaces. Do not add a custom part reader, temporary-file ownership system, disk worker, MultipartRoute, cancellation task, or dedicated getter. Known upstream limits on cleanup during parsing do not disappear; the guarantee follows standard capabilities. If standard APIs cannot express custom headers/media for non-file parts, do not silently approximate them. State the supported explicit-adapter or caller raw-Request path. Distinguish legacy F's practical Request-based uses from improvements through typed Form/File. See [the agreed server contract](DECISIONS-FASTAPI.md).

Remaining server costs are finite standard-API projection conditions, required adapters, DI/OpenAPI consistency, and supported-FastAPI-version conformance tests for the two Pydantic v2 backends. Do not maintain two execution backends for every operation. Reuse original-specification semantics, final-type mappings, and needed codecs for the client; do not measure return by the amount of FastAPI validation/serialization reimplemented. Even ordinary Pydantic models can require adapters for original-specification differences in optional/null, validation mode, and serialization. Native-path usage and speedups have not been measured.

The two-backend server scope avoids permanent FastAPI projection and route/DI/served-document combinations for standard dataclass, TypedDict, and msgspec. Their client converters/tests still remain as planned. Shared validators, operation/binding, publication, and HTTP-runtime costs do not scale with backend counts. Do not derive implementation time, maintenance cost, or savings from the two-to-five ratio.

Distribute by target and actual need. Do not bundle converters or dedicated dependencies supporting the three excluded built-in backends into server private runtimes. Explicit custom field types inside Pydantic v2 models and their adapter dependencies are separate real needs; do not prohibit them by package name alone. Clients bundle the closure required by their selected backend and enabled capabilities. Even entirely native server boundaries retain dependencies such as common validators for strict public ResponseCodecs/HTTPResult factories. Do not add these runtime dependencies to existing D model-only installation or unused hot paths.

Continually check new Api/old-scope alignment for overrides by resolved `(name, in)`, operation declaration order and unoverridden common-parameter order, absent/explicit-empty security and materialization, and Path Item reference/base-context/declaration-origin mappings. Give shared semantics independent expectations; separately verify Api-only schema-use coverage, generation order, and type generation. This does not require byte equality between old scopes and Api under different settings. Maintaining these oracles remains a cost after initial integration; loop length does not establish that cost is small. Server and client do not require duplicated fixes, but old-scope changes in D require an impact check against new Api. This responsibility concerns scope/operation progression, not maintaining another compiler or independent model/reference engine.

Initial implementation adds maintenance alongside the legacy tool. Avoid permanent duplication inside the new server/client foundation, and record remaining legacy work separately. No legacy retirement date or automatic migration is assumed. Generated private runtime fixes require regeneration, consumer verification, and release; they do not update installed SDKs automatically.

Optional APIs and internal integration points must preserve the default path. Do not add unconditional observers, graph state, a second parse, or target runtime dependencies to ordinary dcg. Measure dispatch, allocation, retained objects, and imports as well as end-to-end generation; a disabled feature alone does not establish non-interference.

## 3. Backend reuse and caller-visible limits

**The new server's product scope is Pydantic v2 BaseModel/dataclass; the initial client scope is all five backends.** The server focuses on the selected Pydantic v2 business types and FastAPI interfaces; the client connects existing D users' model systems. Explicitly diagnose unsupported server backends. Do not expand support by generating separate Pydantic models or converting at runtime. This does not constrain existing D model-only capability.

| Backend | New targets and implementation stage | Concrete consumer benefit | Additional differences to maintain |
|---|---|---|---|
| Pydantic v2 BaseModel | Server first; reused by client | Integrate existing validators/model APIs/types | Validation/serialization aliases, custom serializers, RootModel, native versus wire constraints |
| Pydantic v2 dataclass | Server first; reused by client | Preserve dataclass call shapes with existing Pydantic validation | Construction/access APIs differing from BaseModel, constructors/native validators, presence outside models |
| Standard dataclass | Added during client work; outside server scope | Preserve business-domain dataclass/frozen/slots/post-init use in the client | Wire validation/recursive conversion, constructor defaults/init, integration without later field mutation |
| TypedDict | Added during client work; outside server scope | Preserve dict-based processing and static types | Absent keys, Required/NotRequired/ReadOnly and related rules, runtime validation, nested-value conversion |
| msgspec.Struct | Added during client work; outside server scope | Preserve existing Struct types/tags/settings and surrounding code | Encoded names, UNSET/default, Meta, union/array-like representations versus API wire rules |

Retry/OAuth/WebSocket need not be implemented per client backend. Converters and combination tests do add work. For each of the two server and five client backends, verify request/response direction, aliases, null/omission, unions/enums/roots, reuse/collapse/module layout, and sync/async integration. Shared wire expectations do not remove per-target execution checks. Do not claim complete initial client support before the other three backends pass. This plan also contains no later expansion of the server to every backend.

Preserving model bytes under the same D/settings lowers switching costs. Users explicitly select **`--openapi-scopes api`** to add types needed for API headers/cookies/response headers/callbacks and similar uses to normal D model generation. New targets must not silently change scopes, reuse, collapse, directional variants, or validation settings. Explain that adding an explicit scope changes the model set as a user configuration change; compare against normal D output with that same configuration.

Unchanged models can have native required fields incompatible with valid directional wire data. Use envelopes reflected in public types at generation time, rather than hiding arbitrary validation failures in dicts or weaker types and calling them successful. This exposes real differences for callers to handle; conversion is not free. All-backend client support does not promise identical native APIs across backends. See [MODEL-CODECS](DECISIONS-MODEL-CODECS.md).

The following presence/direction examples belong to client/server codecs and public factories. Standard FastAPI profiles apply at native server boundaries. Known original-schema differences in nullable/assertion/mode select an adapter at generation time. Restricting support to Pydantic v2 does not make every boundary native. Dataclass differences below apply to shared server/client Pydantic v2 dataclasses and client-only standard dataclasses; TypedDict/msgspec explanations concern the client.

For example, wire `tag` may be optional/nonnullable while D's standard fallback produces dataclass `tag: str | None = None`. `Pet(name='A')` and `Pet(name='A', tag=None)` have identical field values; plain T cannot reveal constructor argument history. Without adding model presence fields, that distinction cannot be reconstructed automatically. Omit this None during plain-T sending only when binding proves the default/nullable annotation came from D's standard optional fallback. Do not extend this rule to schema defaults, explicit model settings, factories, or custom None values. When explicit presence is observable through Pydantic BaseModel `model_fields_set` or actual TypedDict keys, retain None and reject it as a nonnullable violation. Handle normal msgspec UNSET separately.

Pydantic BaseModel applies official optional-field `model_fields_set` before value conversion regardless of nullable/default settings. Omit absent keys; only explicit None becomes null when nullable or an error when nonnullable. TypedDict key absence and msgspec UNSET feed the same omission rule. Plain T for either dataclass has no argument history; nullable None becomes null. In Merge Patch and similar operations, a field intended as omitted can therefore become a deletion request. Generated README/reference documentation must explain required caller use of bound factories or explicit presence. Do not advertise automatic recovery of identical wire values.

Callers needing argument history explicitly switch to generated outbound-codec `from_wire(...)` or `snapshot(value, presence=presence_of(...))`. For example, including dataclass `tag=None` in explicit presence detects a nonnullable violation before sending. Valid omitted wire remains omitted. Do not apply blanket `exclude_none` to plain T or replace constructors to record history. This preserves normal model use, while callers requiring history still change factory calls and tests.

Directional structural differences also require explicit caller operations. Construct a request omitting required/readOnly `id` with `CreatePetRequestCodecs.body().from_wire({'name': 'A'})` and pass the result as the client body. Construct a response omitting required/writeOnly `password` with `GetPetResponseCodecs.body(status_code=200).from_wire({'id': 1})` and return it from the handler. Do not insert fake required values into T; declare the public envelope type for that use in advance. Callers distinguish `ModelValue`, containing a native value, from `ModelInput`, containing validated wire but no complete T. Valid complete T values remain accepted for sending; the original model class is unchanged.

Envelopes retain wire snapshots, so later mutation of an enclosed model does not automatically change sent content. To send changes, use `snapshot(new_value, presence=...)` or `from_wire(new_wire)`. The cost of model preservation includes public-type checks, caller/handler changes, migration documentation, and presence/direction tests across two server/five client backends. The benefit is avoiding redefinition of supported existing models, validators, and surrounding code, not a guarantee that every integration call stays unchanged.

## 4. Implementation assistance and independent verification

LLM assistance can be used for implementation, reproductions, fixtures, documentation, and dependency-change investigation. Acceptance still requires independent protocol expectations, code review, static positive/negative cases, generated-package execution, and compatibility/performance comparisons. Do not derive expected results solely from the same extractor or implementation under test.

Measure maintenance through rules changed, affected combinations, and distribution units receiving a fix. Do not substitute generated line counts or assumed savings percentages for observed work. Count shared semantics, binding, the first two backend codecs, and publication once; keep the other three client converters, client integration tests, runtime behavior, and dependency updates explicit.

## 5. Bounded later-input roadmap

The fixed main accepts OpenAPI, JSON Schema, AsyncAPI, MCP tool schemas, GraphQL, Avro, XML Schema, Protocol Buffers, JSON/YAML/CSV/dict, and Python models. See [input list](https://github.com/datamodel-code-generator/datamodel-code-generator/blob/4f96e22ea403a66faae96f3949d41dd61fc1186f/README.md#L260) and [enum](https://github.com/datamodel-code-generator/datamodel-code-generator/blob/4f96e22ea403a66faae96f3949d41dd61fc1186f/src/datamodel_code_generator/enums.py#L35). Their model-generation support does not establish existing communication/execution runtimes.

**Expand uses in the following order. Do not add new-protocol generators to the initial server/client implementation.** This is a bounded roadmap selecting later artifacts and exclusions, not a list of implemented future capabilities. Do not make these later items prerequisites for the initial contracts.

| Priority | Input/use | Selected later artifact | Reuse/new cost | Explicit exclusions |
|---|---|---|---|---|
| 0 | Single-root OpenAPI server/client, with external references | Complete two server/five client backends, production capabilities, and regeneration preserving supported existing models/handwritten code | Current shared semantics/binding/codecs/ownership/publication; new-Api/old-scope alignment | Multiple-root batch input in new targets, the three excluded server backends, or requiring other schemas for completion. Preserve existing D directory input |
| 1 | JSON Schema: configuration files, ETL JSON records, job inputs/outputs, structured LLM-output boundaries | Generate typed decode/encode and schema-conformance checks without communication. Validate wire conditions absent from models outside them, then pass data into existing models | JSON alias/presence/validation/type-binding/regeneration rules. Schema-only entry points/type acquisition are additional work, not completed by OpenAPI support | Guarantees of LLM semantic/business correctness, universal arbitrary-format validators, mandatory validation dependencies for model-only use |
| 2 | MCP tool schemas: typed connections between existing Python business functions and tool calls | Types from explicit inputSchema/outputSchema and input/output adapters for an existing MCP SDK. The SDK/caller owns connections/sessions | Reuse JSON Schema/model binding; add tool names, structuredContent, protocol-error/tool-error distinctions, and schema-change reconciliation | Custom MCP transports, authorization infrastructure, autonomous tool selection/agent loops, arbitrary-tool safety judgments, inferred types for undeclared output |
| 3 | AsyncAPI: event/task-message producer/consumer boundaries | Codecs binding payloads/headers to existing Python types and handler integration. Initially limit output to JSON-message boundaries and inject broker clients | Reuse model/field binding, JSON codecs, manifests/regeneration; add dedicated channel/message/reply semantics | Custom Kafka/AMQP/MQTT transports, generic ack/offset/ordering/exactly-once guarantees, automatic execution of every binding |
| 4 | GraphQL: calls using existing schemas and explicit queries | Later adapters providing operation-document and variable/selection type bindings to existing GraphQL execution libraries | Naming/type/regeneration foundations; new selection/alias/fragment/partial-error/result-shape mappings | Treating schema types as results for every query; simultaneous implementation of resolvers/query builders/subscription transports |
| 5 | Protobuf/gRPC and Avro: RPC/data-pipeline type boundaries | Explicitly mapped adapters between supported native messages/serializers and D models. Model-only uses remain available first | Python type assets/artifact management; new format-specific presence/oneof/logical-type/reader-writer-schema conversions | Custom protobuf wire codecs, gRPC stacks, Avro binary codecs/containers, or schema-registry operation |
| 6 | XML Schema: existing XML integrations and Python domains | Use-specific mappings between selected existing XML parsers/serializers and D models | Reuse final types/regeneration; add namespaces, attributes/elements, ordering, and mixed-content mappings | Complete XML round-trip guarantees from XSD models alone, SOAP/WS-* stacks, custom XML-validation engines |
| Entry point at every stage | JSON/YAML/CSV/dict samples and existing Python models | Preserve current model-only generation as the entry point. Validate inferred sample shapes; move to explicit schemas for ongoing contracts. Generate type representations from Python types for integration/migration | Improve use of current inputs, type settings, and regeneration | Guarantees about unseen sample values/requiredness, semantic migration of arbitrary Python methods/validators, communication protocols inferred from samples alone |

This order follows whether existing assets can complete a useful task with few new responsibilities. Start with non-network JSON boundaries, then MCP using an existing SDK, then message boundaries. GraphQL, binary schemas, and XML come later because their semantic differences extend further beyond types. Do not begin multiple new protocols simultaneously.

The official MCP 2025-06-18 specification distinguishes inputSchema, optional outputSchema, structuredContent, protocol errors, and tool-execution errors. These provide a concrete use for typed adapters. [MCP Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools). Fixed D's [MCP input](https://github.com/datamodel-code-generator/datamodel-code-generator/blob/4f96e22ea403a66faae96f3949d41dd61fc1186f/docs/mcp-tools.md) remains experimental model generation without connections or tool execution. Its [AsyncAPI input](https://github.com/datamodel-code-generator/datamodel-code-generator/blob/4f96e22ea403a66faae96f3949d41dd61fc1186f/docs/asyncapi.md) generates payload/header and related models without broker runtimes or runtime message validators.

Likewise, fixed D's [GraphQL](https://github.com/datamodel-code-generator/datamodel-code-generator/blob/4f96e22ea403a66faae96f3949d41dd61fc1186f/docs/graphql.md#L261), [Protobuf](https://github.com/datamodel-code-generator/datamodel-code-generator/blob/4f96e22ea403a66faae96f3949d41dd61fc1186f/docs/protobuf.md#L152), [Avro](https://github.com/datamodel-code-generator/datamodel-code-generator/blob/4f96e22ea403a66faae96f3949d41dd61fc1186f/docs/avro.md#L128), and [XML Schema](https://github.com/datamodel-code-generator/datamodel-code-generator/blob/4f96e22ea403a66faae96f3949d41dd61fc1186f/docs/xmlschema.md#L72) documentation states their runtime exclusions. The roadmap does not immediately implement every missing part. It selects only needed type integrations for each later target and uses existing specialized runtimes.

Later reuse concerns final Python type/field/artifact contracts, ownership/publication, applicable codecs, and tests. Do not expand OpenAPI operation records into a common IR for GraphQL selections or broker deliveries. Extract only responsibilities actually used by a second consumer, retaining model-output invariance and unused-path dependency/performance protection.

## 6. Evidence required from implementation

| Observation | Comparison and records | What does not count as success |
|---|---|---|
| Protecting existing D | Same-version/same-condition baseline/candidate; normal/new-target generation with identical model settings. Compare bytes/APIs/side effects/dependencies/wall/CPU/memory against existing gates | Silent setting changes such as timestamps, broad normalization, or golden updates hiding differences |
| Ongoing new-Api/old-scope alignment | Independent override/order/security-materialization/reference/declaration-origin oracles; record preserved old-scope behavior separately from Api-only coverage | Assuming simple inheritance of the old loop preserves declaration identity, judging cost by line counts, unconditional byte equality across different scopes |
| New-server regeneration value | Original/changed specifications for the same business workflow; record unchanged implementation modules, necessary business changes, and manual patches to generated code | Generation alone, apparent success with unimplemented service methods, examples omitting needed operations |
| Client incremental costs and benefits | Separate shared-foundation/first-two-backend reuse, three additional converters/tests, and client runtime. Record consumer edits across workflows and revisions including authentication/failures/paging/streams | Counting shared-source effort again, hiding client work as completed server work, deriving effort from backend counts |
| Two server/five client backends and API-conditional capabilities | Run target-specific fixtures, combination acceptance, independent wire/state/signature vectors, generated-package installation/typing. Record plain-T None, explicit presence, outbound factories, directional envelopes, and caller changes | Reusing acceptance claims from a different server scope, counting checkmarks, expectations only from a shared extractor, unsupported diagnostics alone, claims of recovering unobservable constructor history |

These checks are implementation acceptance requirements, not completed results or unresolved design choices.
