# S07 implementation record

Status: in progress. S07 (FastAPI completion and publication) stacks on S06 (#4157, #4158, #4159), which stacks on the S05 stack (#4151, #4152, #4154). Nothing in these stacks has been merged. S07-1 (#4160), S07-2 (#4161) and S07-3 are ready for review.

## Baseline and review boundaries

The authoritative contracts are DECISIONS-FASTAPI §1 (the `templates`, `hooks` and `update_groups` fields), §8 (served OpenAPI), §9 (public values, hooks, templates and formatting), §10 (selective regeneration and the target manifest) and §11 (diagnostics and the F01–F13 oracles), DECISIONS-ENTRY for the public entry points, and FASTAPI-REQUIREMENTS F01–F13, read from the plan checkout used since S03. PR-STACKS splits S07 into templates, hooks, selective updates and collision diagnostics; served OpenAPI, two-generation updates and the F01–F13 integration; and the public Python APIs, the CLI, distribution, docs and examples. Only S07-3 exposes the new server as available, so S07-1 and S07-2 keep every new surface in the private `_fastapi` package behind the S05 coordinator.

## Deviations from the plan

- Template rendering follows the model side, as decided before S05 and recorded in S06. Builtin roles are `.jinja2` files shipped with compiled renderers; a template directory overlays roles through the same `_build_environment` as custom model templates, with Jinja imported only when a directory is configured. The sandboxed environment of §9.1 and §9.3 (`SpecText`, `Identifier`, `EncodedFragment`, `TemplateSafetyError`, and the provenance-tracking AST comparison of rendered tokens) is not implemented: templates receive plain values, and every Python artifact is still parsed and compiled before and after formatting (`E_TARGET_SOURCE`, S05-3). Rendered JSON, TOML and YAML extra files are parsed as well; Markdown, HTML, XML and text files are written as rendered.
- A custom role receives the builtin role's own values, so a copy of a builtin template renders the same file, and the §9.1 frame: `context`, plus `router` and `tag` in the router role. The plan's handler, `auth.py` and `main.py` roles do not exist, since generated packages have no create-only stubs (S06-3); the services role renders the service Protocols. The convenience aliases `info`, `imports`, `operations`, `callbacks`, `routers` and `tags` are not added, because `imports` already names the module's import block in every builtin role; templates read them from `context`. To give the router frame its §9.1 name, the builtin router template now calls the `APIRouter` spelling `api_router`.
- `RenderType` has no per-file `annotation`. A type's `value` spells it through the aliases of its absolute `imports`; a custom role that keeps the builtin module structure uses the builtin role's precomputed signatures instead.
- `FastAPIContext` has no `diagnostics` field yet: the binding records ignored encodings and headers without reporting `I_OAS_ENCODING_IGNORED` or `I_OAS_HEADER_IGNORED`, so there is nothing to snapshot. `callbacks` and `CallbackView` joined with S07-2.
- Context records are frozen dataclasses and read-only mappings. Assigning to a record raises `dataclasses.FrozenInstanceError`, an `AttributeError`, rather than the `TypeError` §9.2 names; writing to a mapping raises `TypeError`.
- Hook failures are reported at a new `hook` diagnostic stage, between selection and target.
- The configured template directory is recorded like model custom templates, as a public option URI; the bytes of its templates are not digested into the manifest. Changing a template changes the files it renders, which `check` reports.
- Fingerprints are conservative equality checks, as §10.1 intends. `signature_sha256` hashes the operation's service method spelled in a module of its own. `plan_sha256` hashes the finalized operation plan: its reference, method, source facts, route, names, mode, arguments with their native declarations, decisions, security, body media and responses. `codec_sha256` hashes the operation's codec bindings with the schema each validates against, not whole source documents, so an unrelated schema change does not block a partial update. `docs_sha256` (S07-2) hashes the operation's served-document fragment with the schema components and security schemes it uses. The builder of the finalized `OperationView` spells every type and costs about 22 ms for 200 operations, so it runs only for hooks and templates.
- The OpenAPI plan module carries the package's fragments and components as one raw string of ASCII JSON, which the runtime reads only when it composes a document, instead of Python literals. For 200 operations, formatting and compiling the literal module took 51 ms of every render and importing it 3.2 ms; the string takes 4.5 ms to format and compile, and reading it 1.0 ms. `OpenAPIPackagePlan` therefore has `package`, `version`, `repeated`, `operation_keys` and `bundle`, whose operations keep the method, route path, slots and fragment §8 lists.
- Added schema components are named `<name>__<first 12 hex digits of SHA-256 of the canonical [package, schema_id, direction]>`. §8 names the schema and direction only, but schema identities use logical document URIs every package shares, so two packages installed in one application would otherwise give different schemas one name. The name is the source component name (or the `$defs`/`definitions` name), otherwise the model symbol a type use binds to the schema, otherwise `Schema`; §3 normalizes it only when it does not match OpenAPI's component-name pattern. Security scheme components are `dcg_<§3 scheme name>__<12 hex digits of the package name's SHA-256>`, and two schemes whose names normalize alike are `F_NAME_CONFLICT`. The generated errors use `dcg_http_error` (a `detail` of any JSON value, with the generated messages as examples), `dcg_validation_error` and `dcg_server_error` under the same suffix.
- Every operation's fragment carries its source security, `[]` when it is anonymous, so the composition always sets the operation's `security`.
- A 3.2 custom method, which FastAPI documents as a lowercase path item member, is served under `additionalOperations` with its source spelling.
- The parser walks a callback object once, so an operation that reuses a callback object documents the operations the first walk recorded, under keys built from its own use site. A callback nested in itself is documented once. Callback security that is malformed or names an undeclared scheme is left out with `W_DOCUMENTATION_ANNOTATION`, as is a documentation value without a JSON form; only non-string mapping keys reach that point, since non-finite numbers stop binding capture and binary values stop the document digest. Callbacks bind no codec, so `CallbackUseView.type` is always `None`.
- Multipart encoding headers and source `x-` extensions are not served: the binding does not plan encoding headers, and operation facts do not capture extensions.
- The installed `app.openapi` returns its cached document only while `app.openapi_schema` is that document, so clearing the public cache also composes the document again.
- A native path argument whose placeholder takes a slot is declared by the slot. S06-1 declared it by the wire name, which FastAPI never finds in the route (every request failed with 422); the fix is in #4157. FastAPI's own 422 reports the slot name in `loc`.
- A partial update requires every model artifact to be byte-identical to the previous generation. §10 limits that to the model modules unselected operations reference; with the default single model module the two rules are the same, and precise module dependencies for multi-module output are left to a later change.

## S07-1: templates, hooks, selective updates, and collision diagnostics

Generator:

- `config.py`: `hooks` (`HookReference` records or callables; TOML `[[hooks]]` tables with `module` or `file` and an optional `callable`), `templates` (a directory path, resolved against the configuration file in TOML) and `update_groups` (a tuple of group keys; a TOML array).
- `context.py`: the §9.1 records the hooks read and the templates receive: `FastAPIContext`, `OperationView`, `ArgumentView`, `RequestView`, `MediaView`, `ResponseView`, `HeaderView`, `PrimaryResponseView`, `RouterView`, `ModelSymbolView`, `FastAPIProjectionView`, `NativeDeclarationView`, `PathSlotView`, `SourceView`, `RenderType` and `ImportSpec`, with `FastAPIContextPatch`, `FastAPIHook` and `HookReference`. `views.py` builds them from the plan: source locations as the manifest's persistent URIs, types through the renderer's own spellings with absolute imports, codec binding and schema identities for bound uses, native declarations with their projected keywords, and nullability from the bound model symbol.
- `hooks.py`: each hook is called once at each position, a referenced module or file once per generation (a file under a module name derived from its path and content, without touching `sys.path`). A patch that is not a `FastAPIContextPatch`, names keys the context does not have, or carries invalid names, modes, JSON extras or imports is `E_HOOK_CONTRACT`; a revision the planner rejects, such as two operations with one name, is `E_HOOK_CONFLICT`; an exception of the hook itself propagates. Names, router names and modes merge last-wins into a `Revision` the planner applies over the configuration, `operation_order` selects and orders operations, and extras and imports stay in the context. Operations a hook removes are reported and persisted as `S_OPERATION_EXCLUDED`.
- `templates.py`: a template directory overrides any of the builtin roles present in it (`application.jinja2`, `router.jinja2` and `services.jinja2`, and `readme.jinja2` since S07-3), and `fastapi-templates.toml` declares extra files in order: `template`, `path`, `scope` (`project`, `router` or `operation`, expanding `{router}` or `{operation}`), `format` (inferred from the extension) and `header` (false outside Python). Every extra file is owned and rendered again on each run, so the manifest has no `ownership` key. An invalid manifest, an escaping or misplaced path, an unknown format, or a rendered JSON, TOML or YAML file that does not parse is `F_TEMPLATE_INVALID`; two files on one path are `F_NAME_CONFLICT`.
- `fingerprints.py` and `target.py`: the manifest records `update_groups`, each operation's `binding_uses`, `model_artifacts`, `files` and three fingerprints, each group's `files`, the `shared_files`, and the `runtime_revision` pointer. Each record is projected once however often the plan refers to it.
- `partial.py`: `update_groups` needs an earlier generation and known group keys (`F_SELECTION_INVALID`), and the same layout, selection and runtime revision, unchanged fingerprints outside the updated groups, and unchanged model artifacts (`F_PARTIAL_UPDATE_INCONSISTENT`).
- `_api_generation.py`: `RenderedFile.header` leaves the generated header off a file, and `TargetRender.update_groups` makes the coordinator reject a partial update whose finished files of other groups differ from the recorded hashes, or that would delete a file.

Tests:

- The main suite renders the hook fixtures: a chain that renames, reorders and removes, makes methods asynchronous, adds extras and imports, and records the final context, which the report shows as JSON; hooks loaded from a module, a file and a file that fails to load; and every contract, conflict and exception path. Template fixtures override each role and render extra files of every scope and format, and reject every manifest, path, format and collision error. Seven scenarios cover `update_groups`: a first run, unknown and empty groups, an update confined to one group, changes of another group's operation, of a model, of the layout, of the selection, of the runtime revision, of the router template, and a partial update that would delete files. The configuration cases load and reject the new fields.
- The `fastapi-e2e` suite serves a package whose hooks renamed its operations and made them asynchronous, rendered from the custom templates.
- The `_fastapi` package stays fully covered, and strict mypy 2.3.1, strict Pyright 1.1.414 and 1.1.411, and ty report nothing for it.

Benchmarks (`render_target`, builtin formatter, median of seven runs, one session): 10, 50 and 200 operations take 44.3, 172.3 and 692.2 ms on S06-3 and 45.9, 177.3 and 711.4 ms on S07-1. The difference is the target data every manifest now records, about 20 ms for 200 operations, mostly the plan, codec and signature fingerprints. Memoizing mapping projections as well as records made the codec fingerprints 0.7 ms faster but the plan fingerprints 3.2 ms slower, so only records are memoized. A no-op hook takes 46.7, 185.7 and 740.4 ms, one context build; the custom template directory, which adds two extra files per operation, takes 52.2, 196.0 and 773.0 ms.

## S07-2: served OpenAPI, two-generation updates, and the F01–F13 integration

Generator:

- `openapi.py`: each operation's fragment: its adapter parameters, its adapter or raw request body (a raw body says the server does not validate it), every declared response with its headers, content and links, the exact response a route without a primary registers, the generated errors (400 and 422 for codec adapters, 415 for an adapter body, 401 with an optional `WWW-Authenticate` header and 403 for security, and 500 always) merged into the exact, range or default response they fall under, its security, its callbacks, and its own servers and external docs. Schemas are the codec's normalized 2020-12 resources with the direction's patches, and every reference is renamed to a component; discriminator mappings follow bundled schemas. Callbacks are planned in a wire plan of their own, only when there are any, so the codec's bundled resources do not change.
- `callbacks.py` finds each operation's callback operations, including those of shared callback objects; the context (`CallbackView`, `CallbackOperationView`, `CallbackUseView`, and `OperationView.servers` and `callbacks`) and the docs use the same tree.
- `render.py` registers each route with its source `response_description` and the `x-dcg-operation` marker, renders `_generated/openapi.py`, and adds `install_openapi` to the application and the package root; `create_app` installs the package and evaluates `app.openapi()` before it returns, then drops the checked document so the served one also covers routes the application adds afterwards. A source operation that declares `x-dcg-operation` is `F_ROUTE_INVALID`.
- `target.py` records `served_openapi` (version, plan module, bundle digest, components, security schemes), `callbacks`, and each operation's `docs_sha256`, which `partial.py` compares with the other fingerprints. The digest covers the operation's fragment and every schema component and security scheme it uses, following references between components, so a partial update cannot change the served documentation of another group through a shared component.

Runtime (`_runtime/server/openapi.py`): `install` registers or replaces one package's plan with the checked `operation_keys`, keeping the first factory, and clears both caches without calling the factory. Evaluation follows §8's order: the cached document, one factory call, a checked JSON copy, marker validation (shape, version, owner, included keys, method, and a literal prefix before the route path), composition in package, operation and path order, marker removal, and caching; a failure leaves both caches empty and propagates the factory's own exceptions. Composition renames slots and path parameters back to the source placeholders, adds adapter parameters by location and name, shares identical request bodies and other members, merges responses (the factory's values first, `anyOf` for different schemas of one media, identical headers only), composes the application's security with the source's as a product, adds components (identical ones shared; a package serving some of its operations adds only the components and security schemes their fragments reach), and serves 3.2.1 when any package or the factory needs it; conflicts are `OpenAPIConfigurationError`. A later package validates an earlier runtime's state and plans by their attributes.

Tests:

- The `fastapi-e2e` suite serves seven documents (pets, parameters with renamed and repeated placeholders, security, bodies, callbacks, the 3.2 methods, and renamed native path parameters) and composes applications that include one package under two prefixes, a nested prefix and `create_app`'s prefix; install a group, every operation, or none; combine two packages in either order, with a package that includes nothing, and with an unknown owner; count factory calls through installs, evaluations, cache hits, invalidation and a failing factory; reject every install argument, marker, prefix, version, collision and document error; reject unknown states and malformed or incomplete plans and accept a foreign one; and compose the application's own security, headers, bodies, a user query named like a cookie adapter, a factory example, and `default_response_class=PlainTextResponse`. The e2e `parameters` case (#4157) now serves a native path argument in a slot.
- The main suite shows the plan module of the parameters, security, bodies and callbacks fixtures, records the callbacks context, rejects two schemes that normalize alike and a source marker, and adds an update scenario whose only change is a response link, which `docs_sha256` catches, and one that changes a security scheme only the updated group uses, then one another group shares, which it refuses.
- The typing samples connect `install_openapi` with a subset and with every key, and pass an unknown key, which every checker rejects once (mypy `arg-type`, Pyright `reportArgumentType`, ty `invalid-argument-type`); the generated package and samples have zero diagnostics on strict mypy 2.3.1 and strict Pyright 1.1.414 and 1.1.411 for both backends.
- `_fastapi` and the server runtime stay fully covered.

F01–F13: besides the S05–S07-1 tests, S07-2 covers the served-document parts of F02 (prefixes, repeated and nested includes, markers, versions), F07 (declared responses next to FastAPI's, `default_response_class`), F08 (the reserved marker), F10 (security composition, install order, caching and document errors), F11 (callback documentation) and F13 (the docs fingerprint in partial updates). Not run yet: the comparisons with handwritten control applications (F01, F06-a, F07) and with a client generated from the same source (F04, F05), F06-c (disconnects and cancellation), F12's excluded backends and multi-module model output, and F13's runs from other working directories and separate checkouts.

Benchmarks (one session, as in S07-1): 10, 50 and 200 operations render in 50.8, 198.8 and 780.0 ms on S07-1 and 51.9, 202.1 and 802.6 ms on S07-2. For 200 operations the docs take 5.2 ms, the plan module 0.9 ms, the added manifest records 4.5 ms, and the 287 KB plan module the rest of its per-file work. Composing a served document adds 0.4 and 5.1 ms to FastAPI's own 3.7 and 62.8 ms for 10 and 200 operations.

## S07-3: public Python APIs, the command line, the package README, and docs

Public API:

- `datamodel_code_generator.fastapi` exports `generate_fastapi` and `render_fastapi` (ENTRY §2), `FastAPIConfig`, `ResponseChoice`, `HookReference`, the `GenerationInput` alias, and the shared records; `datamodel_code_generator.fastapi.templates` exports the context records hooks read and templates receive; `datamodel_code_generator.api_types` exports the shared records, errors, operation selection, codec registrations and capability values. Nothing is added to the top-level module. The entry points import the coordinator and the target lazily, and `get_type_hints(..., include_extras=True)` resolves their annotations, so `GenerateConfig` is imported at runtime: 53 ms of the module's 92 ms import, which a caller constructing a `GenerateConfig` pays anyway.
- Existing D failures keep their types and causes, and a stage diagnostic is attached to them: `E_MODEL_CONFIG` for facade preparation, `E_MODEL_PARSE` for model generation, and `E_HOOK_FAILURE` (with the hook's option path and the target id) for an exception a hook raises or its module raises while loading. The command line reports the attached diagnostic; any other exception is `E_GENERATION_FAILURE`, with its traceback on stderr.

Command line (`_target_cli.py`, ENTRY §3–§4):

- `--generate-server fastapi` (one choice, in a mutually exclusive group that `--generate-client httpx` joins in S14), `--target-config`, `--target-output` and `--diagnostics-json` belong to a new experimental help group. A target option without the selector, the selector without `--target-config`, or the selector with an option that only prints information (`--install-skill`, `--generate-prompt`, `--generate-pyproject-config`, `--generate-cli-command`, `--output-format-json-schema`, `--list-deprecations`, `--list-experimental`) is a usage error checked right after parsing; `--help` and `--version` keep their early exits.
- The selector runs after the existing model validation. `--job` and `--all-jobs`, and `--watch`, `--diff-against`, `--input-model` and `--output-format json` from the command line or `pyproject.toml`, are `E_CONFIG_CONFLICT` diagnostics. The model settings are the CLI configuration's `GenerateConfig` fields with the run's values, built once in `__main__._target_settings`: passing the CLI configuration itself recorded CLI-only fields such as `check` in the manifest provenance, so `--check` right after a generation reported the manifest as changed.
- Without `--input` or `--url`, the target validates its settings, then reads the document from stdin. `--check` renders without writing and lists each changed file as `<action> <path>` on stderr (paths under the working directory relative to it), exiting 0, 1 or 2; `--check` with `--emit-model-metadata` keeps the existing D error. Diagnostics print to stderr as `CODE severity stage location: message`, and `--diagnostics-json` writes JSON v1 to a file or, with `-`, to stdout, which carries nothing else. A diagnostics path the generation reads or writes, or inside the model or target output, is `E_CONFIG_CONFLICT`, checked before any setting is read, and nothing is written to it; an existing file is replaced only when it has the exact shape of a report for the same target; a directory, a path in a missing directory, or a failed write is `E_CONFIG_VALUE` with exit 2. Usage errors, like argparse's, write no document.
- `__main__` hands the target to the runner through one lazy import in `_run_target`, the only exception the architecture checker allows (`_target_cli` itself is a target module).

Package and docs:

- Target files other than Python sources are encoded as UTF-8, which TOML, JSON and the packaging tools reading the README require; `encoding` applies to Python sources, which declare it.
- The builtin `readme.jinja2` role renders an owned `README.md` at the target root: the operations of each service, implementing the service Protocols in the user's own modules and connecting them through `create_app` (with the authorizer when any operation is secured) or a user's own `FastAPI` app with `build_router` and `install_openapi`, the schemes and their credentials (a credential extractor may return any payload, whose `kind` the authorizer checks, as #4158's review asked to state), the served document and the duplicate-registration limit, the validation boundaries (codec answers, FastAPI's repeated query and header values, native form extraction, raw request bodies), the dataclass omission example, and regeneration. A standalone `pyproject.toml` declares it as `readme` and includes it in the sdist. With each service's methods and the other placeholders filled in, every Python example of the README of the pets and secured fixtures has zero diagnostics on strict mypy 2.3.1 and strict Pyright 1.1.414 and 1.1.411 for both backends. The template compiler accepts `operation`, `scheme` and `service` as loop names.
- `docs/fastapi-server.md` (new "Generation Targets" navigation group) covers the quick start, requirements, the Python API, every target setting, the package layout and ownership, regeneration and checks, templates and hooks, and diagnostics; four manual CLI pages document the new options; generated CLI, skill, experimental and llms docs are rebuilt. `cli-option.generate-server` and `python-api.fastapi-server` are registered experimental features.

Deviations:

- The abbreviation `--generate-s`, which argparse used to expand to `--generate-schema-validators`, is now ambiguous. An alias would have preserved it, but it showed in the help, the CLI reference and the skill reference, and earlier options sharing a prefix added none.
- `--check` lists changed paths instead of printing diffs: stdout is reserved for the diagnostics JSON, and ENTRY §4 prints no generated code.
- The manifest projected mapping keys with `str()`, so an operation reference key recorded the reference's Python repr, with the absolute URI of a named document. Keys other than strings are now projected like values and recorded as canonical JSON, such as `{"document":"/inputs/root","pointer":"/paths/~1pets/post"}`.

Tests:

- The tests follow the model suites: they reach the target only through the public entry points, with inputs and expected files on disk, and mock nothing but abnormal paths. The S05–S07-2 tests, which called the coordinator with the FastAPI target or a fixture target, now do the same, and the fixture target and configuration are gone.
- The command line runs through `run_main_and_assert` and `run_main_with_args`: a generation that writes the expected pets models and package, then checks that pass, find a changed model and fail on a removed owned file; `--target-output` with both `--diagnostics-json` forms; stdin input and a rejected backend; every usage error and conflict, including `--input-model`, jobs and colliding diagnostics paths; files that are not a report of this target, a replaced report and a failed write; unreadable, unknown and invalid target files, an unsupported backend and a directory as model metadata; a TOML file with every setting, whose values the manifest records, updating one router group; and an unresolved reference and a failing renderer.
- `render_fastapi` renders every render fixture. Each backend's Python modules are compared with an expected package directory through `assert_generated_modules_output` (the pets package, which the command line must reproduce, includes its runtime copy), and a report shows the other artifacts, the copied runtime modules, the manifest decisions, diagnostics and hook contexts. The fixtures format their target files with the settings of their own root instead of the repository's `pyproject.toml`. The regeneration, server and OpenAPI suites generate with `generate_fastapi`.
- The S05 scenarios run on the FastAPI target: a hook edits the manifest while the target renders, custom `application.jinja2` roles produce invalid, misplaced and newer syntax, a method name collision makes the target refuse to render, and pydantic v2 replaces the backends the server does not support. Shared settings are validated through `FastAPIConfig` and flat target files through `--target-config`. Mocks remain for failed publication steps, races and lock failures, and held locks stand in for another generation.
- The changed sources are fully covered; strict Pyright reports nothing for `_fastapi`, `_target_cli.py`, `api_types.py` and `fastapi`, and ty nothing new.

Benchmarks (one session, as in S07-2): 10, 50 and 200 operations render in 52.4, 206.0 and 824.7 ms on S07-2 and 53.3, 208.0 and 827.8 ms on S07-3; the difference is the README. Command-line cold starts are unchanged: `--version` 25 ms, `--help` 33 ms and a model run 137 ms on both, and a model run imports no target module. Generating the pets server takes 283 ms and checking it 263 ms.
