# dcg requirements, contracts, and acceptance coverage

Updated 2026-09-19. This ledger maps dcg requirements to their authoritative design contracts, independent acceptance criteria, and maintenance responsibilities. Every item is still at the design stage; the proposed generators and runtimes have not been implemented or tested.

X/G identify combination tests in [ACCEPTANCE](ACCEPTANCE.md), C identifies [client requirements](CLIENT-REQUIREMENTS.md), and F identifies [FastAPI requirements](FASTAPI-REQUIREMENTS.md). B/MC/FA/CG/RT/P/TY identify the detailed contracts' independent acceptance cases. These identifiers describe dcg requirements, not completed test results.

## 0. Entry points to the agreed specification

The initial FastAPI server supports **two backends: Pydantic v2 BaseModel and Pydantic v2 dataclass**. The initial client supports **all five backends**, adding standard-library dataclass, TypedDict, and msgspec Struct. The server stage implements the shared wire foundation and the two backend codecs; the client stage adds converters and conformance tests for the other three. Existing D model-only behavior for all five backends, output bytes, APIs, dependencies, and performance are protected. Server and client are selected and generated independently: two backend choices for the server and all five for the client. There is no simultaneous-generation API.

## 2. Explicit OAuth and additional-protocol boundaries

A single statement of OAuth support is insufficient. Initial requirements include caller-provided tokens/providers and client-credentials acquisition, with explicit refresh contracts for APIs that issue refresh tokens, expiry/skew, scope/audience, concurrent refresh, and resending after 401. Authorization-code/PKCE, device authorization, browser interaction, code verifiers, state, and token storage are separate flow capabilities. Design provider integration even for flows without automation; a generic client must not open a browser or store secrets on its own. A token-acquisition endpoint alone does not implement the entire interactive flow.

Apply the same principle to WebSockets, webhook signatures, resumable uploads, polling, and pagination. First specify the source, version, and validation of information absent from OpenAPI. API-conditional capabilities are contracts for APIs that need them, not features to add later by breaking the architecture. Do not invent exactly-once guarantees when the API itself does not guarantee delivery or idempotency.

## 3. FastAPI coverage and reuse of investment

Existing source, tests, and golden outputs for F01–F13 are mapped individually in [FASTAPI-REQUIREMENTS](FASTAPI-REQUIREMENTS.md). The server supports the two Pydantic v2 backends. Preserve F's use cases while fixing the boundaries between standard FastAPI interfaces, required codec adapters, and explicit Request access. Shared server/client boundaries must satisfy both F and C requirements, but server acceptance must not add FastAPI projection for the three client-only backends.

| Shared asset | Server use | Client use | Additional work that must not be counted as already shared |
|---|---|---|---|
| Effective operations and parameter/body/media facts | Routes, arguments, forms/uploads, validation | Methods and wire parameter/body codecs | FastAPI Depends/UploadFile and HTTP encoding are separate |
| All responses/statuses/headers | Suitable primary response_model, required adapters/explicit Response, served response declarations, and independent HTTP behavior | Status/media-specific decoding, typed errors, raw access, streams | Do not write server-primary or standard-interface choices back into the shared table |
| Security/server/source/use context | Authentication boundaries, server mounts, diagnostics | Credentials, URLs, request/response codecs | Do not put secrets, tokens, or refresh state in the shared parser |
| Final type/import/module mappings and attempt identity | Route annotations using reused models | Method/response typing using reused models | Do not add client-specific model mutation, reparsing, or name reservation |
| Shared wire rules and codecs for the two Pydantic v2 backends | Required request/response adapters and public ResponseCodecs; standard FastAPI profiles where suitable | The same converters and schema/presence rules connected to requests/responses | Reuse the earlier source, but test client direction, HTTP, and typing separately. Two backends do not eliminate every nullable/mode/alias difference |
| Three additional backend converters in the client stage | Not generated for the server | Integration with existing dataclass/TypedDict/msgspec types, constructors, presence, and serializers | Adding them to shared source does not make them completed server work. Finish conformance for all five client backends before initial publication; do not expand FastAPI native support |
| Generated-file ownership, configuration validation, and diagnostic rules | Selective router regeneration and handwritten-code protection | SDK regeneration and package/private-runtime updates | Target-specific layouts and public APIs need not be identical |

The entire client runtime need not be embedded into FastAPI from the start. However, reducing shared information to the server's minimum single response or type strings would reintroduce duplicate parsing and type repair when adding the client. The server's backend selection must not reduce shared parser/binding information: preserve the boundaries for all five existing D and client backends.

Distribution and verification also differ by target. Do not bundle converters or dedicated dependencies for the three unsupported built-in server backends. Generate the client's dependency closure from the selected backend and enabled capabilities. Adapters and dependencies for explicit custom field types in Pydantic v2 models are a separate, actual need. Even when every server interface is native, common validator dependencies remain for public factories; zero codec calls on the native hot path does not mean zero package dependencies. Even on the server, a plain Pydantic v2 dataclass T cannot always recover omission versus nullable None. Explicit bound-factory/presence/envelope operations and independent wire oracles remain necessary. Additional converters and client tests address standard dataclass, TypedDict, and msgspec differences.

Preserving supported model types allows application code to retain its existing names, validators, and model APIs across specification updates. Count the shared wire foundation and first two backend codecs once. Separate the other three client converters and conformance tests, client integration tests for the first two, and retry/stream/auth/transport costs. Do not infer effort or savings from backend counts. Independent oracles, API-specific metadata, and dependency-update decisions remain necessary. See [maintenance responsibilities](RATIONALE.md).

## 4. Implementation evidence required

Preservation of existing dcg behavior, complete binding for two server/five client backends, runtime performance, and behavior across all 33 client areas require implementation tests. Each area has a design contract and independent acceptance cases; record actual fixtures, environments, commands, and results when implemented. Document review and CI on this planning change do not establish product acceptance.

Type safety throughout the new generated output maps to the TY-series oracles in [TYPING](DECISIONS-TYPING.md). Preserve compatibility with existing D types and provide separate positive and negative call fixtures for both server backends and all five client backends. Evaluate the benefits of concrete types together with the added Python-version, type-checker, and extension-Protocol conformance costs.
