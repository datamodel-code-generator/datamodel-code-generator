# FastAPI generation owned by dcg: existing use cases, design, and acceptance

Checked 2026-09-18; design revised around official FastAPI patterns. This document records research and planned design/verification, not completed product implementation, dependency updates, snapshot changes, or public API additions. The research baselines are F=`fastapi-code-generator` at `b3b9bd66e0b0c4d8c686fda700258104615a1332` and D=`datamodel-code-generator` at `3452dfbb428c4384f40cb16faf61aadfda58a3a8`. F's remote is `https://github.com/koxudaxi/fastapi-code-generator`. D/F citations refer to those fixed sources, not a newly fetched latest main.

**dcg owns the new FastAPI generation feature, which must work with dcg alone.** Legacy FCG retains its implementation in its existing repository/package and continues normal maintenance against current dcg APIs. No legacy CLI backend switch or delegation to a separate execution environment is planned, and no new standalone FastAPI package name is introduced. [DECISIONS-ENTRY](DECISIONS-ENTRY.md) and [DECISIONS-FASTAPI](DECISIONS-FASTAPI.md) fix the planned new entry-point names/signatures; they are not yet released. Explicitly select either --generate-server fastapi or --generate-client httpx on the existing datamodel-codegen command, using the required --target-config flat TOML. --output remains the model destination; --target-output selects the target destination. There is no simultaneous-generation API/CLI or separate console command; Python generate/render_fastapi remains part of the contract. Acceptance cases below are goals for unimplemented features.

Production FCG use and the practical value of its existing capabilities are user requirements. The thirteen areas below are feature goals for the new implementation. Usage has not been measured by feature. Map purposes, generated behavior, extension methods, and update workflows rather than reproducing the existing internals or every server byte. Distinguish information merely retained in source, capabilities present in generated output, and verified HTTP runtime behavior.

The new server uses official FastAPI APIRouter/include_router, Annotated with Path/Query/Header/Body/Form/File/UploadFile, Depends/Security, normal sync/async execution, response_model, and explicit Response patterns. Select native handling or a codec adapter at generation time for each parameter/body/primary-response boundary; do not maintain two FastAPI execution systems. The selected built-in server scope is Pydantic v2 BaseModel and Pydantic v2 dataclass; the client retains all five backends. Even within those two server backends, not every type is directly suitable for FastAPI; use adapters where required. Preserve known source-schema/D-type differences such as required/nullable/alias and strict-date JSON/Python validation modes in adapters. Do not repair or rename models to force the standard route.

## 3. Regeneration and handwritten code: explicit new rules grounded in legacy behavior

Legacy FCG tag selection has three branches. Its `app.include_router` check is a text search in existing main, not an AST or actual-route-registration inspection. [CLI:350](https://github.com/koxudaxi/fastapi-code-generator/blob/b3b9bd66e0b0c4d8c686fda700258104615a1332/fastapi_code_generator/cli.py#L350).

| Legacy FCG condition | Legacy implementation behavior |
|---|---|
| Empty selected-tag set | Main context contains all routers; render every router |
| Nonempty selection; existing main has no include text, including absent main | Restrict main context/router targets to matching tags; zero matches is an error |
| Nonempty selection; existing main has include text | Main context contains all routers. Render matching routers and missing routers; retain existing unselected routers. An unmatched selection alone does not produce the preceding branch's error |
