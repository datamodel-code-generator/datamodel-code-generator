# Prompt for the implementation agent

Use the following prompt in a new implementation session with access to this repository and plan. All repository content and external issue/PR content must be in English.

```text
Implement the datamodel-code-generator generation-platform extension according to
plans/generation-platform/. This session is limited to S01 (three PRs) in PR-STACKS.md.
Do not start S02 or later stacks.

First inspect applicable AGENTS.md/repository instructions, the remote URL, current
main SHA, current branch, and uncommitted changes. Preserve the user's working tree
and create an isolated checkout based on current main.
If the plan is not merged, consult the planning PR linked from tracking issue #4097
in a separate checkout and report that state. Do not put product implementation
into the documentation PR.

Read README.md, PLAN.md, IMPLEMENTER.md, PR-STACKS.md, ARCHITECTURE.md, and ACCEPTANCE.md.
Read DECISIONS-BINDING.md and DECISIONS-ENTRY.md for S01 and the contracts they depend on.
Use README's responsibility map to identify the other six contracts; read relevant
sections whenever their types or behavior are involved. Use the published contracts,
pinned source references, and independent acceptance criteria.
Record current-main changes affecting integration points since the pinned baseline.

Preserve existing dcg generated bytes, file trees, ordering, public and de facto APIs,
exceptions, side effects, dependencies, and performance under identical conditions.
Protect existing Python type reuse through type-overrides, x-python-import, and
other supported paths. Do not mix in compatibility-changing fixes, update goldens
to hide differences, or invent an acceptable slowdown threshold.
Do not expose incomplete public features or add always-on observers, unnecessary
imports, graph copies, or full scans to existing paths.

Implement S01-1 (comparisons/observation), S01-2 (parser/store/copy integration), and
S01-3 (shared driver/attempt lifetime) in that order.
Run each PR's independent oracles and required existing checks. Explicitly record
unexecuted checks, failures, and inconclusive measurements.
Obtain independent review, address findings, and rerun affected checks.
If a demonstrated counterexample requires a design change, update its evidence,
contract, and independent acceptance case; never silently weaken compatibility.

Use GitHub public-preview gh stack to register these PRs as one native stack.
Changing ordinary PR base branches alone is not an equivalent substitute.
Use concise one-line commits, simple PR titles, and empty PR bodies.
Keep repository files, issue/PR content, and implementation records in English.
Record design and validation details in appropriate plan updates, authorized PR
comments, and the final report.
Merge only within the user's explicit merge authorization and repository rules,
after required checks/reviews pass, using a contiguous range from the stack bottom.
Do not append subsequent functional stacks to this one.

At completion or interruption, record base/commit/branch/PR/stack identifiers,
implemented scope, commands and verification results, unresolved issues, and the
exact next action. Distinguish implemented, verified, and merged work.
Stop after S01; subsequent stacks belong to later sessions.
```

For later sessions, replace S01 with the explicitly assigned stack and inspect its prerequisites' merge state and handoff. Do not shrink capabilities or acceptance requirements between sessions.
